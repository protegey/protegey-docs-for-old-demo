# Failures & Fallbacks

Reliability is a shared responsibility. While we strive for 100% uptime, network issues, timeouts, and outages can occur. Your integration **must** be resilient.

## The Golden Rule

> **Never block a good user because of a fraud vendor failure.**

If the Protegey API is unreachable or returns a 500 error, your application should implement a "Fail Open" or "Fail Closed" strategy based on your risk appetite.

### Strategy A: Fail Open (Recommended)
**Scenario**: User is logging in, API times out.
**Action**: Allow the login. Log the error.
**Pros**: Zero friction for legitimate users.
**Cons**: Potential fraud could slip through during the outage.

### Strategy B: Fail Closed
**Scenario**: User is logging in, API times out.
**Action**: Block the login or ask for MFA.
**Pros**: Maximum security.
**Cons**: High friction; good users may be blocked or frustrated.

## Circuit Breakers

We recommend implementing a [Circuit Breaker](https://martinfowler.com/bliki/CircuitBreaker.html) pattern.
1. If the API fails X times in Y seconds, "trip" the breaker.
2. While open, stop calling the API and immediately return your default decision (Fail Open/Closed).
3. After Z seconds, allow a single test request through.
4. If successful, close the breaker and resume normal operation.

## Retries

### Idempotency
- **Queries (`GET`)**: Safe to retry.
- **Signals (`POST`)**: Not idempotent. Retrying a failed signal submission may result in duplicates if the original request actually succeeded but the response was lost.

### Exponential Backoff
If you receive a `429 Too Many Requests` or `5xx Server Error`:
1. Wait 100ms
2. Retry
3. Wait 200ms
4. Retry
5. Wait 400ms...

Do not simply loop retries immediately; this exacerbates the issue.
