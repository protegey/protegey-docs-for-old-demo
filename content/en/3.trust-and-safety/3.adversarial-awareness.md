Protegey is a high-value target. Fraud actors actively attempt to understand, probe, and ultimately evade our detection systems. This page explains how we design for that reality.

## The Threat Model

We operate under a consistent assumption: **our adversaries are sophisticated, well-resourced, and persistent**. This includes:

- Organised fraud rings that systematically test detection boundaries
- Insiders with partial knowledge of financial institution controls
- Technical actors capable of scripting API interactions to map system behaviour
- Actors who monitor outcomes (block/allow) to reverse-engineer scoring logic

Designing without this assumption leads to systems that fail the moment they are encountered by a motivated adversary.

## Probing Resistance

### Opaque Scoring Responses

Risk scores returned to partners are intentionally coarse. Specific threshold values, factor weightings, and detector identifiers are never exposed in API responses. A fraud actor observing API output cannot determine:

- What score would have triggered a different decision
- Which specific signals contributed to their score
- What the score would be if they changed a single input field

### Non-Deterministic Responses

Detection logic includes contextual and temporal components that make brute-force boundary testing unreliable. The same payload submitted at different times, from different network contexts, or with varying entity history may produce different outcomes — legitimately.

### Rate Limiting as a Defence Layer

API rate limits are not just operational controls. They function as an adversarial constraint: an actor cannot submit enough probing requests in a meaningful time window to map system behaviour statistically. Hitting rate limits produces generic 429 responses that reveal nothing about detection state.

## Adversarial Machine Learning

Our detection pipeline is deliberately not a single end-to-end neural model that could be inverted or attacked through gradient estimation. Instead:

- **Detector-based architecture**: Each of the 9 detectors evaluates a specific, narrow behavioural signal — ranging from single-signal patterns (velocity, outlier amounts, SIM swap) to cross-actor graph patterns (beneficiary concentration, agent concentration, attack chains). No single detector output is predictable from API responses alone.
- **Taxonomy + fusion**: Fraud categories are assigned after detection — not before. Actors cannot probe taxonomy logic by varying inputs.
- **Network component (40% weight)**: Graph neighbourhood risk is based on the full history of all connected entities in the network. An actor cannot reconstruct their network neighbourhood from public information.
- **Historical component (10% weight)**: Rolling 90-day entity risk history means evasion requires sustained clean behaviour over months, not a single clean transaction.

## No Disclosure Policy

Specific detection thresholds, base severity values, fusion weights, and taxonomy identifiers are not disclosed externally — including to partners. This is a deliberate security boundary, not an oversight.

::callout{icon="i-lucide-shield-alert" color="amber"}
**Why this matters**: If an actor knows that `LARGE_OUTLIER_TRANSACTION` fires at 3σ deviation, they structure transactions to stay at 2.9σ. The protection value of the detector is eliminated.
::

Reason codes returned to partners (e.g., `VELOCITY_HIGH`, `DEVICE_ANOMALY`) convey _categories_ of risk, not thresholds. Partners receive enough information to act on; adversaries receive too little to exploit.

## Network Effect as Adversarial Resilience

The collective intelligence architecture creates an asymmetric advantage:

- A fraud actor who evades detection at one partner still triggers signals at every other partner they interact with
- Cross-partner signal correlation exposes patterns that no single partner can see
- New fraud patterns identified by any partner propagate to the entire network within milliseconds

This means an adversary must simultaneously evade detection across every participating institution — a bar that increases with network size.

## Canary Signals and Honeypot Monitoring

Protegey maintains synthetic entity profiles in the network that have no legitimate associated activity. Any signal referencing these identifiers indicates:

- An actor guessing identifiers
- Data harvested from a previous breach
- Systematic enumeration of the identity space

Canary triggers immediately elevate monitoring on the associated API key and partner account without alerting the actor.

## Red Team Operations

Our security posture is validated through ongoing adversarial testing:

- **Annual external penetration testing** targeting the API ingestion pipeline, partner portal, and admin interfaces
- **Internal red team exercises** simulating partner credential compromise and signal manipulation
- **Detection logic audits** to identify patterns that could be reverse-engineered from public documentation

Findings feed directly into detection updates and public documentation review.

## What This Means for Partners

Partners operating in good faith are unaffected by these controls. Legitimate integration produces consistent, explainable results within documented response formats.

If you encounter unexpected behaviour during integration, it is almost always a configuration issue rather than an adversarial detection. The [Sandbox environment](/en/partners/environments/sandbox) is designed to surface integration errors clearly without triggering production adversarial controls.

Contact [support@protegey.com](mailto:support@protegey.com) if you believe legitimate traffic is being affected by adversarial controls.
