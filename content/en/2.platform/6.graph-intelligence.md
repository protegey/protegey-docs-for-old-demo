# Graph Intelligence

Fraud rarely acts in isolation. A device fingerprint shared across multiple phone numbers, a single IP address appearing in dozens of transactions, a mule account connected to 14 previously flagged entities — these are graph problems. Protegey's graph intelligence engine maps these connections and propagates risk through entity networks in real time.

---

## The Core Insight

Standard fraud detection treats each transaction as independent. Graph intelligence treats every entity as a node in a network and every shared attribute as an edge. When one node in a network is confirmed fraudulent, that risk signal propagates outward — surfacing previously low-scored entities that share infrastructure.

This is how Protegey catches fraud rings that defeat detector-by-detector analysis.

---

## What Gets Connected

The hot graph builds edges from shared attributes between entities:

| Edge Type | Description | Strength |
|-----------|-------------|---------|
| `shared_device` | Same device fingerprint | Very high (0.9–1.0) |
| `shared_ip` | Same IP address in recent window | High (0.7–0.89) |
| `shared_phone` | Same MSISDN hash linked to multiple accounts | High (0.7–0.89) |
| `shared_network` | Same carrier + approximate location | Moderate (0.5–0.69) |
| `co_occurrence` | Entities appear in the same transaction | Moderate (0.5–0.69) |
| `behavioral` | Similar transaction patterns (timing, amounts) | Moderate (0.5–0.69) |

Edge strength is recalculated on each signal ingestion. Edges below 0.3 strength are pruned from the active graph.

---

## Risk Propagation

When a new signal is ingested, the graph engine:

1. Looks up the entity's direct neighbors (1-hop) and second-degree connections (2-hop)
2. Computes a **propagated risk** score — a weighted average of neighbor risk scores, decayed by hop distance and edge strength
3. Applies a graph amplifier to the `network_score` component of the weighted risk fusion:
   - Any neighbor with `risk_score > 80` amplifies the network score by up to **+15 points**
   - High-risk neighbor count is factored into the final fused score

This means an entity with a low individual risk score can receive a substantially higher final score if it shares infrastructure with confirmed fraud actors.

---

## Fraud Ring Detection

A fraud ring signature is present when a cluster of entities shares multiple edge types with high strength. The visualization endpoint (`GET /entities/{uuid}/graph-visualization`) returns force-graph data that makes these clusters visually apparent.

Classic fraud ring patterns:

- **Device farm**: 10–50 accounts sharing 1–3 device fingerprints, each transacting just below threshold
- **Mule network**: Accounts with `confirmed_fraud` status feeding into a central aggregator account
- **Synthetic identity ring**: Entities with unique phone numbers but identical device + IP patterns

## Accessing Graph Data

### Neighborhood Risk Analysis

```http
GET /api/v1/partner/entities/{uuid}/graph
```

Returns aggregate risk metrics for the entity's 2-hop neighborhood:
- `direct_neighbors` — count of 1-hop connections
- `avg_risk` — average risk score across all neighbors
- `max_risk` — highest neighbor risk score
- `high_risk_count` — neighbors with `risk_score > 80`
- `propagated_risk` — computed network risk contribution

### Network Visualization

```http
GET /api/v1/partner/entities/{uuid}/graph-visualization
```

Returns force-graph data (nodes + edges) for rendering in the partner portal's network visualization view:
- BFS traversal up to depth 2
- Capped at 200 nodes (truncated flag returned if exceeded)
- Supports `node_type[]` filter and `from`/`to` temporal range

### Privacy: Masked IDs

All external entity identifiers in graph responses are masked to the first 8 characters followed by `****`. This prevents cross-partner entity inference while still allowing your team to recognize entities from your own records.

Example: `a1b2c3d4****` — if `a1b2c3d4` matches the first 8 chars of your stored hash, this is your entity.

## Performance Characteristics

The hot graph runs entirely in PostgreSQL with a Redis adjacency cache:

| Metric | Value |
|--------|-------|
| Cache TTL | 15 minutes |
| Max traversal depth | 2 hops (configurable) |
| Max nodes returned | 200 |
| Edge computation latency | < 5ms (cached) |
| Graph rebuild (cold start) | Weekly background job |

For larger graph traversals or cold graph analytics (historical patterns, multi-degree community detection), Phase 12 will introduce a dedicated Neo4j instance. The hot graph is optimised for real-time ingestion path performance.

## Practical Guidance

**When a new entity arrives with a high graph risk**: the entity's own signals may be clean, but the network context tells a different story. Treat graph-amplified scores as a signal to increase manual review frequency, not as an automatic block — false positives in network propagation happen when legitimate users share infrastructure (e.g., mobile money agents serving the same community).

**When graph-visualization shows a tight cluster**: export the entity list and cross-reference with your KYC records. Shared devices across unrelated customers often indicates account takeover rather than an organized ring.

**When `propagated_risk` exceeds 80 but individual signals are clean**: consider opening a proactive case for enhanced monitoring. Use `POST /cases` with `type: enhanced_monitoring` and attach the entity UUIDs from the graph neighborhood.
