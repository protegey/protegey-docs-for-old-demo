Every risk verdict from Protegey answers four questions:

1. **How risky?** → `risk_score` + `risk_level`
2. **How sure are we?** → `confidence`
3. **Why?** → `explanations[]`
4. **What should you do?** → `recommendation`

This unified contract applies to both `/evaluate` and `/risk/assess`. The `/evaluate` response is lighter (fewer signals, no full history); `/risk/assess` is enriched with behavioral depth. The structure is identical.

---

## risk_score

A continuous 0.0–1.0 float representing the probability of fraud or abuse. Higher = riskier.

The score is produced by the **Weighted Risk Fusion Engine (NUFSS)**, which aggregates four dimensions:

| Dimension | Weight | Source |
|---|---|---|
| Behavioral | 35% | Detector aggregate (velocity, outlier, SIM swap, device, travel) |
| Network | 40% | Hot graph 2-hop propagated risk |
| Contextual | 15% | Resolver enrichment (geo, device, carrier, time-of-day) |
| Historical | 10% | 90-day rolling entity average |

The fused float is what you see as `risk_score`. It is **deterministic** — the same inputs produce the same score.

---

## risk_level

Normalized buckets derived from `risk_score`:

| `risk_level` | `risk_score` Range | Meaning |
|---|---|---|
| `low` | 0.00 – 0.20 | Normal activity, no significant signals |
| `medium` | 0.21 – 0.50 | Suspicious patterns; step-up authentication recommended |
| `high` | 0.51 – 0.80 | Strong fraud indicators; manual review or challenge |
| `critical` | 0.81 – 1.00 | High confidence of fraud; block and investigate |

These buckets are stable — they will not change between API versions without a major version bump and deprecation notice.

---

## confidence

A 0.0–1.0 float representing how certain Protegey is in the `risk_score`. A high risk score with low confidence means: "this looks risky, but we don't have enough data to be sure."

**What drives confidence:**

- **Signal volume**: More signals = more certainty
- **Signal recency**: Fresh signals carry more weight than stale ones
- **Pattern consistency**: Consistent patterns across multiple detectors increase confidence
- **Match strength**: Strong OSINT hits, exact graph matches, and high-quality identifiers raise confidence

### Confidence × Risk Quadrant

Use this matrix when routing decisions:

| | High Confidence | Low Confidence |
|---|---|---|
| **High Risk** | Act immediately | Investigate further |
| **Low Risk** | Safe to proceed | Insufficient data |

::callout{icon="i-lucide-info" color="blue"}
**New entities have lower confidence by default.** An entity seen for the first time today will have `confidence` around 0.3–0.5 even if detectors fire. This prevents aggressive action on first-time actors without behavioral history.
::

## explanations[]

A structured list of reasons that contributed to the risk verdict. Each explanation is machine-readable and human-readable.

### Explanation Object

```json
{
  "code": "DEVICE_REUSE",
  "category": "device",
  "severity": "high",
  "message": "Device fingerprint linked to 3 flagged entities",
  "evidence": {
    "linked_entity_count": 3,
    "highest_linked_risk": 0.91
  }
}
```

### Fields

| Field | Type | Description |
|---|---|---|
| `code` | string | Machine-readable code (see reference below) |
| `category` | string | Signal category (see categories below) |
| `severity` | string | `low`, `medium`, `high`, or `critical` |
| `message` | string | Human-readable explanation in English |
| `evidence` | object | Supporting data used to generate this explanation |

### Standard Categories

| Category | What It Covers |
|---|---|
| `identity` | Phone, email, national ID risk signals |
| `device` | Device fingerprint anomalies, reuse patterns |
| `network` | Graph neighborhood risk, linked entities |
| `behavioral` | Velocity, outlier amounts, temporal anomalies |
| `historical` | Past fraud involvement, prior status changes |
| `synthetic_identity` | Signals consistent with synthetic ID fraud |
| `transactional` | Transaction-level patterns (structuring, cross-border) |

### Explanation Code Reference

| Code | Category | What It Means |
|---|---|---|
| `DEVICE_REUSE` | device | Device fingerprint linked to multiple distinct entities |
| `NEW_DEVICE` | device | First-ever device for this entity combined with high-risk geo |
| `RAPID_VELOCITY` | behavioral | Transaction frequency exceeds threshold within rolling window |
| `LARGE_OUTLIER` | behavioral | Transaction amount is a statistical outlier vs entity baseline |
| `SIM_SWAP_PROXIMITY` | behavioral | Transaction occurred within hours of a SIM swap event |
| `IMPOSSIBLE_TRAVEL` | behavioral | Same entity in two geographic locations within impossibly short time |
| `EMAIL_RISK_PATTERN` | identity | Email provider or pattern associated with synthetic identities |
| `PHONE_NETWORK_RISK` | identity | Carrier or number type associated with fraud patterns |
| `NETWORK_CONTAMINATION` | network | Entity connected to known fraudsters in the graph |
| `HIGH_RISK_NEIGHBORHOOD` | network | 2-hop neighborhood average risk exceeds threshold |
| `OSINT_MATCH` | identity | Entity matches a sanctions, PEP, or adverse media record |

## recommendation

A structured action directive based on the combined `risk_score` and `confidence`.

```json
{
  "action": "review",
  "priority": "high"
}
```

### Action Types

| `action` | When Used | Suggested Response |
|---|---|---|
| `allow` | Low risk, sufficient confidence | Proceed normally |
| `review` | Medium risk or low confidence | Manual review queue |
| `challenge` | High risk, moderate confidence | Step-up authentication (OTP, biometric) |
| `block` | Critical risk or confirmed match | Block transaction, open investigation |

### Priority Levels

| `priority` | Meaning |
|---|---|
| `low` | Informational, no urgency |
| `medium` | Review within normal SLA |
| `high` | Review promptly (within hours) |
| `critical` | Immediate action required |

## Unified Response Contract

Both `/evaluate` and `/risk/assess` return the same top-level structure. The difference is depth:

```json
{
  "risk_score": 0.73,
  "risk_level": "high",
  "confidence": 0.81,
  "explanations": [
    {
      "code": "RAPID_VELOCITY",
      "category": "behavioral",
      "severity": "high",
      "message": "12 transactions in the last hour — threshold is 10",
      "evidence": { "count_1h": 12, "threshold": 10 }
    },
    {
      "code": "NETWORK_CONTAMINATION",
      "category": "network",
      "severity": "medium",
      "message": "Shares device with 1 confirmed fraudster",
      "evidence": { "shared_with_confirmed": 1 }
    }
  ],
  "recommendation": {
    "action": "review",
    "priority": "high"
  }
}
```

`/evaluate` returns this structure with signal-level context. `/risk/assess` additionally includes `profile`, `network`, and `history` blocks with the full entity intelligence package.

## Composite Scoring Logic

This is a simplified description for partners. Internal scoring mechanics are confidential.

- **Recency decay**: Signals older than 90 days contribute less weight. Signals from the last 24 hours carry full weight.
- **Signal diversity**: Multiple independent detectors firing increases both `risk_score` and `confidence` more than a single detector firing repeatedly.
- **Network amplification**: An entity connected to confirmed fraudsters via the graph sees its `network_score` component amplified proportionally.
- **OSINT confidence gating**: OSINT matches with confidence < 0.3 surface as `review` explanations but do not drive automated `block` recommendations.

---

## Design Rules

These are commitments, not aspirations:

- **No black boxes**: Every non-trivial risk score includes at least one `explanation` entry
- **Deterministic outputs**: Same inputs → same output (modulo graph state changes between calls)
- **Backward compatibility**: New `explanation` codes are additive; existing codes are never removed without deprecation
- **Auditability**: All scoring inputs and outputs are logged and available via the Audit Log API
