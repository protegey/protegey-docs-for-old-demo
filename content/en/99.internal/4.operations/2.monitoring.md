# Monitoring & Health

## Health Endpoints

### Liveness Probe: `/ready`

```http
GET /ready
```

Lightweight liveness check. Verifies database connectivity only. Target response time < 100ms. Used by load balancers and container orchestrators for readiness gates.

**Response (healthy)**:
```json
{ "status": "ok", "db": "connected", "latency_ms": 4 }
```

**Response (degraded)**:
```json
{ "status": "degraded", "db": "error", "error": "Connection timeout after 5000ms" }
```

HTTP 200 on healthy, HTTP 503 on any failure.

### Deep Health Check: `/health`

```http
GET /health
Authorization: Bearer {internal-token}  # or admin session
```

Comprehensive health check across all system components. Response is cached for 30 seconds to prevent thundering herd on monitoring polls.

**Response**:
```json
{
  "status": "ok",
  "timestamp": "2026-03-16T10:00:00Z",
  "cache_age_seconds": 12,
  "components": {
    "database": { "status": "ok", "latency_ms": 3, "pool_size": 10, "active_connections": 2 },
    "redis": { "status": "ok", "latency_ms": 1, "memory_used_mb": 142 },
    "queue": { "status": "ok", "pending": 14, "failed": 0, "workers": 4 },
    "reverb": { "status": "ok", "connections": 87 },
    "graph_cache": { "status": "ok", "hit_rate": 0.94, "keys": 2841 },
    "osint_ingestion": { "status": "ok", "last_run": "2026-03-16T03:00:00Z", "records_processed": 14209 }
  }
}
```

## Queue Monitoring

### Queue Dashboard

Available in the admin panel at `/admin/queue`. Provides:
- Per-queue pending/processing/failed/completed counts
- Failed job table with exception preview
- One-click retry (single job or bulk by queue)
- Purge failed jobs (requires `super_admin` role)

### Queue Names

| Queue | Purpose | Worker Count |
|-------|---------|-------------|
| `default` | General async work | 2 |
| `signals` | Signal ingestion jobs (high priority) | 4 |
| `graph` | Graph node/edge updates | 2 |
| `osint` | OSINT ingestion, freshness recompute | 1 |
| `webhooks` | Outbound webhook dispatch | 2 |
| `compliance` | SAR, AML flag processing | 1 |
| `notifications` | Email, Reverb push | 2 |

### Failed Job Runbook

1. **Check the exception**: Admin → Queue → Failed → expand job → view `exception` field
2. **Common causes**:
   - `ModelNotFoundException`: Entity was deleted between dispatch and execution — safe to discard
   - `ConnectionException` (Redis): Redis pod restart — retry is safe
   - `CentryContextException`: Job dispatched without context binding — fix dispatcher, do not retry without code fix
3. **Retry single job**: `php artisan queue:retry {job-id}`
4. **Retry all**: `php artisan queue:retry all` — use with caution on `signals` queue
5. **Purge after investigation**: `php artisan queue:flush`

## Context-Aware Job Tracking

All jobs extending `ContextAwareJob` serialize the `CentryContext` (partner UUID + schema) at dispatch time. This ensures:
- Jobs run against the correct PostgreSQL schema (`public` vs `sandbox`)
- Failed jobs can be attributed to the correct partner in logs
- Queue metrics can be partitioned by partner for SLA monitoring

**Verification**: If a job is failing with `search_path` or `schema` errors, check that it extends `ContextAwareJob` (not the base Laravel `Job` class).

```php
// Correct
class ProcessSignalJob extends ContextAwareJob { ... }

// Wrong — will use default search_path
class ProcessSignalJob extends Job { ... }
```

## Alerting Thresholds

Configure in your monitoring system (Grafana / Datadog) against the `/health` endpoint:

| Metric | Warning | Critical |
|--------|---------|---------|
| `queue.failed` | > 10 | > 50 |
| `queue.pending` (signals) | > 500 | > 2000 |
| `graph_cache.hit_rate` | < 0.80 | < 0.60 |
| `database.latency_ms` | > 50ms | > 200ms |
| `redis.latency_ms` | > 10ms | > 50ms |
| `osint_ingestion.last_run` age | > 26h | > 50h |
