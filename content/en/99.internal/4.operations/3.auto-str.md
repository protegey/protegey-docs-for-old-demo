# Auto-STR Correlation

## Overview

The `AutoStrCorrelationService` detects when both `structuring` and `velocity_breach` AML flags fire on the same entity within a 72-hour rolling window. When this pattern is detected, a Suspicious Activity Report (SAR) is automatically drafted and the partner is notified.

Auto-STR is a compliance aid — it reduces the chance that a co-occurring flag pattern is missed during manual review. The SAR remains in `draft` status and is never automatically filed.

---

## Trigger Conditions

A SAR is auto-drafted when **all** of the following are true:

1. `structuring` flag exists for `entity_uuid` within the last `WINDOW_HOURS` (default: 72h)
2. `velocity_breach` flag exists for the same `entity_uuid` within the same window
3. No existing SAR is already `open`, `draft`, or `under_review` for this entity within the dedup window (`DEDUP_HOURS`, default: 168h / 7 days)

The dedup window prevents duplicate SARs from being created for sustained multi-day patterns.

## Service Configuration

```php
// apps/core/config/aml.php
'auto_str' => [
    'window_hours' => env('AUTO_STR_WINDOW_HOURS', 72),
    'dedup_hours'  => env('AUTO_STR_DEDUP_HOURS', 168),
    'enabled'      => env('AUTO_STR_ENABLED', true),
],
```

Both constants will be migrated to DB-backed `configurable_rules` in Phase R.

## SAR Draft Creation

When triggered, `AutoStrCorrelationService::checkAndDraft()` calls `SARService::draft()` with:

```php
$sar = $this->sarService->draft($partnerUuid, $entityUuid, [
    'trigger'          => 'auto_str_correlation',
    'structuring_flag' => $structuringFlag->uuid,
    'velocity_flag'    => $velocityFlag->uuid,
    'window_hours'     => $this->windowHours,
]);
```

`SARService::draft()` pre-computes:
- Total transaction count and aggregate amount within the window
- List of contributing signal UUIDs
- Preliminary narrative fragment (populated by `generateNarrative()`)

After draft creation, a `compliance.sar.auto_drafted` webhook event is dispatched to all of the partner's active webhook endpoints:

## Co-Occurrence Logic Detail

The service queries AML flags using a single JOIN to ensure both flag types fall within the window for the **same** `entity_uuid` (not just the same partner):

```php
$structuringFlag = AmlFlag::where('partner_uuid', $partnerUuid)
    ->where('entity_uuid', $entityUuid)
    ->where('flag_type', 'structuring')
    ->where('created_at', '>=', now()->subHours($this->windowHours))
    ->latest()
    ->first();

$velocityFlag = AmlFlag::where('partner_uuid', $partnerUuid)
    ->where('entity_uuid', $entityUuid)
    ->where('flag_type', 'velocity_breach')
    ->where('created_at', '>=', now()->subHours($this->windowHours))
    ->latest()
    ->first();

if ($structuringFlag && $velocityFlag && !$this->hasDuplicateSar($partnerUuid, $entityUuid)) {
    return $this->sarService->draft(...);
}
```

## SAR Lifecycle After Auto-Draft

```
auto_drafted → draft (partner edits narrative) → under_review → filed
                                                              ↘ closed (partner decision)
```

Partners must:
1. Review the auto-drafted SAR in the compliance dashboard
2. Edit the narrative if needed (add context, correct pre-computed amounts)
3. Move to `under_review` via `POST /compliance/sars/{id}/review`
4. File with regulator via `POST /compliance/sars/{id}/file`

The evidence package exported at filing uses HMAC-hashed entity identifiers. Partners must substitute hashes with real KYC identities before FIU submission.

## Audit Trail

Every auto-STR trigger and SAR state transition is logged to `audit_logs` with:
- `action`: `sar.auto_drafted`, `sar.reviewed`, `sar.filed`
- `actor_type`: `system` (auto-draft), `user` (manual transitions)
- `metadata`: trigger flags, window parameters, actor user UUID
