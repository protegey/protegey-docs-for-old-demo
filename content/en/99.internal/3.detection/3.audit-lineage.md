# Audit Lineage

::callout{icon="i-lucide-lock" color="red"}
**RESTRICTED**: Internal Protegey team only.
::

**Introduced**: v1.3.0 (2026-02-11)
**Service**: `App\Domain\SignalDetection\Services\LineageTrackingService`
**Tables**: `detector_executions`, `alert_lineage`

---

## Purpose

The Audit Lineage system records a complete traceability chain for every alert:

```
Signal received
  └─> Detectors run (detector_executions)
        └─> Severity scored (scoring_breakdown in signal metadata)
              └─> Taxonomy assigned (taxonomy_assignments)
                    └─> Alert generated
                          └─> Lineage recorded (alert_lineage)
                                └─> Exposed via GET /alerts/{uuid}/lineage
```

This satisfies regulatory explainability requirements and enables partners to understand _why_ an alert was generated via the "Explain This Alert" feature.

---

## Schema

### `detector_executions`

One row per detector per signal. Records the outcome of each detector run.

| Column        | Type    | Description                                            |
| ------------- | ------- | ------------------------------------------------------ |
| `id`          | ULID    | Primary key                                            |
| `signal_id`   | ULID    | FK → `signals.id`                                      |
| `detector_id` | string  | Detector identifier (e.g. `LARGE_OUTLIER_TRANSACTION`) |
| `fired`       | boolean | Whether the detector triggered                         |
| `confidence`  | float   | Detector confidence (0.0–1.0)                          |
| `risk_score`  | float   | Risk contribution from this detector                   |
| `evidence`    | JSON    | Key-value evidence from the detector                   |
| `reasoning`   | text    | Optional human-readable explanation                    |
| `version`     | string  | Detector version at time of execution                  |

### `alert_lineage`

One row per alert. Stores the full chain.

| Column              | Type       | Description                                |
| ------------------- | ---------- | ------------------------------------------ |
| `id`                | ULID       | Primary key                                |
| `alert_uuid`        | string     | FK → `fraud_alerts.uuid`                   |
| `signal_id`         | ULID       | FK → `signals.id`                          |
| `taxonomy_primary`  | string     | Primary taxonomy category ID               |
| `taxonomy_all`      | JSON array | All assigned taxonomy categories           |
| `detector_results`  | JSON       | Snapshot of all detector execution results |
| `features`          | JSON       | Signal feature values at detection time    |
| `base_severity`     | float      | Pre-boost base severity                    |
| `final_severity`    | float      | Post-calculation final severity score      |
| `source_confidence` | float      | Signal source confidence                   |
| `anomaly_factor`    | float      | Anomaly detection multiplier               |
| `explanation`       | text       | Auto-generated plain-English explanation   |

## Service API

### `LineageTrackingService::recordDetectorExecutions(Signal $signal, array $results): void`

Upserts `detector_executions` rows for all detectors run against the signal. Called from `CalculateSignalSeverity` listener.

### `LineageTrackingService::recordAlertLineage(string $alertUuid, Signal $signal, array $detectorResults, float $baseSeverity, float $finalSeverity, float $sourceConfidence, float $anomalyFactor): AlertLineage`

Builds and saves an `alert_lineage` record. Automatically:

1. Reads `taxonomy_assignments` from the signal
2. Builds the detector snapshot from `$detectorResults`
3. Extracts features from signal metadata
4. Generates a plain-English `explanation` string

Called non-fatally from `GenerateAlertForSignal` listener (wrapped in try/catch to avoid blocking alert creation).

### `LineageTrackingService::getAlertLineage(string $alertUuid): ?AlertLineage`

Returns the `AlertLineage` model for an alert UUID, or `null` if not found.

## Pipeline Integration

```
CalculateSignalSeverity (listener)
  1. Run detectors via DetectorRegistry::detectMany()
  2. lineageService->recordDetectorExecutions(signal, results)
  3. scoringService->calculateScoringBreakdown(signal, firedIds)
  4. signal->update(['metadata' => [..., 'scoring_breakdown' => $breakdown]])
  5. taxonomyRegistry->assignTaxonomy(signal, detectorResults)

GenerateAlertForSignal (listener)
  1. alertService->generateAlertIfNeeded(signal) → $alert
  2. lineageService->recordAlertLineage($alert->uuid, $signal, ...)
     (non-fatal — wrapped in try/catch)
```

## Partner-Facing API

**Endpoint**: `GET /api/v1/partner/alerts/{uuid}/lineage`
**Feature gate**: `alert_management`

- Returns HTTP 200 in both cases (lineage exists or not)
- `available: true` with full lineage data when record exists
- `available: false` with descriptive message when no record (pre-existing alerts)

See [Alert Management API](../../9.partners/4.api-reference/6.alerts) for full response schema.

## Explanation Generation

The plain-English explanation is generated by `buildExplanation()` (private method in `LineageTrackingService`). Format:

```
Alert generated because {detector1} fired (confidence: {n}) [and {detector2} fired (confidence: {n})].
Taxonomy: {primary_category} (primary).
Final severity: {final} (base: {base}, confidence: {conf}, anomaly: {anomaly}x).
```

---

## Non-Fatal Design

Lineage recording is intentionally non-fatal. If `recordAlertLineage()` throws, a warning is logged but the alert is still created. This prevents lineage tracking failures from blocking fraud detection operations.

Monitoring: Check `Log::warning('Failed to record alert lineage', ...)` in application logs if lineage data appears missing for recent alerts.
