## v1.18.1 — Fix: API Key IP Allowlist Now Works for Sandbox Keys
*Released 2026-05-26*

- **Fix**: Adding IPs to a sandbox API key's allowlist now persists correctly and is respected during signal ingestion. Previously, the portal saved the IP list to the sandbox database schema while signal validation always read from the production schema, so the allowlist had no effect and requests were rejected with HTTP 403.
- **Fix**: The portal's "Save" button on the IP allowlist form now correctly reports failures to the user if the server returns an error, instead of optimistically updating local state.
- **Note**: If you were affected — clear the allowlist for your sandbox key, re-add your IPs, and save again. The record in the production schema will now be updated correctly.

## v1.18.0 — Partner-Configurable Alert Rules
*Released 2026-05-22*

- **New**: Partners can now configure exactly how alerts are generated, per taxonomy fraud category. The new **Alert Rules** page (`/alerts/rules`) shows all 13 fraud categories with individual enable/disable toggles and minimum severity score sliders (range 10%–99%, step 5%).
- **New**: Alert rules respect a three-layer resolution — partner override → system default → global threshold fallback — ensuring alerts always fire when no rule is configured (fail-open design).
- **New**: System rules (`identity.sim_swap`, `identity.account_takeover`, `payment.agent_collusion`) are always active regardless of partner configuration. Attempting to disable them returns a 403.
- **Explainability**: `alert_type` on `FraudAlert` records now contains the taxonomy category slug (e.g. `payment.mobile_money`) instead of the opaque `severity_threshold` label, making it immediately clear which fraud pattern triggered each alert.
- **API**: Three new endpoints — `GET /api/v1/alert-rules` (list all rules with effective partner config), `PUT /api/v1/alert-rules/{categoryId}` (set override), `DELETE /api/v1/alert-rules/{categoryId}` (reset to default).
- **UX**: Per-row save/reset workflow — slider and toggle changes are held as local drafts (shown with an orange dot indicator); a Save button appears per row only when changes are pending. Reset button appears only when a partner override exists.
- **Cache**: Partner config changes take effect immediately — cache is busted on every save and reset, not after the 15-minute TTL.

## v1.16.0 — Cross-Signal & Cross-Actor Detection (Phase S)
*Released 2026-05-15*

Four new detectors bring the total to **9 active detectors**. The new detectors identify fraud patterns that span multiple signals and multiple actors — gaps that single-signal detectors cannot cover.

- **New**: `AttackChainDetector` — recognises multi-step attack sequences for the same actor within a time window. Two chains shipped:
  - `ATO_SIM_SWAP`: `ACCOUNT_TAKEOVER` → `PAYMENT_FRAUD` within 60 minutes (confidence 0.92, max risk +40)
  - `SOCIAL_TO_PAYMENT`: `SOCIAL_ENGINEERING` → `PAYMENT_FRAUD` within 120 minutes (confidence 0.80, max risk +32)
  Adding new attack chains requires zero changes to existing code — chains are registered via the `AttackChainRegistry`.
- **New**: `BeneficiaryConcentrationDetector` — fires when many different actors are all sending funds to the same beneficiary (investment scam funnel, mule account). Tiered scoring: ≥20 unique senders → max risk +35; ≥10 → +25; ≥5 → +15.
- **New**: `AgentConcentrationDetector` — same pattern at agent cashout nodes. Fires when many actors cash out through the same agent in the fraud graph.
- **New**: `SessionAnomalyDetector` — flags sessions with impossible behavioural characteristics (e.g. bot-speed interaction, impossible concurrent sessions).
- **Graph**: AGENT nodes are now materialized in the fraud graph from `related_entities` in UFES v2 mobile/USSD signals. Agent concentration detection requires this field to be populated.
- **Taxonomy coverage expanded**: `identity.account_takeover`, `social.engineering`, `social.investment_scam`, `payment.agent_collusion` now have detector coverage.
- **Admin**: Taxonomy management UI in admin panel — edit taxonomy entries without code deploys.
- **No breaking changes**: Existing detector IDs and API response shapes are unchanged. New detectors appear in `detectors_triggered` arrays when fired.

## v1.15.5 — Platform Hardening & Scoring Accuracy
*Released 2026-05-20*

This release contains no new features but corrects several scoring behaviours that could cause incorrect risk scores or misattributed AML flags.

**Scoring accuracy fixes:**
- **Velocity anchor** (`VelocityCheckService`): velocity windows are now anchored to `event_timestamp` (the time the event occurred) instead of `created_at` (the time the signal was received). This matters for batched or delayed ingestion — a transaction that happened at 14:00 but was submitted at 16:30 is now scored against the correct 1-hour window.
- **Impossible Travel** (`ImpossibleTravelDetector`): `abs()` applied to the travel time difference, so out-of-order signals (e.g. two events submitted in reverse chronological order) no longer produce a false-positive infinite speed.
- **SIM Swap Proximity** (`SimSwapProximityDetector`): signed time difference now correctly skips transactions that occurred *before* the SIM change, not after.
- **Weighted Risk Fusion** (`WeightedRiskFusionEngine`): adaptive mode now uses effective weights so all four dimensions sum to the fused score. Previously, adaptive re-weighting could produce a fused score larger than the sum of its inputs.
- **Feature Engineering**: country codes are normalized to 2-char uppercase before geo feature computation; the current signal is excluded from its own percentile denominator.

**AML compliance fixes:**
- **Rule `is_enabled` bypass** (`ConfigurableRuleEngine`): a null `is_enabled` value was incorrectly treated as enabled. Rules explicitly disabled by a partner are now correctly skipped.
- **SAR deduplication** (`SuspiciousActivityReportService`): dedup check now covers `under_review` and `filed` statuses, not just `draft`. This prevents duplicate SARs from being created for sustained patterns.
- **Auto-STR window** (`AutoStrCorrelationService`): `window_hours` time filter is now enforced when searching for correlating AML flags.
- **PEP hash_type filter** (`PEPDetectionService`): OSINT hash index lookups now filter by `hash_type` to prevent cross-field hash collisions.
- **Cache isolation** (`ConfigurableRuleEngine`): rule parameter cache is now cleared at the start of each queue job execution, preventing stale partner parameters from bleeding across jobs in a shared worker.

**New OSINT source:**
- **CBN/NIGSAC** (`CbnNigsacParser`): Central Bank of Nigeria / Nigeria Sanctions Committee list is now ingested via the daily `osint:ingest` pipeline. No API changes required — entities are now screened against this list automatically.

## v1.14.5 — AML Identity Detection & Extended Sanctions Coverage
*Released 2026-04-06*

- **New AML Rule**: `duplicate_identity` — fires when a device fingerprint linked to this signal is also linked to a high-risk actor in the graph (`USES_DEVICE` edge). Flags synthetic identity patterns where a fraudster reuses a device across fabricated identities. Risk contribution: 0.80.
- **New AML Rule**: `device_farm_detection` — fires when N+ distinct new entities are observed on the same device within a rolling window (default threshold: 10, tunable per partner). Catches agent-banking device farms and bot-operated bulk account creation. Risk contribution: 0.90, severity critical.
- **Updated**: `structuring_detection` gains two new optional parameters: `min_account_age_hours` and `young_account_multiplier`. When set, structuring risk is amplified for young accounts — accounts under the age threshold receive the multiplier applied to their base structuring score. Both default to null (disabled).
- **New**: `duplicate_identity_suspected` and `device_farm_suspected` flag types now appear in the AML flags filter and badge display in the Partner Portal Compliance section.
- **New OSINT source**: OFAC SDN (US Office of Foreign Assets Control Specially Designated Nationals list) is now ingested and screened. This is the primary US unilateral sanctions list. No API changes required — entities screened automatically via the daily `osint:ingest` pipeline.
- **Node.js SDK**: `@protegey/sdk-node` is available. Wraps the partner API with typed request/response interfaces, automatic retries, and HMAC signature verification for webhooks. See the SDK guide in `packages/sdk-node/README.md`.

## v1.13.5 — Stateless Signal Evaluation & PEP Accuracy

This eliminates the previous fuzzy name matching approach which had high false-positive rates. PEP matches now include the same confidence scoring, source attribution, and freshness decay as sanctions matches. **Partners may observe fewer PEP false positives** after this change.
