Welcome to the Protegey technical onboarding. This guide is designed for developers who are responsible for integrating their internal systems with the Protegey Global Fraud Intelligence Network.

## 1. Technical Prerequisites

Before you begin your integration, ensure your environment meets the following requirements:

- **HTTPS Only**: All API requests must be made over TLS 1.2+.
- **JSON Support**: Payloads must be valid JSON.
- **Clock Sync**: Ensure your server clocks are synchronized (NTP). Signals with a timestamp more than 24 hours in the past or 5 minutes in the future may be rejected.

## 2. Environment Selection

Protegey provides two distinct environments for integration:

| Environment    | Purpose                   | Base URL                           |
| -------------- | ------------------------- | ---------------------------------- |
| **Sandbox**    | Integration & Testing     | `https://sandbox-api.protegey.com` |
| **Production** | Live Intelligence Sharing | `https://api.protegey.com`         |

For the access model and approval steps, see [Sandbox vs Production Access](/en/platform/architecture#sandbox-vs-production-access).

::callout{icon="i-lucide-shield-check" color="primary"}
**Sandbox Isolation**: All data submitted to the Sandbox is logically isolated from the production network. Use the Sandbox to verify your ingestion pipeline without affecting network risk scores.
::

## 3. API Key Management

You will receive your API keys through the [Partner Portal](https://app.protegey.com).

1. **Authentication**: All requests must include the `X-Centry-Key` header.
2. **Key Rotation**: We recommend rotating your Secret Keys every 90 days.
3. **Security**: Never share your Secret Keys or include them in client-side code (JavaScript/Mobile).

## 4. Normalization Best Practices

High data quality is critical for accurate cross-network entity linking. Protegey provides built-in normalization for common entity types.

### Identifiers

Always submit identifiers as **plaintext**. Protegey normalizes and hashes them server-side using HMAC-SHA256 with the shared network key before any storage or graph linking occurs. Pre-hashing on the client side will break cross-institution entity matching.

### Phone Numbers & Country Hints

For phone numbers, supply a country hint via `primary_actor.identifiers.region` (ISO 3166-1 alpha-2). This helps the normalization engine resolve ambiguous local patterns (e.g. `0244123456` → `+233244123456` when `region: "GH"` is provided).

```json
{
  "primary_actor": {
    "phone": "0244123456",
    "identifiers": {
      "region": "GH"
    }
  }
}
```

## 5. First Signal Ingestion

A successful integration typically follows this workflow:

1. **Construct Payload**: Format your signal according to the [Signals API](/en/partners/api-reference/signals) documentation.
2. **Submit to Sandbox**: Post your first signal to the Sandbox endpoint.
3. **Verify Response**: Ensure you receive a `201 Created` response with a unique `signal_id`.
4. **Check Partner Portal**: Log in to the portal and verify the signal appears in your activity log.

## 6. Going Live

To transition from Sandbox to Production:

1. **Request Production Keys**: via the Partner Portal.
2. **Update Base URl**: Point your production environment to `https://api.protegey.com`.
3. **Shadow Mode**: We recommend a "Shadow" period of 7 days where you ingest signals but do not yet act on the returned scores.
4. **Monitor Performance**: Review your integration health via the Dashboard.
