Case Management in Protegey provides a structured workflow for investigating fraud signals, collaborating with your team, and maintaining a complete audit trail of all investigation activities.

## Overview

### What is a Case?

A **fraud case** is a structured investigation record that:

- Links to one or more fraud signals
- Contains investigation notes and findings
- Tracks evidence (screenshots, documents, logs)
- Maintains status and priority
- Records complete timeline of all activities
- Supports team collaboration and assignment

### When to Create a Case

Create cases for signals that require:

- **Manual Investigation**: High-risk signals (score ≥ 80) needing analyst review
- **Multi-Signal Pattern**: Multiple related signals suggesting fraud ring
- **Customer Dispute**: User claims legitimate activity flagged as fraud
- **Documentation**: Complex fraud requiring detailed evidence collection
- **Escalation**: Signals requiring senior analyst or law enforcement involvement

---

## Case Lifecycle

### Status Flow

```
open → in_progress → resolved → closed
         ↓
      on_hold
```

| Status          | Description                  | Actions Available                      |
| --------------- | ---------------------------- | -------------------------------------- |
| **open**        | New case awaiting assignment | Assign, add notes, start investigation |
| **in_progress** | Actively being investigated  | Add evidence, update findings, resolve |
| **on_hold**     | Paused (awaiting info)       | Resume, add notes, close               |
| **resolved**    | Investigation complete       | Add resolution notes, close            |
| **closed**      | Case archived                | View only (read-only)                  |

### Priority Levels

| Priority     | Description               | Response SLA | Use When                                      |
| ------------ | ------------------------- | ------------ | --------------------------------------------- |
| **low**      | Non-urgent investigation  | 72 hours     | Low-risk patterns, proactive monitoring       |
| **medium**   | Standard investigation    | 24 hours     | Medium-risk signals, repeat actors            |
| **high**     | Urgent review needed      | 4 hours      | High-risk signals, customer impact            |
| **critical** | Immediate action required | 1 hour       | Confirmed fraud, active attack, large amounts |

## Creating Cases

### Method 1: From Signal (Recommended)

Create a case directly from a high-risk signal:

**Partner Portal**:

1. Navigate to Transaction Monitoring
2. Click on a high-risk signal
3. Click "Create Case" button
4. Case pre-populated with signal data

**API**:

```typescript
const fraudCase = await client.cases.createFromSignal("sig_abc123", {
  description: "High-value cross-border transfer requires investigation",
  priority: "high",
  category: "ACCOUNT_TAKEOVER",
});

console.log(`Case created: ${fraudCase.uuid}`);
```

**When Signal Data is Copied**:

- Transaction ID
- Risk score and level
- Actor hash
- Transaction amount and currency
- Metadata (device, IP, country)
- Risk factors that triggered detection

---

### Method 2: Manual Creation

Create a case without a linked signal:

**Partner Portal**:

1. Navigate to Cases
2. Click "New Case" button
3. Fill in case details
4. Assign to analyst (optional)

**API**:

```typescript
const fraudCase = await client.cases.create({
  title: "Investigation: Account Takeover - 2026-02-03",
  description:
    "Customer reported unauthorized transactions on account ending in 4532. Investigating access pattern and transaction history.",
  priority: "high",
  category: "ACCOUNT_TAKEOVER",
  assigned_user_id: 42, // Optional
});
```

## Investigation Workflow

### Step 1: Case Assignment

**Assign to Analyst**:

```typescript
await client.cases.update(caseUuid, {
  assigned_user_id: 42,
});
```

**Auto-Assignment Rules** (configure in portal):

- **Round-robin**: Distribute evenly across team
- **Skill-based**: Route by fraud category expertise
- **Workload-based**: Assign to analyst with lowest open cases
- **Priority-based**: Critical cases go to senior analysts

---

### Step 2: Investigation & Note-Taking

Add investigation notes as you work:

**API**:

```typescript
await client.cases.addNote(caseUuid, {
  content: `## Initial Findings

- Reviewed account activity for last 30 days
- Login from new device (iPhone 14) in Lagos, Nigeria
- Previous logins always from Accra, Ghana
- 3 high-value transfers within 2 hours of login
- Customer phone number unreachable (possible SIM swap)

## Next Steps
- Contact customer via email for verification
- Check if mobile carrier reported SIM change
- Review linked accounts for similar patterns`,
  visibility: "internal", // or 'external' for customer-facing notes
});
```

**Note Types**:

- **Investigation Notes**: Findings, analysis, next steps
- **Customer Communication**: Records of customer contact
- **External Reference**: Links to external systems (CRM, ticketing)
- **Evidence Summary**: Description of attached evidence

**Best Practices**:

- Use Markdown for formatting
- Include timestamps for key events
- Reference evidence by filename
- Document decision rationale
- Update notes after each investigation session

---

### Step 3: Evidence Collection

Attach supporting evidence to cases:

**Supported Evidence Types**:

- Screenshots (PNG, JPG)
- Transaction logs (CSV, JSON)
- Communication records (TXT, PDF)
- Identity documents (PDF, JPG - redact sensitive data!)
- System logs (TXT, LOG)
- Video recordings (MP4 - fraud simulation proof)

**API**:

```typescript
// Upload evidence
const evidence = await client.cases.attachEvidence(caseUuid, {
  file: await fs.readFile("screenshot_fraudulent_transaction.png"),
  filename: "screenshot_fraudulent_transaction.png",
  description: "Screenshot showing unauthorized transfer of GHS 15,000",
  type: "screenshot",
});

// List all evidence
const allEvidence = await client.cases.listEvidence(caseUuid);
```

**Evidence Best Practices**:

- **Redact PII**: Remove sensitive customer data before uploading
- **Clear Naming**: Use descriptive filenames (e.g., `2026-02-03_login_logs.csv`)
- **Context**: Add description explaining evidence relevance
- **Chain of Custody**: Document who collected evidence and when
- **Size Limits**: Max 10MB per file, 50MB total per case

---

### Step 4: Status Updates

Update case status as investigation progresses:

**Common Status Transitions**:

```typescript
// Start investigation
await client.cases.update(caseUuid, {
  status: "in_progress",
});

// Pause for customer response
await client.cases.update(caseUuid, {
  status: "on_hold",
  notes: "Awaiting customer response to verification email",
});

// Resume investigation
await client.cases.update(caseUuid, {
  status: "in_progress",
  notes: "Customer confirmed unauthorized activity",
});

// Resolve case
await client.cases.update(caseUuid, {
  status: "resolved",
  resolution:
    "Confirmed fraud. Account secured, funds recovered, law enforcement notified.",
});

// Archive case
await client.cases.update(caseUuid, {
  status: "closed",
});
```

---

### Step 5: Resolution & Closure

**Resolution Types**:

| Resolution                | Description                | Actions Taken                                         |
| ------------------------- | -------------------------- | ----------------------------------------------------- |
| **Confirmed Fraud**       | Fraud verified             | Block actor, reverse transactions, notify authorities |
| **False Positive**        | Legitimate activity        | Whitelist actor, adjust risk thresholds               |
| **Insufficient Evidence** | Cannot determine           | No action, continue monitoring                        |
| **Customer Dispute**      | Customer claims legitimate | Investigate customer history, verify identity         |
| **Technical Error**       | System error caused flag   | Fix bug, reprocess signal                             |

**Resolution Documentation**:

```typescript
await client.cases.update(caseUuid, {
  status: "resolved",
  resolution: `## Investigation Summary
Confirmed account takeover via SIM swap fraud.

## Evidence
- Customer confirmed unauthorized SIM replacement on 2026-02-02
- Device fingerprint changed from known iPhone to new Android device
- IP geolocation changed from Accra (normal) to Lagos (unusual)
- Transaction velocity (5 transfers in 2 hours) highly anomalous

## Actions Taken
- Account access disabled pending customer verification
- Transactions reversed (GHS 45,000 total)
- Customer contacted via email - account reset link sent
- Mobile carrier notified of fraudulent SIM swap
- Actor phone number (0244xxxxxx) added to blocklist
- Law enforcement notified (case #NG-2026-0203-001)

## Prevention
- Enabled 2FA requirement for account changes
- Added SIM swap detection rule
- Updated velocity thresholds for Nigeria-origin transactions
- Customer education sent regarding SIM security

## Resolution
Confirmed fraud. All funds recovered. Account secured.`,
  priority: "low", // Downgrade priority after resolution
});
```

## Best Practices

### 1. Create Cases Promptly

**Don't delay investigation**:

```typescript
// ✅ GOOD: Create case immediately for high-risk signals
if (signal.risk_score >= 80) {
  await client.cases.createFromSignal(signal.id, {
    priority: "high",
    category: "ACCOUNT_TAKEOVER",
  });
}

// ❌ BAD: Waiting days before creating case
// Evidence may be lost, actors may continue fraud
```

---

### 2. Document Thoroughly

**Include key details**:

- What triggered the investigation
- Evidence reviewed
- Analysis and findings
- Decision rationale
- Actions taken
- Lessons learned

**Poor Documentation**:

```
Status: Resolved
Resolution: Fraud confirmed.
```

**Good Documentation**:

```markdown
## Investigation Summary

Confirmed SIM swap account takeover targeting high-value account.

## Timeline

- 2026-02-02 14:00: SIM swap completed (mobile carrier confirmed)
- 2026-02-02 14:15: Login from new device (Lagos, Nigeria)
- 2026-02-02 14:30-16:30: 5 unauthorized transfers (GHS 45,000 total)
- 2026-02-03 09:00: Customer reported unauthorized activity

## Evidence

- Mobile carrier confirmation of SIM replacement
- IP logs showing geographic change (Accra → Lagos)
- Device fingerprint change (iPhone 12 → Android Unknown)
- Transaction velocity 10x normal pattern
- Customer verification via email confirmed unauthorized access

## Actions Taken

- Account disabled for security review
- All transactions reversed (GHS 45,000)
- Actor phone number added to global blocklist
- Law enforcement notified (Case #NG-2026-0203-001)
- Customer account secured with enhanced 2FA

## Prevention

- Implemented SIM swap detection rule
- Enhanced velocity checks for Nigeria-origin transactions
- Customer education on SIM security best practices

## Resolution

Confirmed fraud. Funds recovered. Account secured. Actor blocked.
```

---

### 3. Use Priority Correctly

**Priority Guidelines**:

- **Critical**: Active fraud, customer locked out, high amounts (>$10k), reputational risk
- **High**: Recent fraud (<24h), medium amounts ($1k-$10k), repeat actor
- **Medium**: Older signals, low amounts (<$1k), first offense
- **Low**: Proactive monitoring, educational cases, trend analysis

---

### 4. Leverage Categories

**Accurate categorization enables**:

- Specialized analyst routing
- Category-specific analytics
- Fraud trend identification
- Regulatory reporting

---

### 5. Update Status Regularly

**Keep status current**:

- Update within 1 hour of starting investigation
- Change to `on_hold` if waiting for info (don't leave as `in_progress`)
- Resolve promptly when investigation complete
- Close after 30 days of no activity (after resolution)

---

### 6. Collaborate Effectively

**Use assignments for**:

- Clear ownership
- Workload visibility
- Accountability
- Escalation tracking

**Use notes for**:

- Handoff information
- Shift updates
- Asking questions to team
- Documenting discussions

---

### 7. Maintain Evidence Chain

**Evidence handling**:

- Collect evidence early (logs may expire)
- Document source and collection method
- Redact sensitive PII before upload
- Include context for each piece of evidence
- Maintain chronological order

## Common Scenarios

### Scenario 1: High-Risk Signal Triage

```typescript
async function triageHighRiskSignal(signal) {
  // 1. Create case from signal
  const fraudCase = await client.cases.createFromSignal(signal.id, {
    priority: signal.risk_score >= 90 ? "critical" : "high",
    category: signal.event_type,
  });

  // 2. Add initial triage note
  await client.cases.addNote(fraudCase.uuid, {
    content: `## Triage Assessment
Risk Score: ${signal.risk_score}/100
Risk Level: ${signal.risk_level}

## Key Risk Factors:
${signal.risk_factors.map((f) => `- ${f.factor}: ${f.description}`).join("\n")}

## Next Steps:
- Review actor history
- Check similar transactions
- Contact customer if needed`,
  });

  // 3. Assign based on expertise
  const analyst = await findAnalystForCategory(signal.event_type);
  await client.cases.update(fraudCase.uuid, {
    assigned_user_id: analyst.id,
  });

  return fraudCase;
}
```

---

### Scenario 2: Multi-Signal Fraud Ring

```typescript
async function investigateFraudRing(signals) {
  // 1. Create master case
  const masterCase = await client.cases.create({
    title: `Fraud Ring Investigation - ${signals.length} Related Signals`,
    description: `Investigating coordinated fraud pattern across ${signals.length} signals sharing device fingerprints and IP addresses.`,
    priority: "critical",
    category: "ACCOUNT_TAKEOVER",
  });

  // 2. Document pattern
  await client.cases.addNote(masterCase.uuid, {
    content: `## Pattern Identified
- ${signals.length} signals within 24 hours
- Shared device fingerprint: ${signals[0].metadata.device_fingerprint}
- Same IP range: 41.XX.XX.XX
- Total exposure: GHS ${signals.reduce((sum, s) => sum + s.transaction.amount, 0).toLocaleString()}

## Affected Accounts
${signals.map((s) => `- ${s.actor.hashed_id} - GHS ${s.transaction.amount}`).join("\n")}`,
  });

  // 3. Link all signals to case (via notes)
  for (const signal of signals) {
    await client.cases.addNote(masterCase.uuid, {
      content: `Related signal: ${signal.id} - Risk Score: ${signal.risk_score}`,
    });
  }

  return masterCase;
}
```

### Scenario 3: Customer Dispute

```typescript
async function handleCustomerDispute(signal, customerMessage) {
  // 1. Create case for investigation
  const disputeCase = await client.cases.createFromSignal(signal.id, {
    priority: "high",
    category: "CUSTOMER_DISPUTE",
    description: `Customer disputes fraud flag. Claims legitimate activity.`,
  });

  // 2. Document customer claim
  await client.cases.addNote(disputeCase.uuid, {
    content: `## Customer Claim
"${customerMessage}"

## Signal Details
- Risk Score: ${signal.risk_score}
- Risk Factors: ${signal.risk_factors.map((f) => f.factor).join(", ")}

## Investigation Plan
1. Review customer account history (last 6 months)
2. Verify device fingerprint matches known devices
3. Check IP geolocation against customer address
4. Review similar patterns in account
5. Contact customer for additional verification if needed`,
  });

  // 3. Assign to senior analyst
  await client.cases.update(disputeCase.uuid, {
    assigned_user_id: await getSeniorAnalyst(),
    priority: "high",
  });

  return disputeCase;
}
```

## Metrics & Reporting

### Key Case Metrics

**Track performance**:

- **Total Cases**: Overall case volume
- **Open Cases**: Current workload
- **Average Resolution Time**: Efficiency metric
- **Cases by Priority**: Distribution of urgency
- **Cases by Category**: Fraud type breakdown
- **Closure Rate**: % resolved vs created
- **Analyst Performance**: Cases per analyst, avg resolution time

**API** (via analytics endpoints):

```typescript
const metrics = await client.analytics.cases({
  start_date: "2026-02-01",
  end_date: "2026-02-28",
});

console.log(`Total Cases: ${metrics.total}`);
console.log(`Avg Resolution Time: ${metrics.avg_resolution_hours} hours`);
console.log(`Top Category: ${metrics.by_category[0].category}`);
```
