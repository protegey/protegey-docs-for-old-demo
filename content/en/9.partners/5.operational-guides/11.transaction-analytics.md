# Transaction Analytics

The transaction analytics suite gives compliance and operations teams quantitative visibility into signal volumes, risk distributions, decision throughput, and analyst performance. All analytics endpoints are partner-scoped and respect your sandbox/production context.

---

## Overview

The analytics suite has 14 endpoints grouped into four categories:

| Category | Endpoints | Use Case |
|----------|-----------|----------|
| **Volume & Trends** | Time-series, comparison | Track signal volume over time, week-over-week changes |
| **Distribution** | Risk distribution, decision time | Understand risk score spread, decision latency |
| **Behavioural Patterns** | Heatmap, risk factors | Identify timing patterns, top fraud categories |
| **Team Performance** | Reviewer performance, queue stats | Monitor analyst throughput and decision quality |

All endpoints accept `from` and `to` ISO 8601 date parameters. Default range is the last 30 days.

---

## Volume & Trends

### Time-Series Volume

```http
GET /api/v1/transaction-monitoring/analytics/time-series
```

Returns daily or hourly transaction counts and average risk scores over the requested period.

**Parameters**:

| Parameter | Type | Description |
|-----------|------|-------------|
| `from` | date | Start date (ISO 8601) |
| `to` | date | End date (ISO 8601) |
| `granularity` | string | `hour`, `day`, `week` — default `day` |
| `risk_level` | string | Filter by `low`, `medium`, `high`, `critical` |

**Response**:
```json
{
  "data": [
    {
      "date": "2026-03-01",
      "total_transactions": 1247,
      "flagged": 89,
      "avg_risk_score": 34.2,
      "risk_levels": {
        "low": 1045,
        "medium": 123,
        "high": 65,
        "critical": 14
      }
    }
  ],
  "summary": {
    "total_transactions": 38257,
    "total_flagged": 2741,
    "flag_rate": 7.16
  }
}
```

### Period Comparison

```http
GET /api/v1/transaction-monitoring/analytics/comparison
```

Compares two time periods (current vs prior) for volume, flag rate, and average risk score. Useful for detecting week-over-week anomalies in fraud activity.

**Parameters**: `current_from`, `current_to`, `prior_from`, `prior_to`

### Decision Time Distribution

```http
GET /api/v1/transaction-monitoring/analytics/decision-time
```

Shows the distribution of time-to-decision across all reviewed transactions. Useful for SLA monitoring and identifying bottlenecks in the review queue.

**Response includes**: `p50_seconds`, `p90_seconds`, `p99_seconds`, `mean_seconds`, `reviewed_count`

## Behavioural Patterns

### Activity Heatmap

```http
GET /api/v1/transaction-monitoring/analytics/heatmap
```

Returns a 7×24 matrix (day of week × hour of day) of transaction volume and average risk scores. Helps identify high-risk time windows (e.g., overnight bursts, weekend spikes).

**Response**:
```json
{
  "data": {
    "matrix": [
      {
        "day": "monday",
        "hours": [
          { "hour": 0, "count": 12, "avg_risk": 71.2 },
          { "hour": 1, "count": 8, "avg_risk": 68.5 }
        ]
      }
    ],
    "peak_hour": { "day": "friday", "hour": 23, "avg_risk": 82.1 }
  }
}
```

### Risk Factor Breakdown

```http
GET /api/v1/transaction-monitoring/analytics/risk-factors
```

Aggregates the most frequently triggered detectors, AML flags, and taxonomy categories across the selected period. Use this to identify the dominant fraud patterns in your transaction population.

**Response**:
```json
{
  "data": {
    "top_detectors": [
      { "detector": "RAPID_TRANSACTION_VELOCITY", "trigger_count": 892, "pct": 32.5 },
      { "detector": "LARGE_OUTLIER_TRANSACTION", "trigger_count": 741, "pct": 27.0 }
    ],
    "top_taxonomy": [
      { "category": "payment.structuring", "count": 654, "pct": 23.8 }
    ],
    "top_aml_flags": [
      { "flag_type": "velocity_breach", "count": 1102, "pct": 40.2 }

  }
}
```

```http
GET /api/v1/transaction-monitoring/analytics/reviewer-performance
```

Per-analyst metrics: decisions made, average review time, false positive rate, and accuracy (where ground-truth outcomes are available).

      "avg_review_seconds": 147,

```http
GET /api/v1/transaction-monitoring/analytics/performance
```

Overall queue metrics: pending review count, average queue age, SLA breach rate, and throughput.

## Using Analytics for Threshold Calibration

The distribution endpoint is particularly valuable when calibrating your risk score thresholds:

1. Run `GET /analytics/distribution` over 30 days of production data
2. Identify the `p95` score — this is your natural `high` risk boundary
3. Set your `BLOCK` policy threshold at `p99` to minimise false positives
4. Review `risk-factors` to identify detectors generating noise vs signal

Threshold changes take effect immediately via the decision policy engine and do not require code deploys.

## Bulk Transaction Decisions

::callout{icon="i-lucide-lock" color="orange"}
Available on **Enterprise** plans with the `bulk_decisioning` feature enabled.
::

For high-volume operations — alert storms, end-of-day review queues, coordinated fraud responses — the bulk-decide endpoint lets you approve or block multiple transactions in a single API call:

```http
POST /api/v1/transaction-monitoring/bulk-decide
```

**Request:**

```json
{
  "transaction_ids": ["TXN-001", "TXN-002", "TXN-003"],
  "decision": "block",
  "reason": "Coordinated velocity attack — actor blocked across all pending transactions",
  "decision_type": "automated"
}
```

| Field | Type | Values |
|-------|------|--------|
| `transaction_ids` | string[] | Up to 100 per call |
| `decision` | string | `approve` · `block` · `review` |
| `reason` | string | Audit note — required for `block` decisions |
| `decision_type` | string | `manual` · `automated` · `hybrid` |

`decision_type` affects model training weight. Mark automated decisions (`automated`) separately from analyst-reviewed ones so the training pipeline can weight human-verified labels higher.

**High-volume patterns:**

- **Alert storm response** — when `GET /analytics/time-series` shows a spike, pull the affected `pending` transactions and bulk-block in batches of 100
- **Nightly queue flush** — process the end-of-day low-risk pending queue by bulk-approving transactions below your `p50` risk threshold
- **Post-incident cleanup** — after a coordinated fraud case is closed, bulk-block all transactions linked to the same actor hash

## Export

All analytics data can be exported to CSV via:

```http
POST /api/v1/transaction-monitoring/export
```

This returns a signed URL to download the full transaction dataset for the selected period, suitable for offline analysis in Excel or Python.
