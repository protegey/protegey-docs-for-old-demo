## Phase 1: Sandbox Setup

### Environment Configuration

- [ ] **Sandbox Access**: Sandbox API keys generated in Partner Portal
- [ ] **Environment Switching**: Can toggle between sandbox and production environments
- [ ] **Cookie/Header Configuration**: Environment switching works via query params, cookies, or headers

### Demo Data Generation

- [ ] **Signal Generation**: Can generate demo signals via API (`/api/v1/partner/sandbox/generate-demo-signals`)
- [ ] **Template Testing**: Tested multiple signal templates (account takeover, stolen financials, etc.)
- [ ] **Risk Distribution**: Verified risk profiling (10% critical, 20% high, 30% medium, 40% low)

### Data Isolation

- [ ] **Schema Separation**: Confirmed sandbox signals don't appear in production dashboard
- [ ] **Reset Functionality**: Successfully reset sandbox data via API
- [ ] **Production Safety**: No test data polluting production environment

## Phase 2: Core Integration

## Security

- [ ] **API Key Storage**: Keys are stored in environment variables or a secrets manager, not in code.
- [ ] **IP Allowlist**: Production IP addresses are configured in the Partner Portal.
- [ ] **TLS**: All API requests use HTTPS.

## Reliability

- [ ] **Timeouts**: API client has a configured timeout (recommended: 2000ms).
- [ ] **Fail-Open/Closed**: Logic is in place to handle API unavailability (e.g., default to "Allow" or "Manual Review").
- [ ] **Retries**: Exponential backoff is implemented for `429` and `5xx` errors.

## Data Quality

- [ ] **Entity Formatting**: Emails are lowercased and trimmed. Phone numbers are E.164 formatted.
- [ ] **Plaintext Identifiers**: Submit phone, email, account, and national_id as plaintext — Protegey normalizes and hashes them server-side.
- [ ] **Async specific**: Signal submissions are performed asynchronously (background job) to avoid UI blocking.

## Operational

- [ ] **Monitoring**: You are logging Protegey API response codes and latency.
- [ ] **Alerting**: You have alerts set up for a spike in 4xx/5xx errors.
- [ ] **Contacts**: Incident, Billing, and Technical contacts are up to date in the Portal.

## Compliance

- [ ] **Privacy Policy**: Your user-facing privacy policy discloses fraud prevention data sharing.
- [ ] **Data Retention**: You are not storing Protegey risk scores longer than necessary (max 90 days recommended).
- [ ] **User Consent**: Appropriate user consent obtained for fraud detection processing
- [ ] **Data Processing Agreement**: DPA signed with Protegey (required for production)

## Phase 3: Signal Ingestion

### API Integration

- [ ] **UFES v2 Format**: All signals include `schema_version: "2.0"` and `primary_actor.entity_id`
- [ ] **Plaintext Submission**: Submit identifiers (`primary_actor.phone`, `.email`, `.account`, `.national_id`) as plaintext — server-side HMAC-SHA256 hashing is automatic. Do NOT pre-hash.
- [ ] **Detector Fields**: Including `source.ip_address`, `primary_actor.device.fingerprint`, and `primary_actor.identifiers.sim_changed_at` where applicable
- [ ] **Idempotency**: `Idempotency-Key` header sent with every signal; same key reused on retries

### Response Handling

- [ ] **201 Created**: Synchronous risk verdict consumed (`risk_score`, `risk_level`, `detectors_triggered`)
- [ ] **422 Unprocessable**: Validation errors handled; bad payload logged for debugging
- [ ] **429 Rate Limit**: Exponential backoff implemented (with same `Idempotency-Key` on retry)
- [ ] **500 Server Error**: Fail gracefully; retry with same idempotency key

### Testing

- [ ] **SIM Swap**: Test signal with `primary_actor.identifiers.sim_changed_at` within 24h → `SIM_SWAP_PROXIMITY` fires
- [ ] **New Device**: Test signal with fresh `primary_actor.device.fingerprint` → `NEW_DEVICE_ACCESS` fires
- [ ] **High Amount**: Test signal with amount far above baseline → `LARGE_OUTLIER_TRANSACTION` fires
- [ ] **Idempotency**: Send same signal twice with same key → second returns `X-Idempotency-Replayed: true` with same signal_id

## Phase 8: Webhook Integration

### Webhook Configuration

- [ ] **Endpoint Setup**: Webhook URL registered in Partner Portal (HTTPS required)
- [ ] **Secret Stored**: Per-endpoint secret copied at creation and stored in secrets manager
- [ ] **Event Subscription**: Subscribed to relevant events (`signal.ingested`, `alert.created`, `case.created`)
- [ ] **Test Ping**: Sent a test ping and verified receipt + signature validation

### Signature Verification

- [ ] **Header Read**: Reading `X-Centry-Signature` (not `X-Protegey-Signature`)
- [ ] **HMAC-SHA256**: Verifying over `json_encode($payload)` / `JSON.stringify(body)` with per-endpoint secret
- [ ] **Constant-time Compare**: Using `hash_equals()` / `timingSafeEqual()` — not `===`

### Webhook Handler

- [ ] **Immediate 200**: Returns HTTP 200 within 3 seconds before processing
- [ ] **Async Processing**: Heavy processing dispatched to a background job
- [ ] **Idempotency**: Duplicate deliveries handled by tracking `X-Centry-Delivery-ID`

### Event Handling

- [ ] **`signal.ingested`**: Risk verdict extracted (`risk_score`, `risk_level`, `detectors_triggered`) and acted upon
- [ ] **`alert.created`**: High/critical alerts trigger internal escalation flow
- [ ] **`case.created`**: Case opened in internal ticketing/CRM system
- [ ] **`case.status_changed`**: Case status synced to internal system

## Phase 10: Integration Health

### Baseline Score

- [ ] **Dashboard reviewed**: Opened `/integration` in the Partner Portal and reviewed your A–F score
- [ ] **Critical signal types sent**: Signal Coverage card shows all critical types present (no red badges)
- [ ] **Score ≥ C (60)**: Minimum recommended score before going live — below C means detectors are missing data they need

### Enrichment Fields

- [ ] **IP address populated**: `actor_ip_address` in signals enables Impossible Travel detection
- [ ] **Device fingerprint populated**: `actor_device_fingerprint` enables New Device Access detection
- [ ] **SIM change date populated**: `sim_changed_at` enables SIM Swap Proximity detection
- [ ] **Recipient ID populated**: `metadata.transaction.recipient_id` enables Beneficiary Concentration detection
- [ ] **Agent entity populated**: `related_entities` with `entity_type: AGENT` enables Agent Concentration detection (mobile/USSD transactions)

### Outcome Feedback Loop

- [ ] **Outcome endpoint wired**: `PATCH /api/v1/signals/{id}/outcome` called once fraud verdict is confirmed (days/weeks post-ingestion)
- [ ] **`fraud_type` populated**: Submitting `account_takeover | scam | laundering | mule | unknown` for confirmed fraud — enables future supervised learning

## Phase 11: Production Readiness

### Performance

- [ ] **Rate Limits**: Stay within production rate limits (1000 req/min for transactions)
- [ ] **Connection Pooling**: HTTP client uses connection pooling for efficiency
- [ ] **Caching**: Risk scores cached appropriately (5-minute TTL)
- [ ] **Lazy Loading**: Heavy operations deferred to background jobs

### Monitoring

- [ ] **API Latency**: Tracking P50, P95, P99 latency for all API calls
- [ ] **Error Rates**: Monitoring 4xx and 5xx error rates
- [ ] **Success Rates**: Tracking signal ingestion success rate
- [ ] **Queue Depth**: Monitoring internal queue depth (if applicable)

### Alerting

- [ ] **High Error Rate**: Alert if API error rate > 5%
- [ ] **Webhook Failures**: Alert if webhook delivery fails repeatedly
- [ ] **Rate Limit Approaching**: Alert at 80% of rate limit
- [ ] **Latency Spike**: Alert if P95 latency > 2 seconds

### Incident Response

- [ ] **On-Call Rotation**: Team member on-call for Protegey-related issues
- [ ] **Runbook**: Documented procedures for common issues
- [ ] **Contact Info**: Protegey support contact information accessible
- [ ] **Rollback Plan**: Ability to disable Protegey integration if needed

## Phase 13: Go-Live

### Pre-Launch

- [ ] **Legal Review**: MSA and DPA signed
- [ ] **Security Questionnaire**: Completed and approved
- [ ] **Production Keys**: Production API keys generated and secured
- [ ] **Smoke Tests**: Basic health checks passing in production

### Launch Strategy

- [ ] **Shadow Mode**: Running in shadow mode for 1 week (log scores, don't block)
- [ ] **Gradual Rollout**: Blocking only critical risk initially (score ≥ 90)
- [ ] **Threshold Adjustment**: Plan to lower threshold after observing patterns
- [ ] **Customer Communication**: Support team prepared for fraud-related inquiries

### Post-Launch

- [ ] **Daily Monitoring**: Checking dashboards daily for first 2 weeks
- [ ] **False Positive Review**: Reviewing false positives and tuning thresholds
- [ ] **Performance Metrics**: Tracking fraud detection rate and false positive rate
- [ ] **Team Feedback**: Collecting feedback from fraud analysts on workflow
