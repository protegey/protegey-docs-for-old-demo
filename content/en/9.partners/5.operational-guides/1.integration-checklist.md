Use this comprehensive checklist to verify your Protegey integration before going live. Complete all items in sandbox first, then validate in production.

::callout{icon="i-lucide-clipboard-check" color="blue"}
**Production Readiness**: A complete integration includes signal ingestion, case management, alert workflows, webhook handling, and proper error handling.
::

---

## Phase 1: Sandbox Setup

### Environment Configuration
- [ ] **Sandbox Access**: Sandbox API keys generated in Partner Portal
- [ ] **Environment Switching**: Can toggle between sandbox and production environments
- [ ] **Cookie/Header Configuration**: Environment switching works via query params, cookies, or headers

### Demo Data Generation
- [ ] **Signal Generation**: Can generate demo signals via API (`/api/v1/partner/sandbox/generate-demo-signals`)
- [ ] **Template Testing**: Tested multiple signal templates (account takeover, stolen financials, etc.)
- [ ] **Risk Distribution**: Verified risk profiling (10% critical, 20% high, 30% medium, 40% low)

### Data Isolation
- [ ] **Schema Separation**: Confirmed sandbox signals don't appear in production dashboard
- [ ] **Reset Functionality**: Successfully reset sandbox data via API
- [ ] **Production Safety**: No test data polluting production environment

---

## Phase 2: Core Integration

## Security
- [ ] **API Key Storage**: Keys are stored in environment variables or a secrets manager, not in code.
- [ ] **IP Allowlist**: Production IP addresses are configured in the Partner Portal.
- [ ] **TLS**: All API requests use HTTPS.

## Reliability
- [ ] **Timeouts**: API client has a configured timeout (recommended: 2000ms).
- [ ] **Fail-Open/Closed**: Logic is in place to handle API unavailability (e.g., default to "Allow" or "Manual Review").
- [ ] **Retries**: Exponential backoff is implemented for `429` and `5xx` errors.

## Data Quality
- [ ] **Entity Formatting**: Emails are lowercased and trimmed. Phone numbers are E.164 formatted.
- [ ] **Hashing**: If using pre-hashed PII, ensure SHA-256 is used correctly.
- [ ] **Async specific**: Signal submissions are performed asynchronously (background job) to avoid UI blocking.

## Operational
- [ ] **Monitoring**: You are logging Protegey API response codes and latency.
- [ ] **Alerting**: You have alerts set up for a spike in 4xx/5xx errors.
- [ ] **Contacts**: Incident, Billing, and Technical contacts are up to date in the Portal.

## Compliance
- [ ] **Privacy Policy**: Your user-facing privacy policy discloses fraud prevention data sharing.
- [ ] **Data Retention**: You are not storing Protegey risk scores longer than necessary (max 90 days recommended).
- [ ] **User Consent**: Appropriate user consent obtained for fraud detection processing
- [ ] **Data Processing Agreement**: DPA signed with Protegey (required for production)

---

## Phase 3: Signal Ingestion

### API Integration
- [ ] **Signal Submission**: Successfully submit fraud signals via POST `/api/v1/signals`
- [ ] **Required Fields**: All mandatory signal fields populated (transaction_id, event_type, actor, transaction)
- [ ] **Metadata Enrichment**: Include device fingerprint, IP address, country code in metadata
- [ ] **Hashing Implementation**: PII properly hashed using SHA-256 before submission

### Response Handling
- [ ] **201 Created**: Handle successful signal submission (signal ID returned)
- [ ] **400 Bad Request**: Handle validation errors gracefully
- [ ] **429 Rate Limit**: Implement retry logic with exponential backoff
- [ ] **500 Server Error**: Fail gracefully with user-friendly error message

### Testing
- [ ] **High Risk**: Test signal with high-risk indicators (large amount, cross-border, new device)
- [ ] **Low Risk**: Test signal with normal patterns
- [ ] **Bulk Ingestion**: Test ingesting 100+ signals in short timeframe

### Decision Making

- [ ] **Bulk Decisions**: Tested bulk decision workflow (Enterprise feature)

- [ ] **Manual Creation**: Can create case without linked signal

- [ ] **Category Selection**: Can categorize cases (ACCOUNT_TAKEOVER, IDENTITY_THEFT, etc.)

### Investigation Workflow
- [ ] **Note Adding**: Can add investigation notes to cases
- [ ] **Evidence Upload**: Can attach screenshots, logs, documents to cases
- [ ] **Status Updates**: Can transition status (open → in_progress → resolved → closed)
- [ ] **Assignment**: Can assign cases to team members

### Case Collaboration
- [ ] **Team Access**: All fraud team members can access cases
- [ ] **Timeline View**: Complete audit trail visible for all case activities
- [ ] **Handoff Process**: Clear process for shift changes and escalations

### Case Resolution
- [ ] **Resolution Documentation**: Resolution notes required and captured
- [ ] **Action Tracking**: Actions taken recorded (blocked actor, reversed transaction, etc.)
- [ ] **Case Closure**: Cases properly closed after resolution

## Phase 8: Webhook Integration

### Webhook Configuration
- [ ] **Endpoint Setup**: Webhook URL configured in Partner Portal
- [ ] **HTTPS Requirement**: Webhook endpoint uses HTTPS
- [ ] **Signature Verification**: HMAC-SHA256 signature verification implemented
- [ ] **Event Subscription**: Subscribed to relevant events (signal.created, alert.triggered, case.updated)

### Webhook Handler
- [ ] **Immediate Response**: Returns 200 OK within 3 seconds
- [ ] **Async Processing**: Webhook processing happens asynchronously
- [ ] **Idempotency**: Duplicate webhooks handled gracefully (event ID tracking)
- [ ] **Error Recovery**: Failed webhook processing triggers retry or alert

### Event Handling
- [ ] **signal.created**: Signal processing complete webhook handled
- [ ] **alert.triggered**: New alert webhook handled
- [ ] **case.updated**: Case status change webhook handled
- [ ] **export.ready**: CSV export complete webhook handled

### IP Whitelisting
- [ ] **Firewall Rules**: Protegey webhook IPs whitelisted (34.11.23.45-46, 35.22.11.99)
- [ ] **Network Security**: No other IPs can access webhook endpoint

---

## Phase 9: Async Operations

### Context Awareness
- [ ] **Queue Jobs**: Understanding of async signal processing (2-8 seconds)
- [ ] **Timing Expectations**: Not expecting immediate risk scores after signal submission
- [ ] **Polling vs Webhooks**: Using webhooks instead of polling for production

### Error Handling
- [ ] **Job Failures**: Retry logic for failed async operations
- [ ] **Timeout Handling**: Graceful handling when processing takes longer than expected
- [ ] **Failed Job Notifications**: Monitoring for failed job webhooks

---

## Phase 10: Production Readiness

### Performance
- [ ] **Rate Limits**: Stay within production rate limits (1000 req/min for transactions)
- [ ] **Connection Pooling**: HTTP client uses connection pooling for efficiency
- [ ] **Caching**: Risk scores cached appropriately (5-minute TTL)
- [ ] **Lazy Loading**: Heavy operations deferred to background jobs

### Monitoring
- [ ] **API Latency**: Tracking P50, P95, P99 latency for all API calls
- [ ] **Error Rates**: Monitoring 4xx and 5xx error rates
- [ ] **Success Rates**: Tracking signal ingestion success rate
- [ ] **Queue Depth**: Monitoring internal queue depth (if applicable)

### Alerting
- [ ] **High Error Rate**: Alert if API error rate > 5%
- [ ] **Webhook Failures**: Alert if webhook delivery fails repeatedly
- [ ] **Rate Limit Approaching**: Alert at 80% of rate limit
- [ ] **Latency Spike**: Alert if P95 latency > 2 seconds

### Incident Response
- [ ] **On-Call Rotation**: Team member on-call for Protegey-related issues
- [ ] **Runbook**: Documented procedures for common issues
- [ ] **Contact Info**: Protegey support contact information accessible
- [ ] **Rollback Plan**: Ability to disable Protegey integration if needed

## Phase 12: Go-Live

### Pre-Launch
- [ ] **Legal Review**: MSA and DPA signed
- [ ] **Security Questionnaire**: Completed and approved
- [ ] **Production Keys**: Production API keys generated and secured
- [ ] **Smoke Tests**: Basic health checks passing in production

### Launch Strategy
- [ ] **Shadow Mode**: Running in shadow mode for 1 week (log scores, don't block)
- [ ] **Gradual Rollout**: Blocking only critical risk initially (score ≥ 90)
- [ ] **Threshold Adjustment**: Plan to lower threshold after observing patterns
- [ ] **Customer Communication**: Support team prepared for fraud-related inquiries

### Post-Launch
- [ ] **Daily Monitoring**: Checking dashboards daily for first 2 weeks
- [ ] **False Positive Review**: Reviewing false positives and tuning thresholds
- [ ] **Performance Metrics**: Tracking fraud detection rate and false positive rate
- [ ] **Team Feedback**: Collecting feedback from fraud analysts on workflow

---

## Phase 13: Optimization

### Threshold Tuning
- [ ] **False Positive Rate**: Target < 10% false positive rate
- [ ] **Fraud Detection Rate**: Target > 90% fraud detection rate
- [ ] **Manual Review Rate**: Optimize to keep manual review queue manageable
- [ ] **Monthly Review**: Schedule monthly threshold review meetings

### Workflow Optimization
- [ ] **Case Templates**: Create templates for common fraud types
- [ ] **Automated Actions**: Automate routine tasks (e.g., auto-block confirmed fraudsters)
- [ ] **Integration Expansion**: Integrate with CRM, ticketing, or BI tools
- [ ] **Custom Reports**: Build custom reports for leadership

### Knowledge Building
- [ ] **Fraud Pattern Library**: Document common fraud patterns observed
- [ ] **Investigation Playbooks**: Create playbooks for different fraud types
- [ ] **Team Retros**: Regular retrospectives on fraud investigations
- [ ] **Cross-Training**: Cross-train team members on different fraud categories
