The KYB system lets you verify business customers before onboarding them. You design the intake form, send a signed invite link, review submitted documents, and make an approval decision — with sanctions and PEP screening running automatically in the background.

::callout{icon="i-lucide-building-2" color="blue"}
**Who this is for**: Compliance officers and onboarding teams who need a structured, auditable intake process for business customers.
::

---

## How it works

```
Partner builds questionnaire
        ↓
Partner sends invite → Applicant receives email link
        ↓
Applicant completes form + uploads documents → Submits
        ↓
Background: AML risk screening (sanctions + PEP)
        ↓
Partner reviews answers, documents, screening result
        ↓
Decision: Approved / Rejected / Request more info
        ↓
If approved: Entity created in Protegey graph
             EDD case auto-triggered if high-risk
```

## Step 1 — Design your questionnaire

Go to **KYB → Questionnaires → New Questionnaire** in the partner portal, or use the [Questionnaires API](../api-reference/kyb#questionnaire-management).

### Sections and question types

Organise questions into named sections (e.g. "Business Identity", "Ownership", "Compliance"). Each question has a type:

| Type | Use for |
|---|---|
| `text` | Short free-text answers (names, registration numbers) |
| `textarea` | Long-form answers (descriptions, explanations) |
| `boolean` | Yes/No questions |
| `select` | Single-choice from a list |
| `multi_select` | Multiple choices |
| `number` | Numeric values |
| `date` | Calendar dates |

### Conditional questions

Questions can be hidden until a previous answer makes them relevant. Example: "Name of beneficial owner (>25%)" only appears when the preceding boolean question is answered "Yes".

Set conditions on a question using `conditions[]` with:
- `question_uuid` — the question that controls visibility
- `operator` — `eq`, `neq`, or `truthy`
- `value` — required for `eq`/`neq`

### Screening identifier

Mark **one** question with `is_screening_identifier: true`. The answer to that question (typically the registered business name) is what gets screened against sanctions and PEP databases when you approve an application. Without it, AML screening is skipped.

### Document requirements

Configure which document types applicants must upload alongside their answers. Set `is_required: true` for mandatory documents. See the [Document Types table](../api-reference/kyb#document-types) for the full list.

### Versioning and locking

::callout{type="warning"}
**A questionnaire locks automatically when its first invite is sent.** Locked questionnaires cannot be edited. To make changes, use **Clone** — this creates a new version you can modify freely.
::

Keep version numbers meaningful (e.g. `1.0`, `1.1`, `2.0`) so you can identify which form version an applicant used when reviewing historical applications.

## Step 2 — Send an invite

Go to **KYB → Invites → Send Invite**, or `POST /api/v1/partner/kyb/invites`.

Provide the applicant's email address, their name, and the questionnaire to use. If you omit the questionnaire, the system uses your active default.

The applicant receives an email with a unique, signed link to the applicant portal. Each link:
- Is **single-use** — once submitted, the link cannot be reused
- **Expires in 30 days** — expired invites show `status: expired` and cannot be resumed
- Opens the questionnaire immediately without requiring the applicant to create an account

Track invite status under **KYB → Invites**:

| Status | Meaning |
|---|---|
| `pending` | Email sent, not yet opened |
| `opened` | Link clicked |
| `in_progress` | At least one answer saved |
| `submitted` | Application submitted |
| `expired` | 30-day window closed |

If an invite expires before submission, send a new one. The new invite generates a fresh token.

## Step 3 — The applicant experience

The applicant portal (`/apply/{token}`) is a standalone multi-step form. Applicants do not need a Protegey account.

**What they see:**

1. **Section navigation** — left sidebar shows all sections with a progress indicator
2. **Conditional questions** — questions hidden by conditions only appear once the controlling answer is given
3. **Document upload** — drag-and-drop file upload area per document type; shows required vs. optional
4. **Session recovery** — answers are saved incrementally to the server on every field change; applicants can close the browser and resume later using the same link
5. **Submit** — the portal validates all required questions and required documents before allowing submission; missing fields are listed

After submitting, the applicant sees a confirmation screen. If you later request more information, they receive an email with a link back to the same portal to view your notes and resubmit.

## Step 4 — Review an application

Applications appear under **KYB → Applications** once submitted. Filter by status to focus on pending reviews.

**Application detail view shows:**
- All answers (question by question, in section order)
- Uploaded documents (with download links)
- AML screening result (sanctions score, PEP flag)
- Full event history (submitted, screened, decisions)
- Reviewer notes from any prior `more_info_required` round

### Making a decision

| Decision | Outcome |
|---|---|
| `approved` | Application closed. Entity created in Protegey graph. EDD case auto-triggered if high-risk (see below). |
| `rejected` | Application closed permanently. Applicant notified by email. |
| `more_info_required` | Application reopened. Applicant receives email with your notes and a link to resubmit. |

`approved` and `rejected` are **terminal** — you cannot change the decision afterwards.

When you select `more_info_required`, provide clear notes explaining what is missing or incorrect. The applicant sees your notes verbatim before resubmitting.

## Step 5 — Risk screening and EDD

### Automatic screening

When an application is submitted, the business name (from the `is_screening_identifier` question) is automatically screened against:
- **Sanctions lists** — UN, EU, and AU consolidated lists
- **PEP databases** — Politically Exposed Persons registry

Screening runs as a background job within seconds of submission. Results are visible in the application detail view before you make a decision.

### Enhanced Due Diligence (EDD) auto-trigger

When you **approve** an application, a final screening pass runs. If any of the following conditions are met, a high-priority fraud case is automatically created in your Case Management queue:

- `risk_score > 0.75`
- `is_pep = true`
- `sanctions.is_matched = true`

The auto-created case is linked to the KYB application and the newly created entity. Your compliance team will see it in **Cases → Open** with priority `high`.

::callout{icon="i-lucide-shield" color="amber"}
**EDD does not block approval.** The application status moves to `approved` regardless of the EDD trigger. The case is a parallel compliance workflow for your team to conduct additional due diligence.
::

### Entity creation

On approval, the business is materialised as a `FraudEntity` in the Protegey graph. Future signals involving the same entity (by business name hash) will be linked to this entity automatically, giving you a continuous risk profile from the moment of onboarding.

## Resubmission flow

When you request more information:

1. Application status changes to `more_info_required`
2. Applicant receives an email with a resume link
3. Applicant sees your reviewer notes on the portal status page
4. Applicant updates answers and/or documents and resubmits
5. Application status returns to `submitted`
6. Prior reviewer notes are cleared; the new submission starts fresh

There is no limit on the number of `more_info_required` / resubmit cycles. Each cycle is recorded in the event log for audit purposes.

---

## Managing questionnaire versions

Use **Clone** when you need to update a locked questionnaire:

1. Open the locked questionnaire → **Clone**
2. A new copy is created with `is_locked: false` and an incremented version (e.g. `1.0` → `1.1`)
3. Edit the clone freely
4. Set it as your new default under questionnaire settings
5. Future invites use the new version; existing in-progress applications continue on the original version

Old versions remain accessible for reviewing historical applications. The application detail view always shows which questionnaire version was used.
