Protegey blends synchronous and asynchronous processing. The most critical operations — risk scoring, detection, and taxonomy assignment — run **inline during signal ingestion** so you get a risk verdict in the same HTTP response. Heavier downstream tasks (graph linking, AML screening, entity enrichment) run asynchronously in background workers.

---

## Overview

### What Runs Synchronously?

**Signal Ingestion** — everything you need to make an immediate decision runs inline:

- UFES v2 validation and normalization
- Feature engineering (transaction z-scores, velocity windows, device novelty, geo distance)
- All 9 detectors (RapidVelocity, LargeOutlier, SimSwapProximity, NewDeviceAccess, ImpossibleTravel, SessionAnomaly, AttackChain, BeneficiaryConcentration, AgentConcentration)
- NUFSS risk scoring and taxonomy assignment
- Risk verdict returned in the `201` response

### What Runs Asynchronously?

**Signal Post-Processing** (after the HTTP response is sent):

- Hot graph linking (HotGraphService — builds ACTOR/DEVICE/MSISDN nodes and edges)
- AML compliance screening (sanctions, PEP, transaction monitoring rules — Enterprise only)
- Entity linking and trust score updates
- Alert generation for high/critical risk signals
- `signal.ingested` webhook delivery

**Bulk Operations**:

- Bulk decisioning (Enterprise feature)
- CSV exports
- Large data migrations
- Batch signal generation

**Analytics**:

- Dashboard statistics aggregation
- Risk heatmap generation
- Performance metric calculation

**Notifications**:

- Webhook delivery
- Email notifications
- SMS alerts (if configured)

### Why Asynchronous?

**Fast API Responses**: APIs return immediately without waiting for complex processing.

**Scalability**: Background workers can be scaled independently of API servers.

**Reliability**: Failed jobs can be retried automatically with exponential backoff.

**Resource Management**: Expensive operations (ML models, graph queries) run in dedicated workers.

**Context Preservation**: Jobs maintain environment context (sandbox/production) across async boundaries.

## How It Works

### Request Lifecycle

```
1. POST /api/v1/signals  (+ Idempotency-Key header)
   ↓
2. Synchronous pipeline  (runs inline, ~50–150ms)
   - UFES v2 validation
   - Feature engineering
   - 9 detectors run
   - NUFSS risk score computed
   - Taxonomy assigned
   ↓
3. 201 Created response  (risk verdict available immediately)
   {
     "signal_id": "...",
     "risk_score": 0.78,
     "risk_level": "high",
     "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"]
   }
   ↓
4. Background processing  (async, ~1–5 seconds)
   - Hot graph linking
   - AML screening (Enterprise)
   - Entity trust score update
   - Alert generation (if risk ≥ threshold)
   ↓
5. Webhook notifications (if endpoint subscribed)
   - signal.ingested  (always, after scoring)
   - alert.created    (if an alert was generated)
```

### Queue Architecture

Protegey uses **Laravel Queues** with multiple queue priorities:

| Queue      | Priority | Processing Time | Use Case                              |
| ---------- | -------- | --------------- | ------------------------------------- |
| `high`     | Highest  | < 1 second      | Real-time alerts, critical operations |
| `default`  | Normal   | 2-5 seconds     | Signal processing, fraud scoring      |
| `low`      | Low      | 5-30 seconds    | Analytics, bulk operations            |
| `webhooks` | Normal   | 1-3 seconds     | Webhook delivery                      |

**Worker Configuration**:

```bash
# High-priority queue (low latency)
php artisan queue:work --queue=high --tries=3 --timeout=30

# Default queue (normal processing)
php artisan queue:work --queue=default --tries=3 --timeout=60

# Low-priority queue (bulk operations)
php artisan queue:work --queue=low --tries=2 --timeout=300
```

## Context Preservation

### The Challenge

Queue jobs run asynchronously in separate worker processes. Without proper context, jobs might:

- Use the wrong database schema (sandbox vs production)
- Query the wrong partner's data
- Lose request tracing information

### The Solution: ContextAwareJob

All async jobs in Protegey extend `ContextAwareJob`, which:

1. **Captures context** at dispatch time (constructor)
2. **Serializes context** for queue persistence
3. **Restores context** when job executes in worker
4. **Enforces schema** automatically

**Example**:

```php
use App\Jobs\ContextAwareJob;

class ProcessFraudSignal extends ContextAwareJob
{
    public function __construct(
        private string $signalId,
        private string $partnerUuid
    ) {
        parent::__construct(); // ⚠️ CRITICAL: Captures context
    }

    protected function perform(): void
    {
        // Context already restored - queries use correct schema
        $signal = Signal::where('id', $this->signalId)
            ->where('partner_uuid', $this->partnerUuid)
            ->firstOrFail();

        // Calculate risk score
        $riskScore = $this->fraudScoringService->calculate($signal);

        // Update signal (uses correct schema automatically)
        $signal->update(['risk_score' => $riskScore]);
    }
}
```

### Context Flow

```
HTTP Request (sandbox.protegey.com)
    ↓
    environment: 'sandbox'
    schema: 'sandbox'
    ↓
ProcessFraudSignal::dispatch($signalId)
    ↓ [Job Serialized to Queue]
    {
      "job": "ProcessFraudSignal",
      "data": {
        "signalId": "sig_abc123",
        "contextData": {
          "environment": "sandbox",
          "partner_uuid": "uuid",
          "schema": "sandbox"
        }
      }
    }
    ↓ [Queue Worker Picks Up Job]
    ↓
Job::handle()
    ↓ [Context Restored]
    environment: 'sandbox'
    schema: 'sandbox'
    SET search_path TO sandbox, public
    ↓
perform() executes
    ↓ [All queries use sandbox schema]
```

## Timing Expectations

### Signal Ingestion

**API Response**: ~50–150ms (synchronous risk verdict)

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_type": "MOBILE_MONEY_SEND",
    "risk_score": 0.78,
    "risk_level": "high",
    "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
    "taxonomy": "mobile_money_fraud"
  }
}
```

**Background Processing** (1–5 seconds after response):

- Hot graph linking: < 1 second
- AML screening: 1–3 seconds (Enterprise only)
- Alert generation: < 1 second

**Webhook notification** (after background processing):

```json
{
  "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
  "event_type": "MOBILE_MONEY_SEND",
  "event_category": "transaction",
  "risk_score": 0.78,
  "risk_level": "high",
  "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
  "taxonomy": "mobile_money_fraud"
}
```

(delivered with `X-Centry-Event: signal.ingested` header)

### Bulk Operations

**Bulk Decisioning** (Enterprise):

- API Response: < 500ms
- Processing: ~100ms per signal
- 100 signals: ~10 seconds total
- Webhook on completion

**CSV Export**:

- API Response: < 200ms (returns export ID)
- Processing: 1-30 seconds (depending on volume)
- Webhook with download URL when ready

**Batch Signal Generation** (Sandbox):

- API Response: < 500ms
- Processing: ~200ms per signal
- 20 signals: ~4 seconds total
- Risk profiling applied during generation

### Analytics

**Dashboard Statistics**:

- Cached for 5 minutes
- Cache miss: 2-5 seconds to compute
- Real-time updates not available (use webhooks)

**Time-Series Analytics**:

- Computed on-demand
- 30-day range: 1-3 seconds
- 90-day range: 3-8 seconds

## Checking Job Status

### Method 1: Webhooks (Recommended)

Configure webhooks to receive notifications when async operations complete:

```typescript
// 1. Register a webhook endpoint in Partner Portal
// Settings > Integrations > Webhooks

// 2. Subscribe to relevant events
const events = [
  "signal.ingested", // fired after async post-processing completes
  "alert.created", // fired when a new fraud alert is generated
  "case.created",
  "case.status_changed",
];

// 3. Handle webhook in your application
app.post("/webhooks/protegey", express.json(), (req, res) => {
  const event = req.headers["x-centry-event"];
  const payload = req.body;

  switch (event) {
    case "signal.ingested":
      // Confirm risk scores post-graph-linking; trigger downstream enrichment
      console.log("Signal post-processed:", payload.signal_id);
      console.log("Risk score:", payload.risk_score);
      break;

    case "alert.created":
      // Route to analyst queue or PagerDuty
      if (payload.severity === "critical") {
        triggerPagerDuty(payload);
      }
      break;
  }

  res.status(200).send("OK");
});
```

### Method 2: Polling

Poll the API to check if processing is complete:

```typescript
async function waitForSignalProcessing(signalId: string) {
  let attempts = 0;
  const maxAttempts = 20; // 20 seconds max
  const interval = 1000; // 1 second

  while (attempts < maxAttempts) {
    const signal = await client.signals.get(signalId);

    if (signal.risk_score !== null) {
      // Processing complete
      return signal;
    }

    // Wait before next poll
    await sleep(interval);
    attempts++;
  }

  throw new Error("Signal processing timed out");
}
```

**Best Practices**:

- Start with 1-second intervals
- Use exponential backoff for longer waits
- Set reasonable timeouts (10-30 seconds)
- Prefer webhooks over polling for production

## Error Handling

### Automatic Retries

Failed jobs are automatically retried with exponential backoff:

| Attempt | Delay      | Example Time |
| ------- | ---------- | ------------ |
| 1       | Immediate  | 0:00         |
| 2       | 30 seconds | 0:30         |
| 3       | 2 minutes  | 2:30         |
| 4       | 8 minutes  | 10:30        |
| 5       | 32 minutes | 42:30        |

**After 5 attempts**: Job marked as failed, webhook sent (if configured).

### Common Failure Scenarios

**1. Temporary Network Issues**

- **Symptom**: Webhook delivery fails
- **Retry**: Automatic with exponential backoff
- **Resolution**: Usually resolves within 2-3 retries

**2. External API Timeouts**

- **Symptom**: Fraud scoring job times out
- **Retry**: Automatic (up to 3 attempts)
- **Resolution**: Check status page for service issues

**3. Invalid Data**

- **Symptom**: Job fails immediately
- **Retry**: Not retried (permanent failure)
- **Resolution**: Fix data and resubmit

**4. Rate Limits (Internal)**

- **Symptom**: Job delayed in queue
- **Retry**: Automatic with backoff
- **Resolution**: Waits for rate limit window to reset

### Failed Job Webhook

When a job fails after all retries:

```json
{
  "id": "evt_failed_123",
  "type": "job.failed",
  "created_at": "2026-02-03T15:30:00Z",
  "data": {
    "job": "ProcessFraudSignal",
    "signal_id": "sig_abc123",
    "error": "External API timeout after 3 attempts",
    "attempts": 5,
    "failed_at": "2026-02-03T15:30:00Z"
  }
}
```

## Best Practices

### 1. Use the Synchronous Risk Verdict

**Risk score is available immediately in the 201 response** — no polling or waiting required:

```typescript
// ✅ CORRECT: Risk verdict is synchronous
const response = await fetch("/api/v1/signals", {
  method: "POST",
  headers: {
    "X-Centry-Key": process.env.PROTEGEY_SECRET_KEY,
    "Idempotency-Key": crypto.randomUUID(),
  },
  body: JSON.stringify(signalPayload),
});
const { data } = await response.json();

// Available immediately — no poll needed
console.log(data.risk_score); // 0.78
console.log(data.risk_level); // "high"
console.log(data.detectors_triggered); // ["RAPID_TRANSACTION_VELOCITY"]

// Apply your decision logic now
if (data.risk_level === "critical") {
  await blockTransaction(data.signal_id);
} else if (data.risk_level === "high") {
  await requireAdditionalVerification();
}
```

### 2. Use Webhooks for Production

**Webhooks are more efficient than polling**:

- No unnecessary API calls
- Instant notification when ready
- Better user experience

**Setup**:

```typescript
// Configure once in partner portal
// No polling loops needed

app.post("/webhooks/protegey", async (req, res) => {
  const { type, data } = req.body;

  // Verify signature (important!)
  if (!verifySignature(req)) {
    return res.status(401).send("Invalid signature");
  }

  // Process event
  await processEvent(type, data);

  // Acknowledge immediately
  res.status(200).send("OK");
});
```

### 3. Handle Timeouts Gracefully

**Set realistic timeouts**:

```typescript
const timeout = 30000; // 30 seconds
const signal = await client.signals.create(signalData, { timeout });

// Don't wait forever - move on
if (!signal.risk_score) {
  // Process later via webhook
  console.log("Processing async, will notify via webhook");
}
```

### 4. Implement Idempotency

**Webhooks may be delivered multiple times**:

```typescript
const processedEvents = new Set<string>();

app.post("/webhooks/protegey", async (req, res) => {
  const eventId = req.body.id;

  // Check if already processed
  if (processedEvents.has(eventId)) {
    return res.status(200).send("Already processed");
  }

  // Process event
  await processEvent(req.body);

  // Mark as processed
  processedEvents.add(eventId);

  res.status(200).send("OK");
});
```

### 5. Log Job Context

**Include context in logs**:

```php
Log::info('Processing signal', [
    'signal_id' => $this->signalId,
    'partner_uuid' => $this->partnerUuid,
    'environment' => app(CentryContext::class)->environment(),
    'schema' => app(CentryContext::class)->schema(),
    'job' => static::class
]);
```

**Track queue health**:

## Troubleshooting

### Issue: "risk_score missing from 201 response"

**Cause**: Likely a validation error (422) rather than a 201 — check response status and body.

**Solution**: Ensure your payload includes `schema_version: "2.0"` and `primary_actor.entity_id`. The risk verdict is always synchronous on 201 responses — there is no polling needed.

```typescript
const response = await fetch('/api/v1/signals', { ... });
if (response.status === 422) {
  const error = await response.json();
  console.error('Validation failed:', error.errors); // find missing fields
}
```

### Issue: "Jobs processing too slowly"

**Symptoms**: Dashboard shows high queue depth, slow processing times.

**Possible Causes**:

1. Insufficient workers
2. Worker timeout too short
3. Database connection pool exhausted
4. External API rate limits

**Solutions**:

```bash
# Scale up workers
# Add more worker processes

# Increase timeout for complex jobs
php artisan queue:work --timeout=120

# Monitor worker health
php artisan queue:monitor

# Check failed jobs
php artisan queue:failed
```

---

### Issue: "Context not preserved in jobs"

**Symptom**: Job queries wrong schema or partner data.

**Cause**: Job not extending `ContextAwareJob` or parent constructor not called.

**Solution**:

```php
// ✅ CORRECT
class MyJob extends ContextAwareJob {
    public function __construct(private string $data) {
        parent::__construct(); // CRITICAL
    }

    protected function perform(): void {
        // Context restored automatically
    }
}

// ❌ WRONG
class MyJob implements ShouldQueue {
    // Context not captured!
}
```

## Advanced Topics

### Custom Queue Priorities

**Dispatch to specific queue**:

```php
ProcessFraudSignal::dispatch($signalId)->onQueue('high');
```

**Queue priority order**:

```bash
php artisan queue:work --queue=high,default,low
```

### Delayed Jobs

**Process signal after delay**:

```php
ProcessFraudSignal::dispatch($signalId)->delay(now()->addMinutes(5));
```

### Job Chaining

**Sequential job execution**:

```php
ProcessFraudSignal::withChain([
    new CalculateEntityRisk($entityId),
    new GenerateAlerts($signalId),
    new SendNotifications($partnerId)
])->dispatch($signalId);
```

### Job Batching

**Track batch progress**:

```php
$batch = Bus::batch([
    new ProcessSignal($signalId1),
    new ProcessSignal($signalId2),
    new ProcessSignal($signalId3)
])->dispatch();

// Check progress
$batch->progress(); // 66% complete
```
