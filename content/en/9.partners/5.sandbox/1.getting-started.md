The Centry Sandbox is a completely isolated environment where you can test your integration without affecting production data or incurring costs.

## Why use Sandbox?

- **Zero Risk**: Test fraud scenarios without impacting your production metrics.
- **High Fidelity**: The sandbox uses the same API endpoints, validation rules, and processing logic as production.
- **Isolated Data**: All signals, entities, and alerts are stored in a separate schema (`sandbox`).
- **Demo Tools**: Use our built-in simulator to generate realistic fraud data instantly.

## Switching Environments

You can switch between **Sandbox** and **Production** environments using multiple methods:

### In the Partner Portal

Toggle between environments using the switcher in the header.

### Via API Headers

Include the environment in your API requests:

```bash
curl -X GET https://api.protegey.com/api/v1/signals \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Centry-Environment: sandbox"
```

### Via Query Parameters

Append `?environment=sandbox` to any API endpoint:

```bash
https://api.protegey.com/api/v1/signals?environment=sandbox
```

### Via Session/Cookie Override

Set a session cookie `centry_env_override=sandbox` for persistent switching.

### Environment Detection Priority

The system resolves the environment in the following order:

1. Query parameter (`?environment=sandbox`)
2. Session/cookie override (`centry_env_override`)
3. Request header (`X-Centry-Environment`)
4. Domain detection (`sandbox.*` subdomain)
5. Referer header (for cross-origin API calls)
6. Authenticated user's partner status
7. **Default**: `production`

::callout{type="warning"}
**Important**: Each environment has its own set of API keys. Ensure you use the correct key for the environment you are targeting.
::

## Database Schema Isolation

Protegey implements **true database-level isolation** using PostgreSQL schemas:

- **Production data**: Stored in the `public` schema
- **Sandbox data**: Stored in the `sandbox` schema
- **Shared tables**: Users, partners, and subscriptions remain in `public` schema only

This architecture provides:

- **Zero risk** of sandbox data polluting production analytics
- **Easy data reset** (truncate sandbox schema)
- **Performance isolation** between environments
- **Compliance-ready** data segregation

## Context-Aware Execution

All requests and background jobs maintain an immutable **CentryContext** object that encapsulates:

- Environment state (sandbox/production)
- Partner identity (UUID)
- Request tracking ID
- Schema resolution

This ensures that all database queries, queue jobs, and webhook events use the correct schema automatically.

## Data Persistence

Sandbox data is persistent until you choose to reset it. You can perform resets with different scopes:

| Reset Scope       | What Gets Deleted                 | Use Case                          |
| ----------------- | --------------------------------- | --------------------------------- |
| **Full Reset**    | All sandbox data for your partner | Start fresh with clean slate      |
| **Signals Only**  | Just signal records               | Clear test signals but keep cases |
| **Cases Only**    | Just case records                 | Reset investigations              |
| **Entities Only** | Just entity profiles              | Clear actor intelligence          |

Access the reset functionality via **Sandbox > Reset** in the Partner Portal or use the API endpoint: `POST /api/v1/partner/sandbox/reset`
