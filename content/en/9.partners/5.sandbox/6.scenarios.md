Multi-step scenario simulation allows you to test complex fraud patterns that unfold over time, mimicking real-world attack patterns.

## Concept

Unlike single demo signals, **scenarios** generate a sequence of related signals that represent a coordinated fraud attack:

### Example: SIM Swap Drainage

1. **Step 1** (T+0 min): Initial account login from new device → Generates `ACCOUNT_TAKEOVER` signal
2. **Step 2** (T+5 min): Phone verification failure → Generates `PHONE_VERIFICATION_FAILURE` signal
3. **Step 3** (T+10 min): SIM swap detected → Generates `SIM_SWAP` signal
4. **Step 4** (T+12 min): High-value transfer to external account → Generates `TRANSACTION` signal (critical risk)
5. **Step 5** (T+15 min): Multiple small withdrawals → Generates multiple `TRANSACTION` signals (velocity pattern)

## Key Features (Planned)

### Consistent Actor Data

All steps in a scenario share the same actor identifiers (phone number, original device, etc.), creating a coherent fraud pattern:

```json
{
  "scenario_variables": {
    "SCENARIO_PHONE": "0244123456",
    "SCENARIO_ACCOUNT_ID": "ACC-12345"
  }
}
```

These variables are resolved once at scenario start and reused across all steps.

### Time-Based Delays

Scenarios unfold over realistic timeframes:

```json
{
  "step": 3,
  "delay": 600, // 10 minutes after scenario start
  "template": "sim_swap"
}
```

**Delay Modes**:

- **Real-time**: Actual delays (for live testing)
- **Fast-forward**: Accelerated delays (1 second = 1 minute) for quick testing
- **Immediate**: No delays (for bulk testing)

### Batch Tracking

All signals from a scenario are tagged with a shared batch ID:

```json
{
  "metadata": {
    "generated_by": "centry_scenario",
    "scenario_name": "sim_swap_drainage",
    "scenario_batch_id": "scenario_1738598400_abc123",
    "scenario_step": 3,
    "scenario_total_steps": 5
  }
}
```

This allows you to:

- Filter signals by scenario
- Track scenario completion
- Visualize attack timelines
- Test case linkage logic

### Simulation Events (Planned)

Scenarios emit real-time events during execution:

```json
{
  "event": "scenario.step_completed",
  "scenario_id": "scenario_1738598400_abc123",
  "step": 3,
  "total_steps": 5,
  "signals_created": 1,
  "next_step_delay": 120
}
```

## Use Cases

### Test Case Linkage Logic

Run scenarios to verify that your fraud detection system correctly:

- Links related signals to the same actor
- Escalates from signals to alerts to cases
- Prioritizes cases based on pattern severity

### Test Investigation Workflows

Use scenarios to train analysts on:

- Recognizing coordinated attack patterns
- Triaging alerts by timeline
- Identifying modus operandi from signal sequences

### Test Alert Escalation

Verify that alert rules fire correctly as scenarios unfold:

- **After Step 1**: Low-priority alert (device change)
- **After Step 3**: High-priority alert (SIM swap detected)
- **After Step 5**: Critical alert (high-velocity drainage pattern)

### Performance Testing

Run multiple scenarios concurrently to test system load:

```bash
POST /api/v1/partner/sandbox/simulate-batch
{
  "scenarios": [
    {"scenario": "sim_swap_drainage", "count": 10},
    {"scenario": "account_takeover_cascade", "count": 5}
  ],
  "mode": "fast-forward"
}
```

## Detector-Specific Scenarios

The following scenarios are designed to reliably trigger specific fraud detectors. Use them to test your alert handling pipeline and verify that your integration correctly processes each detector type.

### 1. Velocity Burst — `RAPID_TRANSACTION_VELOCITY`

Send **12 signals** for the same `entity_id` within a 45-minute window. Each signal should have `event_type: PAYMENT_FRAUD` and a modest amount (< structuring threshold). The 10th signal will trigger `RAPID_TRANSACTION_VELOCITY`.

```bash
# Loop 12 times with the same entity_id
for i in $(seq 1 12); do
  curl -X POST https://api.protegey.com/api/v1/signals \
    -H "X-API-Key: $SANDBOX_KEY" \
    -d '{"event_type":"PAYMENT_FRAUD","primary_actor":{"entity_id":"test-entity-burst-001"},"event_payload":{"amount":150,"currency":"USD"}}'
  sleep 3
done
```

**Expected**: Alert with `detectors_triggered: ["RAPID_TRANSACTION_VELOCITY"]`, risk_level `high`.

---

### 2. Large Outlier — `LARGE_OUTLIER_TRANSACTION`

First, establish a baseline by sending **10 signals** for the same entity with amounts between 50–200 USD. Then send one signal with `amount: 2500`. The z-score will exceed 3.0 and trigger `LARGE_OUTLIER_TRANSACTION`.

**Expected**: Alert with `detectors_triggered: ["LARGE_OUTLIER_TRANSACTION"]`, `fusion.behavioral_score > 0.7`.

---

### 3. SIM Swap Attack — `SIM_SWAP_PROXIMITY`

Send a signal that includes `sim_changed_at` set to **90 minutes ago** combined with a new (first-seen) device fingerprint. This simulates an account takeover following a SIM swap.

```json
{
  "event_type": "ACCOUNT_TAKEOVER",
  "primary_actor": {
    "entity_id": "test-entity-simswap-001",
    "identifiers": {
      "msisdn": "hash:msisdn",
      "sim_changed_at": "{{ now | minus: 90 | iso8601 }}"
    },
    "device": {
      "fingerprint": "{{ uuid }}",
      "is_first_seen": true
    }
  }
}
```

**Expected**: Alert with `detectors_triggered: ["SIM_SWAP_PROXIMITY"]`.

---

### 4. New Device + High Risk Geography — `NEW_DEVICE_ACCESS`

Send a signal with a first-seen device fingerprint and a source IP that resolves to a high-risk jurisdiction (e.g., Nigeria via the GeoResolver).

```json
{
  "event_type": "ACCOUNT_TAKEOVER",
  "primary_actor": {
    "entity_id": "test-entity-newdevice-001",
    "device": {
      "fingerprint": "{{ uuid }}"
    }
  },
  "source": {
    "ip_address": "197.210.0.1"
  }
}
```

**Expected**: Alert with `detectors_triggered: ["NEW_DEVICE_ACCESS"]`.

---

### 5. Impossible Travel — `IMPOSSIBLE_TRAVEL`

Send two signals for the same entity within **90 minutes** — one with a Ghanaian IP address, one with a French IP address. The GeoResolver will compute the distance and trigger the impossible travel detector.

**Signal 1** — IP resolves to Accra, Ghana: `source.ip_address: "154.160.0.1"`
**Signal 2** (90 min later) — IP resolves to Paris, France: `source.ip_address: "2.2.0.1"`

**Expected**: Second signal triggers alert with `detectors_triggered: ["IMPOSSIBLE_TRAVEL"]`.

---

### 6. Fraud Ring — Graph Network — Graph Visualization

Create **3 entities** that share the same `device.fingerprint`. Send 2–3 signals per entity. After ingestion, call `GET /entities/{uuid}/graph-visualization` on any of the three entities.

**Expected**: Graph response shows all 3 entities connected via `shared_device` edges with weight ≥ 0.9. The `propagated_risk` on each entity will reflect the network's aggregate risk.
