Protegey implements **true database-level isolation** for sandbox environments, ensuring complete separation between sandbox and production data at the PostgreSQL schema level.

## PostgreSQL Schema Isolation

### Physical Separation

Unlike logical separation (e.g., `WHERE environment = 'sandbox'`), Protegey uses **physical schema separation**:

```
protegey_database
├── public schema (production)
│   ├── signals
│   ├── fraud_cases
│   ├── fraud_entities
│   ├── fraud_alerts
│   └── ... (all partner-scoped tables)
│
├── sandbox schema (sandbox)
│   ├── signals
│   ├── fraud_cases
│   ├── fraud_entities
│   ├── fraud_alerts
│   └── ... (duplicated partner-scoped tables)
│
└── shared tables (public only)
    ├── users
    ├── partners
    ├── subscriptions
    ├── plans
    └── invoices
```

### Benefits of Schema Isolation

| Benefit                      | Description                                                      |
| ---------------------------- | ---------------------------------------------------------------- |
| **Zero Analytics Pollution** | Sandbox signals never affect production metrics or risk scoring  |
| **Easy Data Reset**          | `TRUNCATE sandbox.signals` clears all sandbox data instantly     |
| **Performance Isolation**    | Sandbox queries don't compete with production indexes            |
| **Compliance Ready**         | Physical separation for regulatory data segregation requirements |
| **Simple Backup Strategy**   | Back up `public` schema without sandbox test data                |

### How Schema Enforcement Works

Every request automatically sets the PostgreSQL `search_path`:

```sql
-- Sandbox request
SET search_path TO sandbox, public;

-- Production request
SET search_path TO public, public;
```

This means:

1. All queries automatically use the correct schema
2. No need to prefix table names with schema (e.g., `sandbox.signals`)
3. Shared tables (users, partners) are always in `public`, so they work seamlessly

::callout{type="info"}
**Technical Detail**: The `EnforceSchemaIsolation` middleware runs after authentication and sets the schema based on the resolved `CentryContext`. This is idempotent and can run multiple times without issues.
::

## CentryContext: Immutable Execution Context

The `CentryContext` is an immutable object that encapsulates all environment state for a request or job.

### Context Structure

```php
CentryContext {
  environment: 'sandbox' | 'production'
  partnerUuid: string | null
  requestId: string | null
  metadata: array
}
```

### Context Creation

```php
// Create sandbox context
$context = CentryContext::sandbox($partnerUuid);

// Create production context
$context = CentryContext::production($partnerUuid);

// Detect from HTTP request
$context = CentryContext::fromRequest($request);

// With metadata
$context = CentryContext::sandbox($partnerUuid)
    ->withMetadata(['user_id' => $userId]);
```

### Context Methods

| Method           | Returns        | Description                                      |
| ---------------- | -------------- | ------------------------------------------------ |
| `environment()`  | `string`       | Get environment name                             |
| `partnerUuid()`  | `string\|null` | Get partner UUID                                 |
| `requestId()`    | `string\|null` | Get request tracking ID                          |
| `metadata()`     | `array`        | Get additional metadata                          |
| `isSandbox()`    | `bool`         | Check if sandbox                                 |
| `isProduction()` | `bool`         | Check if production                              |
| `schema()`       | `string`       | Get database schema name (`sandbox` or `public`) |

## Environment Detection Priority

When processing a request, the system resolves the environment in this order:

1. **Query Parameter**: `?environment=sandbox`

   ```bash
   https://api.protegey.com/api/v1/signals?environment=sandbox
   ```

2. **Session/Cookie Override**: `centry_env_override` cookie

   ```javascript
   // Set in browser console for persistent switching
   document.cookie = "centry_env_override=sandbox; path=/";
   ```

3. **Request Header**: `X-Centry-Environment` header

   ```bash
   curl -H "X-Centry-Environment: sandbox" \
     https://api.protegey.com/api/v1/signals
   ```

4. **Domain Detection**: `sandbox.*` subdomain

   ```
   https://sandbox.api.protegey.com/api/v1/signals
   ```

5. **Referer Header**: For cross-origin API calls from Partner Portal

   ```
   Referer: https://sandbox.partner.protegey.com/...
   ```

6. **Authenticated User**: Partner's environment status

   ```php
   if ($user->partner->is_sandbox) {
       $environment = 'sandbox';
   }
   ```

7. **Default**: `production` (fail-safe)

::callout{type="warning"}
**Security Note**: Environment detection is always validated against the authenticated partner's allowed environments. You cannot access production data while authenticated to a sandbox-only partner.
::

## Context-Aware Execution

### HTTP Requests

```
HTTP Request
    ↓
[ResolveCentryContext Middleware]
    ↓
[EnforceSchemaIsolation Middleware]
    ↓
Controller → Model Query
    ↓
PostgreSQL (correct schema)
```

**Middleware Stack**:

```php
Route::middleware([
    'auth:api',
    'resolve.context',      // Creates CentryContext
    'enforce.schema',       // Sets search_path
])->group(function () {
    // All routes here have correct schema
});
```

### Queue Jobs

For asynchronous processing, context must be preserved across the queue boundary.

**ContextAwareJob Base Class**:

```php
use App\Jobs\ContextAwareJob;

class ProcessFraudSignal extends ContextAwareJob
{
    public function __construct(private string $signalId) {
        parent::__construct(); // Captures current context
    }

    protected function perform(): void {
        // Context already restored
        // All queries use correct schema
        $signal = Signal::find($this->signalId);
        // ... fraud scoring logic
    }
}
```

**How It Works**:

1. **Dispatch Time**: Constructor captures current `CentryContext` from service container
2. **Serialization**: Context is serialized and stored with job payload
3. **Worker Execution**: Context is restored before `perform()` runs
4. **Schema Enforcement**: `search_path` is set automatically

::callout{type="danger"}
**Critical**: All queue jobs MUST extend `ContextAwareJob` to ensure correct schema isolation. Jobs that don't extend this base class will fail with `MissingContextException` if they try to dispatch without context bound.
::

### CLI Commands

For Artisan commands that dispatch jobs, you must explicitly bind context:

```php
use App\Context\CentryContext;

class GenerateDemoSignalsCommand extends Command
{
    public function handle()
    {
        $partnerUuid = $this->argument('partner');

        // Bind sandbox context
        app()->instance(
            CentryContext::class,
            CentryContext::sandbox($partnerUuid)
        );

        // Now jobs dispatched from this command inherit context
        ProcessFraudSignal::dispatch($signalId);
    }
}
```

## Data Isolation Guarantees

### What is Isolated

✅ **Partner-scoped tables** (duplicated in `sandbox` schema):

- `signals`
- `fraud_cases`
- `fraud_entities`
- `fraud_alerts`
- `case_notes`
- `case_evidence`
- All partner-specific operational data

### What is Shared

🔗 **Shared tables** (only in `public` schema):

- `users` - User accounts
- `partners` - Partner organizations
- `subscriptions` - Billing subscriptions
- `plans` - Subscription plans
- `invoices` - Billing invoices
- `partner_api_keys` - API keys (with environment flag)
- System configuration tables

::callout{type="info"}
**Why Share These Tables?**: Billing, user management, and system configuration are global to the partner organization. A sandbox partner record links to its production parent via `production_parent_uuid`.
::

## Testing Best Practices

### Test Schema Isolation

```php
// In tests, explicitly set context
public function test_sandbox_signal_creation()
{
    $this->actingAs($user);

    app()->instance(
        CentryContext::class,
        CentryContext::sandbox($partner->uuid)
    );

    $response = $this->postJson('/api/v1/signals', $payload);

    // Signal should exist in sandbox schema only
    $this->assertDatabaseHas('sandbox.signals', [
        'partner_uuid' => $partner->uuid,
    ]);

    $this->assertDatabaseMissing('public.signals', [
        'partner_uuid' => $partner->uuid,
    ]);
}
```

### Verify Context Preservation in Jobs

```php
public function test_job_preserves_context()
{
    app()->instance(
        CentryContext::class,
        CentryContext::sandbox($partner->uuid)
    );

    ProcessFraudSignal::dispatch($signalId);

    // After job runs, signal should be scored in sandbox
    $signal = Signal::find($signalId); // Queries sandbox schema
    $this->assertEquals('sandbox', $signal->environment);
}
```

## Advanced Topics

### Custom Schema Names

While not recommended, you can extend the system to support custom schema names:

```php
// In CentryContext
public function schema(): string
{
    return match($this->environment) {
        'sandbox' => 'sandbox',
        'staging' => 'staging',
        'production' => 'public',
        default => 'public',
    };
}
```

### Multi-Region Schema Isolation

For multi-region deployments, you can combine schema isolation with database-level separation:

```
Region: West Africa (WA)
└── protegey_wa
    ├── public (production)
    └── sandbox (sandbox)

Region: East Africa (EA)
└── protegey_ea
    ├── public (production)
    └── sandbox (sandbox)
```

### Performance Considerations

**Indexes**: Each schema maintains its own indexes, so:

- Sandbox testing doesn't affect production index statistics
- You can drop/recreate sandbox indexes without downtime

**Vacuum**: Sandbox and production schemas can be vacuumed independently:

```sql
VACUUM ANALYZE sandbox.signals;
```

**Connections**: Schema isolation uses the same connection pool, so no connection overhead.

## Troubleshooting

### "Table not found" errors

**Symptom**: `ERROR: relation "signals" does not exist`

**Cause**: Schema not set correctly

**Solution**: Verify middleware order:

```php
// ResolveCentryContext MUST come before EnforceSchemaIsolation
Route::middleware([
    'resolve.context',
    'enforce.schema',
])->group(...);
```

### Jobs writing to wrong schema

**Symptom**: Sandbox jobs creating records in production

**Cause**: Job doesn't extend `ContextAwareJob`

**Solution**:

```php
// ❌ Wrong
class MyJob extends Job { ... }

// ✅ Correct
class MyJob extends ContextAwareJob { ... }
```

### Context not found in CLI

**Symptom**: `MissingContextException` when running Artisan command

**Cause**: Context not bound in CLI environment

**Solution**:

```php
// Bind context before dispatching jobs
app()->instance(
    CentryContext::class,
    CentryContext::sandbox($partnerUuid)
);
```

## Security Considerations

### Environment Validation

The system validates environment access based on partner permissions:

```php
// Partner can only access sandbox if explicitly allowed
if ($requestedEnvironment === 'sandbox' && !$partner->has_sandbox_access) {
    abort(403, 'Sandbox access not enabled for this partner');
}
```

### API Key Environment Scoping

API keys are scoped to environments:

- **Production keys**: `cen_live_sk_*` → Can only access production
- **Sandbox keys**: `cen_test_sk_*` → Can only access sandbox

### Preventing Cross-Environment Data Leakage

1. **Schema isolation**: Physical database separation
2. **Context validation**: Middleware enforces environment boundaries
3. **API key scoping**: Keys cannot cross environments
4. **Job context capture**: Asynchronous jobs preserve environment

::callout{type="success"}
**Result**: Zero risk of sandbox data polluting production metrics or vice versa.
::
