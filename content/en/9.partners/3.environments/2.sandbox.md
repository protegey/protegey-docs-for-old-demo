The Sandbox is designed to help you integrate quickly and safely. It behaves exactly like Production but uses **physically isolated data** with complete schema separation at the database level.

::callout{icon="i-lucide-database" color="blue"}
**True Isolation**: Protegey implements physical database schema separation using PostgreSQL schemas. Sandbox data lives in a separate `sandbox` schema, ensuring zero risk of pollution in production analytics.
::

---

## Architecture Overview

### Database Schema Isolation

Protegey uses **PostgreSQL schema-level separation** to ensure complete data isolation between sandbox and production environments:

**Schema Structure**:
```
PostgreSQL Database
├── public schema (Production + Shared Tables)
│   ├── signals (production data)
│   ├── fraud_entities (production data)
│   ├── fraud_cases (production data)
│   ├── users (shared across all environments)
│   ├── partners (shared across all environments)
│   └── subscriptions (shared across all environments)
│
└── sandbox schema (Sandbox Data)
    ├── signals (sandbox data)
    ├── fraud_entities (sandbox data)
    ├── fraud_cases (sandbox data)
    └── [all partner-scoped tables duplicated]
```

**Key Benefits**:
- **Zero cross-contamination**: Sandbox signals never affect production risk scores
- **Easy data reset**: Truncate sandbox schema without touching production
- **Performance isolation**: Sandbox queries don't impact production performance
- **Compliance-ready**: Clear audit trail showing data segregation

### How It Works

When you make an API request or log into the partner portal:

1. **Environment Detection**: System detects environment from query params, cookies, headers, or domain
2. **Context Binding**: Creates `CentryContext` object with environment state
3. **Schema Enforcement**: Sets PostgreSQL `search_path` to correct schema
4. **Query Execution**: All database queries automatically use the correct schema

**Example**:
```sql
-- Sandbox request sets search_path
SET search_path TO sandbox, public;

-- Queries automatically use sandbox schema
SELECT * FROM signals WHERE partner_uuid = 'your-uuid';
-- Reads from: sandbox.signals

-- Shared tables still use public schema
SELECT * FROM users WHERE id = 42;
-- Reads from: public.users (shared)
```

**See Also**: [Context-Aware Execution](./context-resolution) for technical deep-dive.

## Data Separation Guarantees

### What's Isolated

**Per-Environment Data** (duplicated across schemas):
- ✅ Fraud signals
- ✅ Fraud entities
- ✅ Fraud cases
- ✅ Fraud alerts
- ✅ Transactions
- ✅ Analytics data
- ✅ Decision history

**Shared Data** (same across environments):
- ✅ Users (your team members)
- ✅ Partner organization settings
- ✅ Subscriptions and billing
- ✅ Roles and permissions
- ✅ API keys

### Isolation Enforcement

**Automatic Schema Selection**:
```typescript
// Sandbox API call
const client = new ProtegeyClient({
  accessToken: 'YOUR_TOKEN',
  environment: 'sandbox'
});

// All queries use sandbox schema automatically
const signals = await client.signals.list();
// Reads from: sandbox.signals
```

**Query-Level Enforcement**:
- Every HTTP request resolves environment context
- Middleware sets PostgreSQL `search_path` before any queries
- No manual schema prefixing required in application code
- Impossible to accidentally query wrong schema

**Audit Trail**:
- All sandbox operations logged with `environment: 'sandbox'`
- Request ID tracking across HTTP and queue jobs
- Schema enforcement logged for debugging

## Switching Between Environments

### Method 1: Query Parameter

**Partner Portal**:
```
https://partner.protegey.com/dashboard?environment=sandbox
```

**API Request**:
```bash
curl "https://api.protegey.com/v1/signals?environment=sandbox" \
  -H "Authorization: Bearer YOUR_TOKEN"
```

### Method 2: HTTP Header

```bash
curl "https://api.protegey.com/v1/signals" \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Centry-Environment: sandbox"
```

### Method 3: Cookie (Persistent)

```javascript
// Switch to sandbox (persists across requests)
document.cookie = 'centry_env_override=sandbox; path=/; max-age=86400';

// Switch back to production
document.cookie = 'centry_env_override=production; path=/; max-age=86400';
```

**See Also**: [Context-Aware Execution - Switching Environments](./context-resolution#switching-environments) for all methods.

## Reset Functionality

### Granular Reset Options

Reset specific data types in your sandbox without affecting others:

| Reset Option | Description | API Endpoint |
|--------------|-------------|--------------|
| **Full Reset** | Clear all sandbox data | `POST /api/v1/partner/sandbox/reset` |
| **Signals Only** | Clear signals, keep entities and cases | `POST /api/v1/partner/sandbox/reset?scope=signals` |
| **Entities Only** | Clear entities, keep signals and cases | `POST /api/v1/partner/sandbox/reset?scope=entities` |
| **Cases Only** | Clear cases, keep signals and entities | `POST /api/v1/partner/sandbox/reset?scope=cases` |
| **Alerts Only** | Clear alerts | `POST /api/v1/partner/sandbox/reset?scope=alerts` |
| **Relationships** | Clear entity relationships | `POST /api/v1/partner/sandbox/reset?scope=relationships` |

**Full Reset Example**:
```bash
curl -X POST "https://api.protegey.com/v1/partner/sandbox/reset" \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Centry-Environment: sandbox"
```

**Selective Reset Example**:
```typescript
// Clear only signals, preserve entity profiles
await client.sandbox.reset({ scope: 'signals' });
```

### What Happens During Reset

**Full Reset**:
1. All sandbox signals deleted (`sandbox.signals`)
2. All sandbox entities deleted (`sandbox.fraud_entities`)
3. All sandbox cases deleted (`sandbox.fraud_cases`)
4. All sandbox alerts deleted (`sandbox.fraud_alerts`)
5. Entity relationships cleared
6. Analytics recalculated

**Preserved Data**:
- User accounts (shared)
- Partner settings (shared)
- API keys (shared)
- Subscription status (shared)

**Post-Reset State**:
- Clean sandbox environment
- Ready for fresh testing
- No data carryover from previous tests

### Reset Frequency

**Manual Reset**: Available on-demand via API
**Automatic Reset**: Weekly on Sundays at 00:00 UTC (configurable per partner)

::callout{icon="i-lucide-alert-circle" color="amber"}
**Important**: Reset is irreversible. Ensure you've exported any data you need before resetting.
::

## Testing Best Practices

### 1. Use Sandbox for All Development

Always develop and test integration code in sandbox before going to production:

```typescript
// ✅ CORRECT: Develop in sandbox
const devClient = new ProtegeyClient({
  accessToken: process.env.SANDBOX_TOKEN,
  environment: 'sandbox'
});

// Test your integration
await devClient.signals.create({...});

// ❌ WRONG: Developing in production
const prodClient = new ProtegeyClient({
  accessToken: process.env.PROD_TOKEN,
  environment: 'production' // Don't use for testing!
});
```

### 2. Generate Demo Signals for Testing

Use the demo signal generation API to create realistic test data:

```bash
# Generate 20 demo signals with varied risk profiles
curl -X POST "https://api.protegey.com/v1/partner/sandbox/generate-demo-signals" \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -d '{
    "template": "transaction/account_takeover",
    "count": 20
  }'
```

**Risk Profile Distribution**:
- 10% critical risk (scores 80-100)
- 20% high risk (scores 60-79)
- 30% medium risk (scores 40-59)
- 40% low risk (scores 0-39)

**See Also**: [Demo Signals Guide](../sandbox/demo-signals) for template options.

### 3. Test Edge Cases

**High-Risk Scenarios**:

### 4. Test Error Handling

Use magic values to force errors (see section below):

```typescript
try {
  // Force a rate limit error
  await client.signals.create({
    ...signalData,
    headers: { 'X-Force-Error': 'rate_limit' }
  });
} catch (error) {
  if (error.status === 429) {
    console.log('Correctly handled rate limit');
  }
}
```

### 5. Reset Between Test Runs

Reset sandbox data between test suites for consistency:

```typescript
// Before each test suite
beforeAll(async () => {
  await client.sandbox.reset({ scope: 'signals' });
});

// Run tests with clean state
test('signal ingestion', async () => {
  const signal = await client.signals.create({...});
  expect(signal.id).toBeDefined();
});
```

### 6. Validate Data Isolation

Verify sandbox data doesn't leak into production:

```typescript
// Create signal in sandbox
const sandboxClient = new ProtegeyClient({
  environment: 'sandbox',
  accessToken: YOUR_TOKEN
});

await sandboxClient.signals.create({ transaction_id: 'SANDBOX-001' });

// Switch to production and verify signal doesn't exist
const prodClient = new ProtegeyClient({
  environment: 'production',
  accessToken: YOUR_TOKEN
});

const prodSignals = await prodClient.signals.list({
  search: 'SANDBOX-001'
});

expect(prodSignals.data.length).toBe(0); // Should not exist in production
```

## Magic Values

Sandbox supports "Magic Values" to force specific responses. This allows you to test your logic for different risk scenarios without needing to create complex signals.

### Forcing Risk Scores

When querying an entity (e.g., an Email), use these prefixes to trigger specific scores:

| Email Pattern | Resulting Score | Recommendation |
|---------------|-----------------|----------------|
| `low_risk_user@example.com` | `10` | APPROVE |
| `med_risk_user@example.com` | `45` | REVIEW |
| `high_risk_user@example.com` | `85` | DECLINE |
| `critical_user@example.com` | `99` | DECLINE |

### Forcing Errors

To test your error handling, pass these values in the `X-Force-Error` header (Sandbox only):

| Header Value | HTTP Response | Scenario |
|--------------|---------------|----------|
| `timeout` | `504 Gateway Timeout` | Simulate network latency |
| `rate_limit` | `429 Too Many Requests` | Simulate quota exhaustion |
| `server_error` | `500 Internal Server Error` | Simulate platform outage |

```bash
# Example: Force a 429 error
curl -X GET https://sandbox-api.protegey.com/v1/queries/user \
  -H "X-Centry-Key: cen_test_sk_..." \
  -H "X-Force-Error: rate_limit"
```
