# Signals API

The Signals API enables partners to submit fraud indicators to the network. Signals are ingested asynchronously and processed by the Risk Engine.

::callout{icon="i-lucide-shield-alert" color="amber"}
**Production Access Required**: You must have active production keys to post live signals. Sandbox signals do not affect network scores.
::

## Endpoint

```http
POST /api/v1/signals
```

## Request Schema

### Headers

| Header | Value | Required | Description |
|--------|-------|----------|-------------|
| `Content-Type` | `application/json` | Yes | Standard JSON payload. |
| `X-Centry-Key` | `cen_live_sk_...` | Yes | Your Production Secret Key. |

### Body Parameters

The payload is structured into `actor`, `event`, and `transaction` objects.

```typescript
interface SignalRequest {
  actor: {
    hashed_id: string; // The primary entity identifier (hashed or plain)
    device_fingerprint?: string;
    region?: string;
  };
  event: {
    type: string; // The fraud signal (e.g., ACCOUNT_TAKEOVER)
    timestamp: string; // ISO 8601 (e.g., 2026-01-12T14:30:00Z)
    channel?: string; // WEB, MOBILE, API, etc.
  };
  transaction?: {
    amount?: number;
    currency?: string; // ISO 4217 (3 chars)
    geo_location?: {
      lat: number;
      lon: number;
    };
  };
  source_confidence?: number; // 0.0 to 1.0 (default: 0.5)
  metadata?: Record<string, any>;
}
```

### Validation Rules

| Field | Required | Rules |
|-------|----------|-------|
| `actor.hashed_id` | **Yes** | String. The identifier of the entity (e.g. SHA-256 hash or raw value). |
| `event.type` | **Yes** | Must match a valid code (e.g., `ACCOUNT_TAKEOVER`, `SYNTHETIC_IDENTITY`). |
| `event.timestamp` | **Yes** | ISO 8601. Cannot be in the future. |
| `transaction.currency` | No | Must be exactly 3 characters if provided. |
| `transaction.geo_location` | No | Both `lat` and `lon` required if object exists. |
| `source_confidence` | No | Float between 0.0 and 1.0. |

## Phone Normalization

Protegey uses a **Tiered Normalization Strategy** to ensure high data quality for phone-based entities. When you submit a signal with an `actor_hashed_id` or metadata containing a phone number, the system automatically converts it to a canonical E.164 format.

### Supported Markets (African Primary Markets)

The system provides strict, local-format normalization for the following countries:

| Country | ISO Code | Local Format Examples | Result (E.164) |
|---------|----------|-----------------------|----------------|
| **Senegal** | `SN` | `077 123 45 67`, `771234567` | `+221771234567` |
| **Côte d'Ivoire** | `CI` | `07 01 23 45 67`, `0102030405` | `+2250701234567` |
| **Mali** | `ML` | `07123456`, `6123456` | `+2237123456` |
| **Burkina Faso** | `BF` | `54123456`, `76123456` | `+22654123456` |
| **Cameroon** | `CM` | `690123456` | `+237690123456` |
| **DR Congo** | `CD` | `810123456`, `990123456` | `+243810123456` |
| **Morocco** | `MA` | `06 12 34 56 78`, `612345678` | `+212612345678` |
| **Algeria** | `DZ` | `05 12 34 56 78`, `512345678` | `+213512345678` |
| **Tunisia** | `TN` | `21 123 456`, `98123456` | `+21621123456` |
| **Egypt** | `EG` | `010 1234 5678`, `1112345678` | `+201012345678` |
| **Ghana** | `GH` | `024 123 4567`, `241234567` | `+233241234567` |
| **Nigeria** | `NG` | `0803 123 4567`, `7012345678` | `+2348031234567` |

### Optional Country Hint (`actor.region`)

If a phone number pattern is ambiguous (e.g., overlapping patterns between Morocco and Algeria), you can provide an optional **Country Hint** using the `actor.region` field.

::callout{icon="i-lucide-lightbulb" color="primary"}
**Best Practice**: Always provide the `actor.region` (ISO 3166-1 alpha-2) if known. This guarantees 100% normalization accuracy even for complex or overlapping local formats.
::

```json
{
  "actor": {
    "hashed_id": "0612345678",
    "region": "MA" // Ensures normalization as a Moroccan (+212) number
  }
}
```

## Examples

### 1. Standard Submission

```bash
curl -X POST "https://api.protegey.com/v1/signals" \
  -H "Content-Type: application/json" \
  -H "X-Centry-Key: cen_live_sk_..." \
  -d '{
    "actor": {
      "hashed_id": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "region": "US"
    },
    "event": {
      "type": "ACCOUNT_TAKEOVER",
      "timestamp": "2026-01-12T14:30:00Z",
      "channel": "MOBILE"
    },
    "source_confidence": 0.9,
    "metadata": {
      "detection_method": "behavioral_biometrics"
    }
  }'
```

### 2. Transaction Signal

```bash
curl -X POST "https://api.protegey.com/v1/signals" \
  -H "Content-Type: application/json" \
  -H "X-Centry-Key: cen_live_..." \
  -d '{
    "actor": {
      "hashed_id": "user@example.com"
    },
    "event": {
      "type": "STOLEN_FINANCIALS",
      "timestamp": "2026-01-12T14:30:00Z"
    },
    "transaction": {
      "amount": 4500.00,
      "currency": "USD",
      "geo_location": {
        "lat": 37.7749,
        "lon": -122.4194
      }
    }
  }'
```

## Response

### Success Response (`201 Created`)

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-...",
    "status": "received",
    "event_type": "ACCOUNT_TAKEOVER",
    "timestamp": "2026-01-12T14:30:00+00:00"
  },
  "message": "Signal received and queued for processing"
}
```

### Error Response (`422 Unprocessable Content`)

```json
{
    "message": "The event.type field is required.",
    "errors": {
        "event.type": [
            "The event.type field is required."
        ]
    }
}
```
