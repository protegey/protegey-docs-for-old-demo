::callout{icon="i-lucide-arrow-right" color="primary"}
**Signals = ingest.** This API adds events to the entity graph and returns a preliminary risk score. For real-time scoring of raw data without creating entities, use the [Evaluate API](/partners/api-reference/evaluate) instead.
::

The Signals API enables partners to submit fraud indicators to the Protegey network. Each signal is **synchronously validated and scored** — a preliminary risk verdict is returned in the same HTTP response. Async processing (graph linking, entity enrichment, alert generation) continues in the background.

> **Looking for something else?**
> - Real-time scoring without persistence → [Evaluate API](/partners/api-reference/evaluate)
> - Deep entity intelligence → [Assess API](/partners/api-reference/entities#assess)
> - Ingest signals into the graph → [Signals API](/partners/api-reference/signals)

::callout{icon="i-lucide-shield-alert" color="amber"}
**Production Access Required**: You must have active production keys to post live signals. Sandbox signals do not affect network scores.
::

## Endpoint

```http
POST /api/v1/signals
```

### Headers

| Header            | Value                     | Required    |
| ----------------- | ------------------------- | ----------- |
| `Content-Type`    | `application/json`        | Yes         |
| `X-Centry-Key`    | `cen_live_sk_...`         | Yes         |
| `Idempotency-Key` | Unique key (max 64 chars) | Recommended |

## UFES v2 — The Only Supported Format

All new integrations must use **UFES v2** (`schema_version: "2.0"`). Legacy and v1 formats have been removed from the ingestion pipeline.

### Required Fields

| Field                     | Type    | Description                                                                  |
| ------------------------- | ------- | ---------------------------------------------------------------------------- |
| `schema_version`          | `"2.0"` | Must be exactly `"2.0"`                                                      |
| `event_type`              | string  | Free-form event type (e.g. `MOBILE_MONEY_SEND`, `LOGIN_FAILURE`, `SIM_SWAP`) |
| `timestamp`               | string  | ISO 8601 datetime                                                            |
| `source`                  | object  | Submission source metadata                                                   |
| `source.confidence_score` | number  | 0.0–1.0 — your confidence this event is fraud-relevant                       |
| `primary_actor`           | object  | The entity performing the action                                             |
| `primary_actor.entity_id` | string  | Your internal identifier for this entity                                     |

::callout{icon="i-lucide-info" color="blue"}
`event_category` is **optional** — it is automatically derived from `event_type` when omitted (e.g. `TRANSFER` → `transaction`, `LOGIN` → `auth`, `SIM_SWAP` → `auth`). Supply it explicitly only when the auto-derivation is wrong for your use case.
::

### Full Schema

```typescript
interface UFESv2Signal {
  // ── Envelope (required) ──────────────────────────────────────────
  schema_version: "2.0";
  event_type: string; // e.g. "MOBILE_MONEY_SEND", "SIM_SWAP", "LOGIN_FAILURE"
  timestamp: string; // ISO 8601

  // ── Envelope (optional) ──────────────────────────────────────────
  event_category?: "transaction" | "auth" | "kyc" | "fraud_signal" | "system";
  flow_type?: "payment" | "auth" | "kyc"; // auto-inferred from event_category if omitted
  trace_id?: string; // your cross-system trace ID

  // ── Source ───────────────────────────────────────────────────────
  source: {
    confidence_score: number; // 0.0–1.0, required
    integration_channel?: "api" | "batch" | "stream";
    partner_user_id?: string; // your internal user reference
    ip_address?: string; // submitting user's IP — feeds IMPOSSIBLE_TRAVEL detector
  };

  // ── Primary actor (required — one plaintext identifier required) ─
  primary_actor: {
    entity_id?: string; // your stable internal ID for this actor
    entity_type?: "individual" | "business" | "account" | "device";
    display_name?: string;

    // ── Plaintext identifiers (submit as-is; Protegey normalizes + hashes) ──
    // At least one of the following is required.
    phone?: string; // E.164 recommended (e.g. "+233241234567"); spaces stripped
    email?: string; // any casing; trimmed + lowercased server-side
    account?: string; // any account reference; trimmed + lowercased server-side
    national_id?: string; // any casing; uppercased + spaces stripped server-side

    // ── Secondary identifiers (all plaintext → all hashed server-side) ────
    identifiers?: {
      msisdn?: string; // alias for phone
      bvn?: string; // 11-digit Bank Verification Number (Nigeria)
      tin?: string; // Tax Identification Number
      passport_number?: string;
      driver_license?: string;
      voter_id?: string;
      pan?: string; // Payment card number (13–19 digits)
      iban?: string;
      wallet_address?: string;
      name?: string; // display name — lowercased + collapsed spaces
      region?: string; // ISO 3166-1 alpha-2 country code (e.g. "GH")
      sim_changed_at?: string; // ISO 8601 — feeds SIM_SWAP_PROXIMITY detector
    };

    // ── Device ────────────────────────────────────────────────────────────
    device?: {
      fingerprint?: string; // opaque fingerprint (max 255 chars) — feeds NEW_DEVICE_ACCESS
      ip_address?: string; // device IP
      user_agent?: string; // raw UA string (max 512 chars)
      imei?: string; // 15 digits — hashed server-side
      sim_iccid?: string; // 18–20 digits — hashed server-side
    };
    risk_flags?: string[]; // e.g. ["high_velocity", "new_device"]
  };

  // ── Related entities (optional) ──────────────────────────────────
  related_entities?: Array<{
    entity_id: string;
    entity_type?: string;
    relationship_type?:
      | "sender"
      | "receiver"
      | "beneficiary"
      | "shared_device"
      | "linked_account"
      | "mule"
      | "director"
      | "proxy";
  }>;

  // ── Event payload (optional, category-specific data) ─────────────
  event_payload?: {
    amount?: number;
    currency?: string;
    reference_id?: string;
    geo_location?: { lat: number; lng: number };
    [key: string]: any;
  };

  // ── Partner intelligence blocks (optional, audit trail only) ─────
  risk_intelligence?: {
    risk_score?: number;
    risk_level?: "low" | "medium" | "high" | "critical";
    risk_factors?: string[];
    model_version?: string;
  };
  compliance_context?: {
    jurisdiction?: string;
    regulatory_flags?: string[];
    screening_results?: Record<string, any>[];
  };

  // ── Partner decision (v2.1) ───────────────────────────────────────
  // Capture the decision your system made at signal time.
  // decision_type distinguishes human review from automated rules —
  // critical for model training and audit trails.
  partner_decision?: {
    decision?: "approve" | "deny" | "review" | "block" | "escalate";
    decision_type?: "manual" | "automated" | "hybrid";
    timestamp?: string; // ISO 8601 — enables detection latency metrics
    rationale?: string;
    policy_id?: string;
  };

  // ── Outcome feedback (v2.1) ──────────────────────────────────────
  // Submit at signal time if already known, or later via PATCH /signals/{id}/outcome.
  // These two fields are intentionally separate: a "blocked" transaction is not
  // necessarily fraud, and a "success" is not necessarily legitimate.
  event_outcome?: "success" | "failure" | "blocked" | "reversed"; // operational
  event_outcome_source?: "partner" | "system" | "regulator";
  fraud_outcome?: "fraud" | "legitimate" | "suspected" | "unknown"; // analytical
  fraud_type?: "account_takeover" | "scam" | "laundering" | "mule" | "unknown";

  // ── Case linkage (v2.1) ───────────────────────────────────────────
  // Link this signal to a case for outcome propagation in Phase 3.
  case_id?: string; // UUID of the linked FraudCase

  metadata?: Record<string, any>;
}
```

### Event Category Auto-Derivation

When `event_category` is omitted, Protegey derives it from `event_type`:

| `event_category` | Auto-mapped `event_type` values                                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth`           | `LOGIN`, `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `SIM_SWAP`, `ACCOUNT_TAKEOVER`, `ACCOUNT_UPDATE`, `MFA_BYPASS`, `PASSWORD_RESET`, `DEVICE_ANOMALY` |
| `transaction`    | `PAYMENT`, `TRANSFER`, `WITHDRAWAL`, `MOBILE_MONEY_SEND`, `CARD_FRAUD`, `PAYMENT_FRAUD`                                                       |
| `kyc`            | `ACCOUNT_CREATE`, `ACCOUNT_OPENING`, `KYC_CHECK`, `DOCUMENT_VERIFY`, `IDENTITY_THEFT`                                                         |
| `fraud_signal`   | Everything else                                                                                                                               |

## Detector-Required Fields

Protegey runs **five detectors** on every signal. Some detectors require specific fields to fire. Providing these fields maximizes the quality of your risk assessment.

| Detector                     | Required Field          | Where to Provide It                                   |
| ---------------------------- | ----------------------- | ----------------------------------------------------- |
| `RAPID_TRANSACTION_VELOCITY` | Actor ID + past signals | `primary_actor.entity_id`                             |
| `LARGE_OUTLIER_TRANSACTION`  | Transaction amount      | `event_payload.amount` + `event_payload.currency`     |
| `SIM_SWAP_PROXIMITY`         | SIM change timestamp    | `primary_actor.identifiers.sim_changed_at` (ISO 8601) |
| `NEW_DEVICE_ACCESS`          | Device fingerprint      | `primary_actor.device.fingerprint`                    |
| `IMPOSSIBLE_TRAVEL`          | Submitting IP address   | `source.ip_address`                                   |

::callout{icon="i-lucide-zap" color="primary"}
**Enrich every signal**: Providing `source.ip_address`, `primary_actor.device.fingerprint`, and `primary_actor.identifiers.sim_changed_at` wherever applicable significantly increases detection accuracy — especially for SIM-swap and account-takeover patterns common in African mobile money fraud.
::

## Server-Side Privacy Processing

Protegey **never stores plaintext PII**. Submit identifiers as plaintext — the server normalizes and hashes them automatically using **HMAC-SHA256 with the shared network key** before any storage or graph linking occurs.

::callout{icon="i-lucide-shield-alert" color="red"}
**Do NOT pre-hash identifiers.** Submitting a pre-hashed value causes a double-hash on the server, breaking cross-institution entity matching. Always submit raw, unmodified identifiers.
::

### Automatic Normalization

The server applies type-specific normalization before hashing:

| Type           | Normalization Applied        | Example Input          | Canonical Form     |
| -------------- | ---------------------------- | ---------------------- | ------------------ |
| Phone (MSISDN) | E.164 via libphonenumber     | `0244 123 456`         | `+233244123456`    |
| Email          | lowercase + trim             | `User@Example.COM `    | `user@example.com` |
| Account        | lowercase + trim             | `ACC-00123456`         | `acc-00123456`     |
| National ID    | uppercase + strip whitespace | `gh 12 34`             | `GH1234`           |
| BVN            | digits only, 11 chars        | `123-456-789-01`       | `12345678901`      |
| PAN            | digits only, 13–19 chars     | `4111 1111 1111 1111`  | `4111111111111111` |
| IMEI           | digits only, 15 chars        | `35-387923-456789-0`   | `353879234567890`  |

Each normalized value is prefixed with its type before hashing (e.g. `phone:+233244123456`), so two different identifier types that normalize to the same string never produce the same hash.

## Response

### Success (`201 Created`)

Signal ingestion is **synchronous** — a preliminary risk assessment runs inline and is returned immediately. This is a fast ingest-time score based on available entity data. For a full assessment with complete confidence and explanations, use `POST /risk/assess` with the entity UUID.

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_type": "PAYMENT_FRAUD",
    "timestamp": "2026-03-20T10:00:00Z",
    "risk_score": 0.7821,
    "risk_level": "high",
    "detectors_triggered": [
      "RAPID_TRANSACTION_VELOCITY"
    ],
    "taxonomy": "payment.structuring",
    "normalization": {
      "event_type_submitted": "momo_send",
      "event_type_resolved": "PAYMENT_FRAUD",
      "event_type_status": "aliased",
      "match_confidence": 0.85,
      "taxonomy_applied": "payment.mobile_money"
    }
  }
}
```

`ingestion_quality` is included when the payload is missing high-value detector fields. See [Ingestion Quality](#ingestion-quality) below.

### Risk Levels

| `risk_level` | `risk_score` Range | Recommended Action                      |
| ------------ | ------------------ | --------------------------------------- |
| `critical`   | 0.81 – 1.00        | Block immediately, open investigation   |
| `high`       | 0.51 – 0.80        | Require additional verification or hold |
| `medium`     | 0.21 – 0.50        | Step-up authentication or manual review |
| `low`        | 0.00 – 0.20        | Allow — low fraud signal                |

### Detectors

| Detector ID                  | What It Detects                                              |
| ---------------------------- | ------------------------------------------------------------ |
| `RAPID_TRANSACTION_VELOCITY` | Unusually high transaction frequency in a short window       |
| `LARGE_OUTLIER_TRANSACTION`  | Transaction amount far above the actor's historical baseline |
| `SIM_SWAP_PROXIMITY`         | High-value transaction within 24h of a SIM change            |
| `NEW_DEVICE_ACCESS`          | Activity from a device fingerprint never seen for this actor |
| `IMPOSSIBLE_TRAVEL`          | Geographic impossibility between consecutive events          |

::callout{icon="i-lucide-info" color="blue"}
**Weighted risk fusion is async.** The `risk_score` in the `201` response is the synchronous ingest-time score (detector layer only). Full weighted fusion — Behavioral (35%) + Network/Graph (40%) + Contextual (15%) + Historical (10%) — runs asynchronously after entity graph linking completes and is delivered via the `signal.ingested` webhook event. This typically completes within 2–5 seconds of ingestion.
::

### Detector Reference

Five detectors run against every signal. Each has specific required fields — missing fields cause the detector to be skipped (not fail).

| Detector ID | Trigger Condition | Required Field(s) |
|-------------|-------------------|-------------------|
| `RAPID_TRANSACTION_VELOCITY` | ≥ 10 transactions/hour for the same entity | `primary_actor.entity_id` |
| `LARGE_OUTLIER_TRANSACTION` | Z-score ≥ 3.0 vs entity's 90-day baseline | `event_payload.amount` + `event_payload.currency` |
| `SIM_SWAP_PROXIMITY` | Device or location change within 2h of a SIM swap event | `primary_actor.identifiers.sim_changed_at` |
| `NEW_DEVICE_ACCESS` | First-seen device fingerprint combined with a high-risk geography | `primary_actor.device.fingerprint` |
| `IMPOSSIBLE_TRAVEL` | Same entity in two countries within 2h | `source.ip_address` (resolver-enriched to geo) |

`detectors_triggered` in the response lists only the detectors that **fired** (met their threshold). All 5 are evaluated regardless.

| `primary_actor.entity_id is required`                                         | UFES v2 payload missing `primary_actor.entity_id`             |
| `event_category must be one of: auth, transaction, kyc, fraud_signal, system` | Invalid category value — or omit entirely for auto-derivation |

## Idempotency

Use the `Idempotency-Key` header to safely retry failed requests without creating duplicate signals.

**Rules:**

- Key must be unique per logical signal (UUID recommended)
- Maximum 64 characters
- Keys are partner-scoped and expire after 24 hours
- `4xx` responses are never cached — retrying a bad payload does not replay a cached error
- On replay, the response includes `X-Idempotency-Replayed: true`

**Example — retry with backoff:**

```javascript
async function submitSignal(payload, idempotencyKey, retries = 3) {
  for (let attempt = 0; attempt < retries; attempt++) {
    try {
      const response = await fetch("https://api.protegey.com/v1/signals", {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "X-Centry-Key": process.env.PROTEGEY_SECRET_KEY,
          "Idempotency-Key": idempotencyKey, // same key on every retry
        },
        body: JSON.stringify(payload),
      });

      if (response.ok) return await response.json();
      if (response.status < 500)
        throw new Error(`Client error: ${response.status}`);

      // 5xx — wait and retry
      await new Promise((r) => setTimeout(r, Math.pow(2, attempt) * 1000));
    } catch (err) {
      if (attempt === retries - 1) throw err;
    }
  }
}

// Generate key once, before the first attempt
const signalKey = crypto.randomUUID();
await submitSignal(payload, signalKey);
```

::callout{icon="i-lucide-info" color="blue"}
**Best practice**: Generate the idempotency key **before** sending the first request. Store it alongside the signal in your system so you can reuse the same key on any retry, regardless of how much time passes.
::

## v2.1 Response Fields

### Normalization Feedback

Every ingestion response includes a `normalization` block showing how your `event_type` was resolved. Use this to catch mismatches early before they accumulate at scale.

```json
{
  "normalization": {
    "event_type_submitted": "momo_send",
    "event_type_resolved": "PAYMENT_FRAUD",
    "event_type_status": "aliased",
    "match_confidence": 0.85,
    "taxonomy_applied": "payment.mobile_money"
  }
}
```

| Field | Description |
|-------|-------------|
| `event_type_submitted` | What your system sent |
| `event_type_resolved` | The canonical UFES event type Protegey mapped it to |
| `event_type_status` | `canonical` · `aliased` · `unknown` |
| `match_confidence` | How reliable the mapping is (see table below) |
| `taxonomy_applied` | The fraud taxonomy category used for scoring |
| `warning` | Present only when `event_type_status` is `unknown` |

**`match_confidence` values:**

| Value | Meaning |
|-------|---------|
| `1.0` | Submitted type is an exact canonical UFES type |
| `0.85` | Mapped via a registered alias (e.g. `sim_swap` → `ACCOUNT_TAKEOVER`) |
| `0.65` | Inferred from `event_category` only — `event_type` itself was unrecognised |
| `0.0` | Unknown — scored with default severity `0.10`. Register the type for accurate scoring |

::callout{icon="i-lucide-alert-triangle" color="amber"}
When `match_confidence` is `0.0`, your signal is scored at a flat `0.10` severity regardless of its actual risk. Register your event types with the Protegey team to unlock proper detection coverage.
::

### Ingestion Quality

When your payload is missing fields that enable specific detectors, the response includes an `ingestion_quality` block. This block is **omitted for complete payloads** — you only see it when there's something to improve.

```json
{
  "ingestion_quality": {
    "completeness_score": 0.60,
    "missing_recommended": [
      "source.ip_address",
      "primary_actor.device.fingerprint",
      "primary_actor.identifiers.sim_changed_at"
    ],
    "improvement_suggestions": [
      {
        "field": "source.ip_address",
        "impact": "high",
        "reason": "required for IMPOSSIBLE_TRAVEL detection"
      },
      {
        "field": "primary_actor.device.fingerprint",
        "impact": "high",
        "reason": "required for NEW_DEVICE_ACCESS detection"
      },
      {
        "field": "primary_actor.identifiers.sim_changed_at",
        "impact": "high",
        "reason": "required for SIM_SWAP_PROXIMITY detection"
      }
    ]
  }
}
```

`completeness_score` is a weighted 0.0–1.0 value. A score below `0.50` means two or more high-impact detectors are blind on this signal.

## Record Outcome

After a fraud verdict is known — days or weeks after the original signal — submit the ground truth. This closes the learning loop and contributes to network-wide model improvement.

```http
PATCH /api/v1/signals/{id}/outcome
```

`{id}` accepts either the Protegey-assigned `signal_id` (UUID from the ingestion response) or your own `trace_id` submitted at ingestion time. Using `trace_id` means you don't need to store Protegey's UUID in your system.

```http
PATCH /api/v1/signals/TXN-2026-03-20-001/outcome   ← trace_id
PATCH /api/v1/signals/9df4a3b1-c2e3-4f56.../outcome ← signal_id
```

**Request body:**

```json
{
  "event_outcome": "blocked",
  "event_outcome_source": "partner",
  "fraud_outcome": "fraud",
  "fraud_type": "scam",
  "outcome_timestamp": "2026-03-20T14:30:00Z"
}
```

| Field | Type | Values |
|-------|------|--------|
| `event_outcome` | string | `success` · `failure` · `blocked` · `reversed` |
| `event_outcome_source` | string | `partner` · `system` · `regulator` |
| `fraud_outcome` | string | `fraud` · `legitimate` · `suspected` · `unknown` |
| `fraud_type` | string | `account_takeover` · `scam` · `laundering` · `mule` · `unknown` |
| `outcome_timestamp` | string (ISO 8601) | When the outcome was confirmed. Must be ≥ signal `created_at`. Defaults to now if omitted. |

::callout{icon="i-lucide-info" color="blue"}
`event_outcome` and `fraud_outcome` are separate dimensions by design. A `blocked` transaction is not necessarily `fraud` — your block rules fire on suspicion, not confirmation. Keeping them separate prevents label pollution in analytics and model training.
::

**Response (`200 OK`):**

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_outcome": "blocked",
    "event_outcome_source": "partner",
    "fraud_outcome": "fraud",
    "fraud_type": "scam",
    "outcome_timestamp": "2026-03-20T14:30:00Z",
    "recorded_at": "2026-03-20T14:31:05Z"
  }
}
```

**Latency metrics** — once `outcome_timestamp` is set, three latency dimensions become SQL-queryable without JSON extraction:

| Metric | Formula |
|--------|---------|
| Detection latency | `partner_decision_at` − `created_at` |
| Human response time | `outcome_timestamp` − `partner_decision_at` |
| End-to-end resolution | `outcome_timestamp` − `created_at` |
