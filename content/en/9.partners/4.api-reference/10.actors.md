---
title: Actor Intelligence API
description: API reference for actor-level intelligence, including transaction history, risk profiles, and network analysis.
---

The Actor Intelligence API provides granular insights into individual actors (phone numbers, email addresses, device fingerprints, etc.) involved in transactions. This complements the Entity Intelligence API by focusing on transaction-level actor analysis rather than entity-level tracking.

::callout{type="info"}
**Feature Gate**: Actor intelligence is available on Professional plans and above. **Access Level**: Read-only.
::

## Authentication

All actor intelligence endpoints require OAuth2 Bearer token authentication:

```bash
Authorization: Bearer YOUR_ACCESS_TOKEN
```

## Rate Limits

- **Actor History**: 120 requests per minute
- **Actor Profile**: 120 requests per minute
- **Related Actors**: 60 requests per minute

---

## Get Actor History

**GET** `/api/v1/actors/{actorHashedId}/history`

Retrieve the transaction history for a specific actor identified by their hashed identifier (phone number, email, device fingerprint, etc.).

### Path Parameters

| Parameter       | Type   | Description                                       |
| --------------- | ------ | ------------------------------------------------- |
| `actorHashedId` | string | Hashed actor identifier (e.g., `hash_0244567890`) |

### Query Parameters

| Parameter | Type    | Required | Default | Description                                      |
| --------- | ------- | -------- | ------- | ------------------------------------------------ |
| `limit`   | integer | No       | 50      | Maximum number of transactions to return (1-200) |

### Request Example

```bash
curl -X GET "https://api.protegey.com/api/v1/actors/hash_0244567890/history?limit=100" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN"
```

**Response Fields**:

| Field                  | Description                                               |
| ---------------------- | --------------------------------------------------------- |
| `id`                   | Signal unique identifier                                  |

| `risk_reasons`         | Array of risk factors detected                            |

| `metadata`             | Additional transaction context                            |
| `created_at`           | Transaction timestamp                                     |

**Status Codes**:

- `200 OK` - Success
- `401 Unauthorized` - Invalid or missing authentication token
- `403 Forbidden` - Partner context required
- `404 Not Found` - Actor not found or no transactions

::callout{type="success"}
**Use Case**: Actor history is ideal for investigating suspicious patterns across multiple transactions. Use this endpoint when drilling down from an alert or case to understand the full transaction timeline for a specific actor.

## Actor Types

Protegey tracks various actor types based on transaction identifiers:

| Actor Type           | Description                 | Example Identifier            |
| -------------------- | --------------------------- | ----------------------------- |
| `phone_number`       | Mobile/phone numbers        | `hash_0244567890`             |
| `email`              | Email addresses             | `hash_email_john@example.com` |
| `device_fingerprint` | Browser/device fingerprints | `fp_a1b2c3d4e5f6`             |
| `account_id`         | User account identifiers    | `hash_account_12345`          |
| `ip_address`         | IP addresses                | `ip_192.168.1.1`              |
| `payment_method`     | Card BIN, wallet ID, etc.   | `hash_payment_4532`           |

::callout{type="info"}
**Privacy Protection**: All actor identifiers are hashed or masked to protect customer privacy while enabling fraud pattern detection.

## Best Practices

### Investigation Workflow

**Comprehensive Actor Investigation**:

```javascript
const actorId = "hash_0244567890";

// 1. Get risk profile overview
const profile = await client.actors.getProfile(actorId);
console.log(`Risk Score: ${profile.data.risk_score}`);
console.log(
  `Total Transactions: ${profile.data.statistics.total_transactions}`,
);

// 2. Review transaction history
const history = await client.actors.getHistory(actorId, { limit: 100 });
const highRiskTransactions = history.data.filter(
  (tx) => tx.risk_level === "high",
);
console.log(`High risk transactions: ${highRiskTransactions.length}`);

// 3. Discover fraud network
const related = await client.actors.getRelated(actorId);
const strongConnections = related.data.filter(
  (r) => r.relationship_strength > 0.8,
);
console.log(`Strong network connections: ${strongConnections.length}`);

// 4. Create case if warranted
if (profile.data.risk_score > 80 && strongConnections.length > 2) {
  await client.cases.create({
    title: `Network fraud investigation: ${actorId}`,
    priority: "critical",
    description: `Coordinated fraud network detected with ${strongConnections.length} related actors`,
  });
}
```

### Pattern Recognition

**Identify Velocity Abuse**:

```javascript
// Get actor profile
const profile = await client.actors.getProfile(actorId);

// Check velocity indicators
if (profile.data.statistics.velocity_last_24h > 10) {
  console.log("Warning: Abnormal transaction velocity detected");

  // Get recent transactions
  const history = await client.actors.getHistory(actorId, { limit: 20 });

  // Analyze time gaps
  const timeGaps = calculateTimeGaps(history.data);
  const avgGap = timeGaps.reduce((a, b) => a + b) / timeGaps.length;

  if (avgGap < 600) {
    // Less than 10 minutes average
    console.log("Critical: Automated attack pattern detected");
  }
}
```

### Network Mapping

**Build Fraud Network Graph**:

```javascript
async function buildFraudNetwork(seedActorId, maxDepth = 2) {
  const network = { nodes: [], edges: [] };
  const visited = new Set();

  async function traverse(actorId, depth) {
    if (depth > maxDepth || visited.has(actorId)) return;
    visited.add(actorId);

    // Get actor profile
    const profile = await client.actors.getProfile(actorId);
    network.nodes.push({
      id: actorId,
      risk_score: profile.data.risk_score,
      transaction_count: profile.data.statistics.total_transactions,
    });

    // Get related actors
    const related = await client.actors.getRelated(actorId);

    for (const rel of related.data) {
      if (rel.relationship_strength > 0.7) {
        // Only strong connections
        network.edges.push({
          from: actorId,
          to: rel.actor_hashed_id,
          type: rel.relationship_type,
          strength: rel.relationship_strength,
        });

        await traverse(rel.actor_hashed_id, depth + 1);
      }
    }
  }

  await traverse(seedActorId, 0);
  return network;
}

// Use for visualization
const network = await buildFraudNetwork("hash_0244567890");
renderNetworkGraph(network); // Visualize with D3.js, vis.js, etc.
```

## Relationship Types

| Type                      | Description                 | Common in Fraud                                        |
| ------------------------- | --------------------------- | ------------------------------------------------------ |
| **shared_device**         | Same device fingerprint     | ✅ Very common - account takeover, credential stuffing |
| **shared_ip_address**     | Same IP address             | ✅ Common - shared infrastructure, bot networks        |
| **shared_account**        | Same account identifier     | ✅ Very common - account compromise                    |
| **shared_payment_method** | Same payment method         | ⚠️ Less common - stolen cards, mule accounts           |
| **shared_email**          | Same email address          | ⚠️ Less common - fake identity clusters                |
| **shared_location**       | Same geographic coordinates | 🔍 Rare - physical fraud rings                         |

::callout{type="warning"}
**False Positive Risk**: Shared IP addresses and devices can occur legitimately (families, internet cafes, VPNs). Always consider relationship strength and additional risk indicators before flagging.

## FAQ

**Q: What's the difference between actors and entities?**
A: Actors are transaction-level identifiers (phone numbers, emails, device fingerprints in individual signals). Entities are persistent profiles that aggregate multiple actor identifiers into unified fraud actor profiles. One entity can represent multiple actor identifiers.

**Q: How are actors hashed?**
A: Actors are hashed using HMAC-SHA256 with your network key before submission. Display identifiers are masked (e.g., `0244******`) for UI presentation. See [PII Hashing](./signals#pii-hashing) for the canonical normalisation rules and code examples.

**Q: Can I see the original (unhashed) actor identifiers?**
A: Only in the Partner Portal with appropriate permissions. API responses use hashed/masked identifiers to protect customer privacy.

**Q: How is relationship strength calculated?**
A: Relationship strength is calculated using graph analysis algorithms considering shared attribute frequency, temporal proximity, transaction patterns, and risk correlations.

**Q: Why do I see actors with no transactions?**
A: Actors may appear in related actor queries even if they haven't transacted directly with your partner, if they share attributes with actors who have.

**Q: Can I block actors programmatically?**
A: Not directly. You can update the associated entity status via the [Entity Intelligence API](./entities) which affects all related actors.
