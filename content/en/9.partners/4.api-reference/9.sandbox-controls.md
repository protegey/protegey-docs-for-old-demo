The Sandbox Controls API provides programmatic access to sandbox environment management, allowing you to reset sandbox data, generate demo signals, and run multi-step fraud simulations for testing and integration validation.

::callout{type="info"}
**Sandbox Only**: All endpoints in this API are **sandbox-exclusive**. They will return `403 Forbidden` if called in production environment. Access level: **Read/Write** (available on all plans).
::

## Authentication

All sandbox control endpoints require OAuth2 Bearer token authentication:

```bash
Authorization: Bearer YOUR_ACCESS_TOKEN
X-Centry-Environment: sandbox
```

::callout{type="warning"}
**Environment Header Required**: You must explicitly set the environment to `sandbox` using the `X-Centry-Environment` header or query parameter `?environment=sandbox`. Sandbox control endpoints will not work in production.
::

## Rate Limits

- **Reset Sandbox**: 10 requests per hour
- **Generate Demo Signals**: 3 requests per hour
- **List Templates**: 60 requests per minute
- **List Scenarios**: 60 requests per minute
- **Run Simulation**: 5 requests per hour

## Reset Sandbox

**POST** `/api/v1/partner/sandbox/reset`

Reset sandbox data with granular control over what gets deleted. This allows you to start fresh or selectively clear specific data types while preserving others.

### Request Body

| Field                 | Type    | Required | Default | Description                       |
| --------------------- | ------- | -------- | ------- | --------------------------------- |
| `reset_signals`       | boolean | No       | false   | Delete all sandbox signals        |
| `reset_entities`      | boolean | No       | false   | Delete all sandbox fraud entities |
| `reset_relationships` | boolean | No       | false   | Delete all entity relationships   |
| `reset_alerts`        | boolean | No       | false   | Delete all sandbox alerts         |
| `preserve_api_keys`   | boolean | No       | true    | Keep API keys (recommended)       |
| `reset_audit_logs`    | boolean | No       | false   | Delete sandbox audit logs         |
| `reset_usage`         | boolean | No       | false   | Reset usage metrics               |

::callout{type="success"}
**Smart Defaults**: If you call this endpoint with an empty body `{}`, nothing is deleted. This is a safety mechanism requiring explicit opt-in for each data type.
::

### Request Examples

**Full Reset (everything except API keys)**:

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/reset" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "reset_signals": true,
    "reset_entities": true,
    "reset_relationships": true,
    "reset_alerts": true,
    "reset_audit_logs": true,
    "reset_usage": true,
    "preserve_api_keys": true
  }'
```

**Reset Signals Only** (keep cases, entities, alerts):

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/reset" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "reset_signals": true
  }'
```

**Reset for New Test Cycle** (clear signals and alerts, keep entities):

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/reset" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "reset_signals": true,
    "reset_alerts": true,
    "reset_usage": true
  }'
```

### Response Example

**Success (200 OK)**:

```json
{
  "success": true,
  "message": "Sandbox data has been reset successfully."
}
```

**Status Codes**:

- `200 OK` - Reset completed successfully
- `401 Unauthorized` - Invalid or missing authentication token
- `403 Forbidden` - Not in sandbox environment
- `429 Too Many Requests` - Rate limit exceeded (10 requests/hour)
- `500 Internal Server Error` - Reset operation failed

::callout{type="danger"}
**Irreversible Operation**: Sandbox reset is permanent and cannot be undone. Deleted data cannot be recovered. Use with caution.
::

## Generate Demo Signals

**POST** `/api/v1/partner/sandbox/generate-demo-signals`

Generate realistic demo signals from predefined templates for testing fraud detection rules, case management workflows, and integration logic.

### Request Body

| Field       | Type    | Required | Default | Description                                          |
| ----------- | ------- | -------- | ------- | ---------------------------------------------------- |
| `template`  | string  | Yes      | -       | Template name (e.g., `transaction/account_takeover`) |
| `count`     | integer | No       | 20      | Number of signals to generate (1-100)                |
| `overrides` | object  | No       | {}      | Variable overrides for template customization        |

### Request Examples

**Basic Demo Signal Generation**:

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/generate-demo-signals" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "template": "transaction/account_takeover",
    "count": 50
  }'
```

**With Variable Overrides** (force specific phone number):

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/generate-demo-signals" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "template": "transaction/stolen_financials",
    "count": 10,
    "overrides": {
      "PHONE_NUMBER": "0244123456",
      "TRANSACTION_AMOUNT": 50000,
      "COUNTRY_CODE": "US"
    }
  }'
```

**Generate Critical Risk Signals** (for alert testing):

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/generate-demo-signals" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "template": "transaction/account_takeover",
    "count": 20,
    "overrides": {
      "TRANSACTION_AMOUNT": 75000,
      "source_confidence": 0.95
    }
  }'
```

### Response Example

**Success (200 OK)**:

```json
{
  "success": true,
  "data": {
    "signals_generated": 50,
    "template": "transaction/account_takeover",
    "signal_ids": ["sig_abc123", "sig_def456", "sig_ghi789", "..."]
  },
  "message": "Successfully generated 50 demo signals"
}
```

**Rate Limit Exceeded (429)**:

```json
{
  "success": false,
  "message": "Demo generation limit exceeded. Please wait an hour or reset your sandbox."
}
```

**Status Codes**:

- `200 OK` - Signals generated successfully
- `401 Unauthorized` - Invalid authentication
- `403 Forbidden` - Not in sandbox environment
- `422 Unprocessable Entity` - Invalid template name or count
- `429 Too Many Requests` - Rate limit exceeded (3 requests/hour)
- `500 Internal Server Error` - Signal generation failed

### Rate Limiting

Demo signal generation is rate-limited to **3 requests per hour** to ensure system stability. If you need to generate more signals:

1. **Reset your sandbox** (clears the rate limit counter)
2. **Use the CLI simulator** (no rate limits): `php artisan centry:simulate-signals`
3. **Wait for the rate limit window to expire** (1 hour from first request)

::callout{type="info"}
**Why Rate Limits?**: Demo signal generation triggers the full fraud detection pipeline (scoring, alerts, entity linking, etc.). Rate limits prevent sandbox abuse and ensure fair resource allocation.
::

## Run Simulation

**POST** `/api/v1/partner/sandbox/simulate`

Execute a multi-step fraud scenario simulation. Scenarios generate coordinated sequences of related signals that unfold over time, mimicking real-world attack patterns.

::callout{type="warning"}
**Planned Feature**: Multi-step scenario simulation is currently under development (Phase 2, Q2 2026). This endpoint will return a feature unavailable error until implementation is complete.
::

### Request Body

| Field         | Type   | Required | Description                                                                   |
| ------------- | ------ | -------- | ----------------------------------------------------------------------------- |
| `scenario_id` | string | Yes      | Scenario identifier (from `/scenarios` endpoint)                              |
| `mode`        | string | No       | Execution mode: `realtime`, `fast-forward`, `immediate` (default: `realtime`) |
| `overrides`   | object | No       | Scenario variable overrides                                                   |

### Request Example

```bash
curl -X POST "https://api.protegey.com/api/v1/partner/sandbox/simulate" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "X-Centry-Environment: sandbox" \
  -H "Content-Type: application/json" \
  -d '{
    "scenario_id": "sim_swap_drainage",
    "mode": "fast-forward",
    "overrides": {
      "SCENARIO_PHONE": "0244123456"
    }
  }'
```

### Response Example

**Success (200 OK)**:

```json
{
  "success": true,
  "data": {
    "batch_id": "scenario_1738598400_abc123"
  },
  "message": "Simulation started successfully."
}
```

**Feature Not Available (501 Not Implemented)**:

```json
{
  "success": false,
  "message": "Multi-step scenario simulation is not yet available. Expected: Q2 2026."
}
```

**Status Codes**:

- `200 OK` - Simulation started successfully
- `401 Unauthorized` - Invalid authentication
- `403 Forbidden` - Not in sandbox environment
- `422 Unprocessable Entity` - Invalid scenario ID
- `429 Too Many Requests` - Rate limit exceeded (5 requests/hour)
- `500 Internal Server Error` - Simulation failed to start
- `501 Not Implemented` - Feature not yet available

## Best Practices

### Sandbox Testing Workflow

**Recommended Integration Testing Flow**:

```javascript
const client = new ProtegeyClient({ apiKey: "YOUR_SANDBOX_KEY" });

// 1. Start with clean slate
await client.sandbox.reset({
  reset_signals: true,
  reset_alerts: true,
  reset_entities: true,
  preserve_api_keys: true,
});

// 2. Generate test data
await client.sandbox.generateDemoSignals({
  template: "transaction/account_takeover",
  count: 50,
});

// 3. Test your integration logic
const signals = await client.transactionMonitoring.list();
for (const signal of signals.data) {
  await processSignal(signal);
}

// 4. Verify results
const cases = await client.cases.list();
const alerts = await client.alerts.list();

// 5. Clean up after testing
await client.sandbox.reset({ reset_signals: true });
```

### Template Selection Strategy

**Choose templates based on test objectives**:

| Test Objective          | Recommended Template                        | Why                                           |
| ----------------------- | ------------------------------------------- | --------------------------------------------- |
| Alert threshold testing | `transaction/account_takeover`              | Generates high-risk signals (10% critical)    |
| Velocity rule testing   | `transaction/stolen_financials` + overrides | Use same phone number across signals          |
| Case management testing | `transaction/synthetic_identity`            | Complex scenarios requiring investigation     |
| Entity linking testing  | `identity/phone_verification_failure`       | Creates entity profiles with multiple signals |
| Cross-border detection  | Any template + `COUNTRY_CODE` override      | Force cross-border transactions               |

### Variable Override Examples

**Test Velocity Checks** (same actor, multiple transactions):

## Error Handling

### Common Error Codes

| Status Code                 | Error                        | Cause                            | Solution                                   |
| --------------------------- | ---------------------------- | -------------------------------- | ------------------------------------------ |
| `403 Forbidden`             | `Not in sandbox environment` | Called from production           | Add `X-Centry-Environment: sandbox` header |
| `422 Unprocessable Entity`  | `Invalid template`           | Template name doesn't exist      | List available templates first             |
| `422 Unprocessable Entity`  | `Count out of range`         | Count < 1 or > 100               | Use count between 1-100                    |
| `429 Too Many Requests`     | `Rate limit exceeded`        | Too many requests in time window | Wait or reset sandbox                      |
| `500 Internal Server Error` | `Reset operation failed`     | Database transaction failed      | Retry or contact support                   |

### Example Error Response

**Not in Sandbox Environment**:

```json
{
  "success": false,
  "message": "Demo signal generation is only available in sandbox mode"
}
```

**Invalid Template**:

```json
{
  "success": false,
  "message": "Template 'invalid_template' not found"
}
```

**Rate Limit Exceeded**:

```json
{
  "success": false,
  "message": "Demo generation limit exceeded. Please wait an hour or reset your sandbox."
}
```

## FAQ

**Q: What's the difference between demo signals and regular signals?**
A: Demo signals are tagged with `generated_by: centry_demo` metadata and follow predefined templates with dynamic risk profiling. They're identical to regular signals in processing but are clearly marked for testing purposes.

**Q: Can I generate more than 100 signals at once?**
A: No, the limit is 100 per request. For higher volume testing, make multiple requests (subject to rate limits) or use the CLI simulator: `php artisan centry:simulate-signals`.

**Q: Will resetting my sandbox affect my production data?**
A: No. Sandbox and production environments are physically separated at the database schema level. Sandbox operations never affect production data.

**Q: Can I customize signal templates?**
A: Not via API currently. You can use `overrides` to customize template variables on a per-request basis. Custom templates can be added to `storage/app/signal-templates/` (requires backend access).

**Q: Why is there a rate limit on demo signal generation?**
A: Demo signal generation triggers the full fraud detection pipeline (scoring, entity linking, alert generation, etc.). Rate limits ensure fair resource allocation and prevent sandbox abuse.

**Q: How long does it take to generate signals?**
A: Generation is synchronous and typically completes in 2-5 seconds for 20-50 signals. The response includes all generated signal IDs.

**Q: Can I schedule recurring demo signal generation?**
A: Not directly via API. You can build a scheduler using your preferred tool (cron, AWS EventBridge, etc.) that calls the generation endpoint. Be mindful of rate limits.

**Q: What happens if I hit the rate limit?**
A: You'll receive a `429 Too Many Requests` response. You can either wait for the rate limit window to expire (1 hour) or reset your sandbox (which clears the rate limit counter).

**Q: Are multi-step scenarios available yet?**
A: Not yet. Multi-step scenario simulation is planned for Q2 2026. Currently, you can simulate multi-step patterns manually by calling `generateDemoSignals` multiple times with consistent `overrides`.
