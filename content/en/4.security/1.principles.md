Security is not just a feature of Protegey; it is the fundamental premise of our existence. Regulated institutions cannot participate in a collective defense network if that network introduces new vulnerabilities.

This document outlines our "Zero Trust, Maximum Privacy" architecture.

## 1. Encryption Standards

We employ defense-in-depth encryption strategies that exceed industry standards.

### Data at Rest

- **Algorithm**: AES-256-GCM.
- **Key Management**: Granular key rotation with separate keys for disjoint datasets.
- **Scope**: All persistent storage, including backups and logs.

### Data in Transit

- **Protocol**: TLS 1.3 only (we do not support legacy TLS 1.0/1.1 or insecure cipher suites).
- **Certificate Pinning**: Mobile SDKs enforce certificate pinning to prevent MitM attacks.
- **HSTS**: Strict Transport Security is enforced for all web endpoints.

### Application-Layer Encryption

For highly sensitive fields (like PII used for matching), we perform application-level encryption _before_ the data touches the database layer, ensuring that even a database administrator cannot read the raw values.

## 2. Data Isolation Model

Protegey implements **physical data separation** at the database level, not just logical isolation. This provides defense-in-depth against data leakage.

### The Problem with Logical Isolation

Traditional multi-tenant systems use logical isolation (WHERE partner_id = X). Vulnerabilities:

- SQL injection can bypass WHERE clauses
- Application bugs can omit scoping conditions
- ORM misconfiguration can expose cross-tenant data
- Database admin errors can leak data

### The Protegey Solution: Physical Schema Isolation

**PostgreSQL Schema-Level Separation**:

```
PostgreSQL Database
├── public schema (Production + Shared)
│   ├── signals (production partner data)
│   ├── fraud_entities (production partner data)
│   ├── fraud_cases (production partner data)
│   ├── users (shared - RBAC)
│   ├── partners (shared - organizations)
│   └── subscriptions (shared - billing)
│
└── sandbox schema (Sandbox Environment)
    ├── signals (sandbox partner data)
    ├── fraud_entities (sandbox partner data)
    ├── fraud_cases (sandbox partner data)
    └── [all partner-scoped tables duplicated]
```

**Security Benefits**:

1. **Physical Separation**: Sandbox data cannot leak into production (different schema)
2. **Automatic Enforcement**: PostgreSQL `search_path` prevents cross-schema queries
3. **Defense in Depth**: Even if application code is buggy, database enforces separation
4. **Easy Auditing**: Schema-level access logs show what data was accessed
5. **Performance Isolation**: Sandbox queries don't impact production performance

### Context-Aware Execution

Every operation executes within an immutable **CentryContext**:

```php
CentryContext {
  environment: 'production' | 'sandbox'
  partner_uuid: string          // Partner identity
  request_id: string            // Tracing identifier
  schema: 'public' | 'sandbox'  // Derived from environment
}
```

**Context Enforcement Flow**:

```
1. HTTP Request arrives
   ↓
2. Authentication (verify API key/session)
   ↓
3. Resolve CentryContext
   - Detect environment (sandbox/production)
   - Extract partner UUID
   - Generate request ID
   ↓
4. Enforce Schema Isolation
   - SET search_path TO {schema}, public
   - Update permission table names
   - Mark schema as enforced
   ↓
5. Execute Application Code
   - All queries use correct schema automatically
   - Partner UUID scoping applied
   ↓
6. Return Response
   - Context preserved in logs
```

**Fail-Fast Validation**:

```php
// Context required before any database operation
CentryContext::assertBound(); // Throws if not bound

// Get context or fail
$context = CentryContext::getOrFail();

// All queries automatically scoped
Signal::where('partner_uuid', $context->partnerUuid())->get();
// Reads from: {schema}.signals WHERE partner_uuid = X
```

**Queue Job Context Preservation**:

```php
// Context captured at dispatch time
class ProcessFraudSignal extends ContextAwareJob {
    public function __construct(private string $signalId) {
        parent::__construct(); // Captures current context
    }

    protected function perform(): void {
        // Context automatically restored in worker
        // Queries use correct schema
        $signal = Signal::find($this->signalId);
    }
}
```

### Multi-Tenant Scoping

**Partner UUID Enforcement**:

- Every API request authenticated to specific partner
- All database queries include `partner_uuid` filter
- Cross-partner queries explicitly forbidden
- Automatic query scoping via middleware

**Schema + UUID = Double Protection**:

```sql
-- Request from Sandbox Partner A
SET search_path TO sandbox, public;

SELECT * FROM signals
WHERE partner_uuid = 'partner-a-uuid'
AND risk_score >= 80;

-- Returns only:
-- 1. Sandbox data (schema enforcement)
-- 2. Partner A's data (UUID enforcement)
-- 3. High-risk signals (application filter)
```

### Data Segregation Guarantees

**What's Isolated**:

- ✅ Fraud signals (per-partner, per-environment)
- ✅ Entity profiles (per-partner, per-environment)
- ✅ Cases and investigations (per-partner)
- ✅ Alerts (per-partner)
- ✅ Transaction monitoring data (per-partner)
- ✅ Analytics and dashboards (per-partner)

**What's Shared** (by design):

- ✅ Users and authentication (RBAC)
- ✅ Partner organization settings
- ✅ Subscriptions and billing
- ✅ Roles and permissions (Spatie, public schema)

**What's Aggregated** (privacy-preserving):

- ✅ Global fraud patterns (anonymized)
- ✅ Risk scoring models (no raw PII)
- ✅ Network intelligence (hashed identifiers)

### Aggregation vs. Exposure

While the _intelligence_ (scores, patterns) is derived from aggregated network data, the _raw signals_ submitted by Partner A remain invisible to Partner B.

- **Partner A** sends: "User X committed fraud."
- **Partner B** asks: "Is User X risky?"
- **Protegey** answers: "Yes, high risk due to network history." (Source is never revealed).

**Privacy-Preserving Aggregation**:

```
Raw Signal (Partner A only):
  actor: "hash_0244567890"
  transaction: GHS 15,000
  device: "d3v1c3-f1ng3rpr1nt"

Aggregated Pattern (Network-wide):
  actor_hash: "hash_0244567890"
  fraud_count: 3
  avg_risk_score: 87
  linked_entities: 7

  // NO raw transaction amounts
  // NO partner identities
  // NO specific transaction details
```

## 2a. Context Validation & Security

### Environment Validation

**Strict Environment Enforcement**:

- Only two valid environments: `production`, `sandbox`
- Invalid environment string throws exception
- No environment = default to `production` (safe default)
- Environment immutability (cannot change mid-request)

**Partner UUID Validation**:

```php
// Reject invalid UUIDs
if ($partnerUuid !== null && !Str::isUuid($partnerUuid)) {
    throw new InvalidArgumentException(
        "Invalid partner UUID format: {$partnerUuid}"
    );
}
```

### Request Tracing

**Unique Request IDs**:

- Every request assigned unique UUID
- Request ID flows through entire request lifecycle
- Appears in all logs for correlation
- Included in error responses for support

**Distributed Tracing**:

```
HTTP Request: req_abc123
  ↓
Job Dispatch: req_abc123 (context serialized)
  ↓
Queue Worker: req_abc123 (context restored)
  ↓
Webhook Delivery: req_abc123 (context in payload)
```

### Schema Enforcement Security

**Middleware Order Critical**:

```php
// Kernel.php middleware stack
protected $middlewareGroups = [
    'api' => [
        'throttle:api',
        ResolveCentryContext::class,      // 1. FIRST: Resolve context
        EnforceSchemaIsolation::class,    // 2. SECOND: Enforce schema
        'auth:api',                        // 3. Then authentication
        // ... rest of middleware
    ],
];
```

**Why Order Matters**:

- Context must exist before authentication queries
- Schema must be set before RBAC permission checks
- All database queries must use correct schema

**Idempotent Schema Enforcement**:

```php
// Only set search_path once
if (app()->has('schema.enforced')) {
    return; // Already enforced, skip
}

DB::statement("SET search_path TO {$schema}, public");
app()->instance('schema.enforced', true);
```

### Sandbox Safety

**Production Guards**:

```php
// Demo signal generation
if (!$context->isSandbox()) {
    throw new UnauthorizedException(
        'Demo signal generation only available in sandbox'
    );
}

// Reset functionality
if (!$context->isSandbox()) {
    throw new UnauthorizedException(
        'Reset only available in sandbox'
    );
}
```

**Rate Limiting**:

- Sandbox: 100 requests/minute
- Production: 1000 requests/minute
- Demo generation: 3 requests/hour (sandbox only)

**Metadata Tagging**:

```json
{
  "signal_id": "sig_abc123",
  "metadata": {
    "generated_by": "centry_demo",
    "sandbox_batch_id": "batch_xyz789",
    "environment": "sandbox"
  }
}
```

### Security Monitoring

**Anomaly Detection**:

- Unusual cross-schema query attempts
- Failed context resolution patterns
- Repeated authentication failures
- Suspicious API key usage

**Alerts**:

- Context binding failures (critical)
- Schema enforcement failures (critical)
- Cross-tenant query attempts (critical)
- Unusual access patterns (high)

## 3. Access Control Philosophy

We follow the Principle of Least Privilege (PoLP) for both internal systems and partner access.

### Partner Access

- **API Keys**: Dual-key system (Public ID + Secret Key).
- **Scoped Permissions**: Keys can be restricted to specific permissions (`signals:write`, `queries:read`) and environments.
- **IP Allowlisting**: Partners can restrict API access to specific CIDR blocks.

### Internal Access

- **No Production Write Access**: Developers do not have write access to production databases.
- **Ephemeral Access**: Operational access to production data requires a ticketed, time-bound request with MFA.
- **Audit Logging**: Every internal query is logged, analyzed for anomalies, and bound to a specific employee identity.

## 4. Secure Development Lifecycle (SDLC)

Security is baked into our code, not bolted on.

- **Static Analysis**: Automated SAST scans on every pull request.
- **Dependency Scanning**: Automated monitoring of all third-party libraries for CVEs.
- **Peer Review**: Mandatory code review with specific security checklists.
- **Penetration Testing**: Annual third-party audits and continuous bug bounty program.

## 5. Vulnerability Disclosure

We welcome responsible disclosure from the security research community.

- **Program**: See our `security.txt` or [Vulnerability Disclosure Policy](/en/resources/contact).
- **Safe Harbor**: Researchers acting in good faith are protected from legal action.
