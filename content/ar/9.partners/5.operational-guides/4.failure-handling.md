# الأعطال والخطط البديلة

الموثوقية مسؤولية مشتركة. رغم سعينا إلى وقت تشغيل بنسبة 100%، قد تحدث مشاكل في الشبكة ومهلات انتظار وانقطاعات. تكاملك **يجب** أن يكون صاملًا للأعطال.

## القاعدة الذهبية

> **لا تحجب مستخدمًا شرعيًا بسبب عطل لدى مزود مكافحة الاحتيال.**

إن كانت Protegey API غير قابلة للوصول أو تُعيد خطأ 500، فعلى تطبيقك تطبيق استراتيجية "الفشل المفتوح" أو "الفشل المغلق" وفقًا لشهيتك في المخاطر.

### الاستراتيجية أ: الفشل المفتوح (موصى به)

**السيناريو**: يُسجِّل مستخدم الدخول، وتنتهي مهلة انتظار API.
**الإجراء**: السماح بتسجيل الدخول. تسجيل الخطأ.
**المزايا**: لا احتكاك للمستخدمين الشرعيين.
**العيوب**: احتمال تسلل الاحتيال خلال فترة الانقطاع.

### الاستراتيجية ب: الفشل المغلق

**السيناريو**: يُسجِّل مستخدم الدخول، وتنتهي مهلة انتظار API.
**الإجراء**: حجب تسجيل الدخول أو طلب MFA.
**المزايا**: أقصى قدر من الأمان.
**العيوب**: احتكاك عالٍ؛ قد يتعرض المستخدمون الشرعيون للحجب أو الإحباط.

## قواطع الدارة

نوصي بتطبيق نمط [قاطع الدارة (Circuit Breaker)](https://martinfowler.com/bliki/CircuitBreaker.html):

1. إن فشلت API عدد X من المرات خلال Y ثانية، "تعمل" القاطع.
2. أثناء الفتح، أوقف استدعاء API وأعِد قرارك الافتراضي فورًا (فشل مفتوح/مغلق).
3. بعد Z ثانية، اسمح بطلب اختباري واحد.
4. إن نجح، أغلق القاطع واستأنف التشغيل العادي.

## إعادة المحاولة

### الأمانة الإدارية

- **الاستعلامات (`GET`)**: آمنة لإعادة المحاولة.
- **الإشارات (`POST`)**: غير آمنة للأمانة الإدارية. إعادة محاولة إرسال إشارة فاشلة قد تُنتج تكرارات إن كان الطلب الأصلي نجح فعلًا لكن الاستجابة ضاعت.

### التراجع الأسي

عند استلام `429 Too Many Requests` أو `5xx Server Error`:

1. انتظر 100ms
2. أعِد المحاولة
3. انتظر 200ms
4. أعِد المحاولة
5. انتظر 400ms...

لا تُكرر إعادات المحاولة فورًا بالتتالي؛ هذا يُفاقم المشكلة.
