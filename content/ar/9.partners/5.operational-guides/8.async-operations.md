تمزج Protegey بين المعالجة المتزامنة وغير المتزامنة. أهم العمليات — تقييم المخاطر والكشف وتعيين التصنيف — تعمل **بشكل مضمَّن أثناء استيعاب الإشارة** حتى تحصل على حكم المخاطر في نفس استجابة HTTP. المهام الأثقل اللاحقة (ربط الرسم البياني، فحص AML، إثراء الكيانات) تعمل بشكل غير متزامن في عمال الخلفية.

---

## نظرة عامة

### ما الذي يعمل بشكل متزامن؟

**استيعاب الإشارة** — كل ما تحتاجه لاتخاذ قرار فوري يعمل بشكل مضمَّن:

- التحقق من صحة UFES v2 وتطبيعه
- هندسة الميزات (نقاط z للمعاملات، نوافذ السرعة، جدة الجهاز، المسافة الجغرافية)
- جميع الكواشف الخمسة (RapidVelocity، LargeOutlier، SimSwapProximity، NewDeviceAccess، ImpossibleTravel)
- تقييم المخاطر NUFSS وتعيين التصنيف
- حكم المخاطر مُعاد في استجابة `201`

### ما الذي يعمل بشكل غير متزامن؟

**معالجة ما بعد الإشارة** (بعد إرسال استجابة HTTP):

- ربط الرسم البياني الساخن (HotGraphService — يبني عقدًا وحواف ACTOR/DEVICE/MSISDN)
- فحص الامتثال AML (العقوبات، PEP، قواعد مراقبة المعاملات — للخطة Enterprise فقط)
- ربط الكيانات وتحديثات درجة الثقة
- توليد التنبيهات للإشارات ذات المخاطر العالية/الحرجة
- تسليم webhook حدث `signal.ingested`

**العمليات الجماعية**:

- القرارات الجماعية (ميزة Enterprise)
- تصدير CSV
- عمليات نقل البيانات الكبيرة
- توليد الإشارات الدُّفعي

**التحليلات**:

- تجميع إحصاءات لوحة التحكم
- توليد خريطة المخاطر الحرارية
- حساب مقاييس الأداء

**الإشعارات**:

- تسليم webhook
- إشعارات البريد الإلكتروني
- تنبيهات SMS (إن كانت مُهيَّأة)

### لماذا المعالجة غير المتزامنة؟

**استجابات API سريعة**: تُعيد APIs الاستجابة فورًا دون انتظار المعالجة المعقدة.

**قابلية التوسع**: يمكن توسيع عمال الخلفية بشكل مستقل عن خوادم API.

**الموثوقية**: يمكن إعادة محاولة المهام الفاشلة تلقائيًا مع التراجع الأسي.

**إدارة الموارد**: العمليات المكلفة (نماذج ML، استعلامات الرسم البياني) تعمل في عمال مخصصين.

**الحفاظ على السياق**: تحتفظ المهام بسياق البيئة (sandbox/production) عبر الحدود غير المتزامنة.

## كيف يعمل

### دورة حياة الطلب

```
1. POST /api/v1/signals  (+ Idempotency-Key header)
   ↓
2. Synchronous pipeline  (runs inline, ~50–150ms)
   - UFES v2 validation
   - Feature engineering
   - 5 detectors run
   - NUFSS risk score computed
   - Taxonomy assigned
   ↓
3. 201 Created response  (risk verdict available immediately)
   {
     "signal_id": "...",
     "risk_score": 0.78,
     "risk_level": "high",
     "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"]
   }
   ↓
4. Background processing  (async, ~1–5 seconds)
   - Hot graph linking
   - AML screening (Enterprise)
   - Entity trust score update
   - Alert generation (if risk ≥ threshold)
   ↓
5. Webhook notifications (if endpoint subscribed)
   - signal.ingested  (always, after scoring)
   - alert.created    (if an alert was generated)
```

### بنية قائمة الانتظار

تستخدم Protegey **Laravel Queues** مع أولويات قوائم انتظار متعددة:

| قائمة الانتظار | الأولوية | وقت المعالجة  | حالة الاستخدام                |
| -------------- | -------- | ------------- | ----------------------------- |
| `high`         | الأعلى   | < ثانية واحدة | تنبيهات فورية، عمليات حرجة    |
| `default`      | عادية    | 2-5 ثوانٍ     | معالجة الإشارة، تقييم المخاطر |
| `low`          | منخفضة   | 5-30 ثانية    | التحليلات، العمليات الجماعية  |
| `webhooks`     | عادية    | 1-3 ثوانٍ     | تسليم webhook                 |

**تهيئة العامل**:

```bash
# High-priority queue (low latency)
php artisan queue:work --queue=high --tries=3 --timeout=30

# Default queue (normal processing)
php artisan queue:work --queue=default --tries=3 --timeout=60

# Low-priority queue (bulk operations)
php artisan queue:work --queue=low --tries=2 --timeout=300
```

## الحفاظ على السياق

### التحدي

تعمل مهام قائمة الانتظار بشكل غير متزامن في عمليات عامل منفصلة. دون السياق الصحيح، قد تقوم المهام بما يلي:

- استخدام مخطط قاعدة بيانات خاطئ (sandbox مقابل production)
- الاستعلام عن بيانات شريك خاطئ
- فقدان معلومات تتبع الطلب

### الحل: ContextAwareJob

جميع المهام غير المتزامنة في Protegey تمتد من `ContextAwareJob`، الذي:

1. **يلتقط السياق** عند وقت الإرسال (المُنشئ)
2. **يُسلسِل السياق** للاستمرار في قائمة الانتظار
3. **يستعيد السياق** عند تنفيذ المهمة في العامل
4. **يُطبِّق المخطط** تلقائيًا

**مثال**:

```php
use App\Jobs\ContextAwareJob;

class ProcessFraudSignal extends ContextAwareJob
{
    public function __construct(
        private string $signalId,
        private string $partnerUuid
    ) {
        parent::__construct(); // ⚠️ CRITICAL: Captures context
    }

    protected function perform(): void
    {
        // Context already restored - queries use correct schema
        $signal = Signal::where('id', $this->signalId)
            ->where('partner_uuid', $this->partnerUuid)
            ->firstOrFail();

        // Calculate risk score
        $riskScore = $this->fraudScoringService->calculate($signal);

        // Update signal (uses correct schema automatically)
        $signal->update(['risk_score' => $riskScore]);
    }
}
```

### تدفق السياق

```
HTTP Request (sandbox.protegey.com)
    ↓
    environment: 'sandbox'
    schema: 'sandbox'
    ↓
ProcessFraudSignal::dispatch($signalId)
    ↓ [Job Serialized to Queue]
    {
      "job": "ProcessFraudSignal",
      "data": {
        "signalId": "sig_abc123",
        "contextData": {
          "environment": "sandbox",
          "partner_uuid": "uuid",
          "schema": "sandbox"
        }
      }
    }
    ↓ [Queue Worker Picks Up Job]
    ↓
Job::handle()
    ↓ [Context Restored]
    environment: 'sandbox'
    schema: 'sandbox'
    SET search_path TO sandbox, public
    ↓
perform() executes
    ↓ [All queries use sandbox schema]
```

## توقعات التوقيت

### استيعاب الإشارة

**استجابة API**: ~50–150ms (حكم المخاطر المتزامن)

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_type": "MOBILE_MONEY_SEND",
    "risk_score": 0.78,
    "risk_level": "high",
    "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
    "taxonomy": "mobile_money_fraud"
  }
}
```

**معالجة الخلفية** (1–5 ثوانٍ بعد الاستجابة):

- ربط الرسم البياني الساخن: < ثانية واحدة
- فحص AML: 1–3 ثوانٍ (للخطة Enterprise فقط)
- توليد التنبيهات: < ثانية واحدة

**إشعار Webhook** (بعد معالجة الخلفية):

```json
{
  "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
  "event_type": "MOBILE_MONEY_SEND",
  "event_category": "transaction",
  "risk_score": 0.78,
  "risk_level": "high",
  "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
  "taxonomy": "mobile_money_fraud"
}
```

(مُسلَّم مع ترويسة `X-Centry-Event: signal.ingested`)

### العمليات الجماعية

**القرارات الجماعية** (Enterprise):

- استجابة API: < 500ms
- المعالجة: ~100ms لكل إشارة
- 100 إشارة: ~10 ثوانٍ إجمالاً
- webhook عند الاكتمال

**تصدير CSV**:

- استجابة API: < 200ms (تُعيد معرف التصدير)
- المعالجة: 1-30 ثانية (حسب الحجم)
- webhook مع رابط التحميل عند الجاهزية

**توليد الإشارات الدُّفعي** (Sandbox):

- استجابة API: < 500ms
- المعالجة: ~200ms لكل إشارة
- 20 إشارة: ~4 ثوانٍ إجمالاً
- تطبيق توزيع ملف تعريف المخاطر أثناء التوليد

### التحليلات

**إحصاءات لوحة التحكم**:

- محفوظة مؤقتًا لمدة 5 دقائق
- عند انتهاء الذاكرة المؤقتة: 2-5 ثوانٍ للحساب
- التحديثات الفورية غير متاحة (استخدم webhooks)

**تحليلات السلاسل الزمنية**:

- تُحسب عند الطلب
- نطاق 30 يومًا: 1-3 ثوانٍ
- نطاق 90 يومًا: 3-8 ثوانٍ

## التحقق من حالة المهمة

### الطريقة الأولى: Webhooks (موصى بها)

تهيئة webhooks لاستقبال إشعارات عند اكتمال العمليات غير المتزامنة:

```typescript
// 1. Register a webhook endpoint in Partner Portal
// Settings > Integrations > Webhooks

// 2. Subscribe to relevant events
const events = [
  "signal.ingested", // fired after async post-processing completes
  "alert.created", // fired when a new fraud alert is generated
  "case.created",
  "case.status_changed",
];

// 3. Handle webhook in your application
app.post("/webhooks/protegey", express.json(), (req, res) => {
  const event = req.headers["x-centry-event"];
  const payload = req.body;

  switch (event) {
    case "signal.ingested":
      // Confirm risk scores post-graph-linking; trigger downstream enrichment
      console.log("Signal post-processed:", payload.signal_id);
      console.log("Risk score:", payload.risk_score);
      break;

    case "alert.created":
      // Route to analyst queue or PagerDuty
      if (payload.severity === "critical") {
        triggerPagerDuty(payload);
      }
      break;
  }

  res.status(200).send("OK");
});
```

### الطريقة الثانية: الاستطلاع

استطلاع API للتحقق من اكتمال المعالجة:

```typescript
async function waitForSignalProcessing(signalId: string) {
  let attempts = 0;
  const maxAttempts = 20; // 20 seconds max
  const interval = 1000; // 1 second

  while (attempts < maxAttempts) {
    const signal = await client.signals.get(signalId);

    if (signal.risk_score !== null) {
      // Processing complete
      return signal;
    }

    // Wait before next poll
    await sleep(interval);
    attempts++;
  }

  throw new Error("Signal processing timed out");
}
```

**أفضل الممارسات**:

- ابدأ بفترات مدتها ثانية واحدة
- استخدم التراجع الأسي للانتظار الأطول
- اضبط مهلات معقولة (10-30 ثانية)
- فضِّل webhooks على الاستطلاع في الإنتاج

### الطريقة الثالثة: تتبع معرف المهمة (مستقبلاً)

::callout{icon="i-lucide-calendar" color="amber"}
**قريبًا**: ستُعيد إصدارات API المستقبلية معرِّفات المهام لاستعلامات حالة المهمة المباشرة.

## التعامل مع الأخطاء

### إعادة المحاولة التلقائية

تُعاد محاولة المهام الفاشلة تلقائيًا مع التراجع الأسي:

| المحاولة | التأخير  | وقت المثال |
| -------- | -------- | ---------- |
| 1        | فوري     | 0:00       |
| 2        | 30 ثانية | 0:30       |
| 3        | دقيقتان  | 2:30       |
| 4        | 8 دقائق  | 10:30      |
| 5        | 32 دقيقة | 42:30      |

**بعد 5 محاولات**: تُوسَم المهمة كفاشلة، ويُرسَل webhook (إن كان مُهيَّأً).

### سيناريوهات الفشل الشائعة

**1. مشاكل الشبكة المؤقتة**

- **الأعراض**: فشل تسليم webhook
- **إعادة المحاولة**: تلقائية مع التراجع الأسي
- **الحل**: عادةً يُحل خلال 2-3 محاولات

**2. مهلة انتظار API الخارجية**

- **الأعراض**: مهلة مهمة تقييم المخاطر
- **إعادة المحاولة**: تلقائية (حتى 3 محاولات)
- **الحل**: التحقق من صفحة الحالة لمشاكل الخدمة

**3. بيانات غير صالحة**

- **الأعراض**: فشل المهمة فورًا
- **إعادة المحاولة**: لا إعادة محاولة (فشل دائم)
- **الحل**: إصلاح البيانات وإعادة الإرسال

**4. حدود المعدل (داخلية)**

- **الأعراض**: تأخر المهمة في قائمة الانتظار
- **إعادة المحاولة**: تلقائية مع التراجع
- **الحل**: الانتظار حتى إعادة تعيين نافذة حد المعدل

## أفضل الممارسات

### 1. استخدام حكم المخاطر المتزامن

**درجة المخاطر متاحة فورًا في استجابة 201** — لا حاجة للاستطلاع أو الانتظار:

```typescript
// ✅ CORRECT: Risk verdict is synchronous
const response = await fetch("/api/v1/signals", {
  method: "POST",
  headers: {
    "X-Centry-Key": process.env.PROTEGEY_SECRET_KEY,
    "Idempotency-Key": crypto.randomUUID(),
  },
  body: JSON.stringify(signalPayload),
});
const { data } = await response.json();

// Available immediately — no poll needed
console.log(data.risk_score); // 0.78
console.log(data.risk_level); // "high"
console.log(data.detectors_triggered); // ["RAPID_TRANSACTION_VELOCITY"]

// Apply your decision logic now
if (data.risk_level === "critical") {
  await blockTransaction(data.signal_id);
} else if (data.risk_level === "high") {
  await requireAdditionalVerification();
}
```

### 2. استخدام Webhooks في الإنتاج

**Webhooks أكثر كفاءة من الاستطلاع**:

- لا استدعاءات API غير ضرورية
- إشعار فوري عند الجاهزية
- تجربة مستخدم أفضل

**الإعداد**:

```typescript
// Configure once in partner portal
// No polling loops needed

app.post("/webhooks/protegey", async (req, res) => {
  const { type, data } = req.body;

  // Verify signature (important!)
  if (!verifySignature(req)) {
    return res.status(401).send("Invalid signature");
  }

  // Process event
  await processEvent(type, data);

  // Acknowledge immediately
  res.status(200).send("OK");
});
```

### 3. التعامل مع المهل بشكل سلس

**تعيين مهلات واقعية**:

```typescript
const timeout = 30000; // 30 seconds
const signal = await client.signals.create(signalData, { timeout });

  // Process later via webhook

```

### 4. تطبيق الأمانة الإدارية

**قد تُسلَّم Webhooks أكثر من مرة**:

```typescript
const processedEvents = new Set<string>();

app.post("/webhooks/protegey", async (req, res) => {
  const eventId = req.body.id;

  // Check if already processed
  if (processedEvents.has(eventId)) {
    return res.status(200).send("Already processed");
  }

  // Process event
  await processEvent(req.body);

  // Mark as processed
  processedEvents.add(eventId);

  res.status(200).send("OK");
});
```

## استكشاف الأخطاء وإصلاحها

### المشكلة: "risk_score مفقود من استجابة 201"

**السبب**: على الأرجح خطأ تحقق (422) وليس استجابة 201 — تحقق من حالة الاستجابة وجسمها.

**الحل**: تأكد من أن الحمولة تتضمن `schema_version: "2.0"` و `primary_actor.entity_id`. حكم المخاطر دائمًا متزامن على استجابات 201 — لا حاجة للاستطلاع.

```typescript
const response = await fetch('/api/v1/signals', { ... });
if (response.status === 422) {
  const error = await response.json();
  console.error('Validation failed:', error.errors); // find missing fields
}
```

3. نقطة النهاية تُعيد رمز حالة خطأ
4. فشل التحقق من التوقيع

**الأعراض**: تُظهر لوحة التحكم عمق قائمة انتظار عالٍ، وأوقات معالجة بطيئة.

**الأسباب المحتملة**:

2. مهلة انتظار العامل قصيرة جدًا
3. نفاد تجميع اتصال قاعدة البيانات
4. حدود معدل API الخارجية

**الحلول**:

### المشكلة: "السياق لا يُحفَظ في المهام"

**الأعراض**: المهمة تستعلم عن مخطط أو بيانات شريك خاطئ.

**السبب**: المهمة لا تمتد من `ContextAwareJob` أو لم يُستدعَ المُنشئ الأب.

**الحل**:

```php
// ✅ CORRECT
class MyJob extends ContextAwareJob {
    public function __construct(private string $data) {
        parent::__construct(); // CRITICAL
    }

    protected function perform(): void {
        // Context restored automatically
    }
}

// ❌ WRONG
class MyJob implements ShouldQueue {
    // Context not captured!
}
```

**ترتيب أولوية قائمة الانتظار**:

```bash
php artisan queue:work --queue=high,default,low
```

### المهام المؤجلة

**معالجة الإشارة بعد تأخير**:

```php
ProcessFraudSignal::dispatch($signalId)->delay(now()->addMinutes(5));
```

### تسلسل المهام

**تنفيذ المهام بشكل تسلسلي**:

```php
ProcessFraudSignal::withChain([
    new CalculateEntityRisk($entityId),
    new GenerateAlerts($signalId),
    new SendNotifications($partnerId)
])->dispatch($signalId);
```

### دُفعات المهام

**تتبع تقدم الدُّفعة**:

```php
$batch = Bus::batch([
    new ProcessSignal($signalId1),
    new ProcessSignal($signalId2),
    new ProcessSignal($signalId3)
])->dispatch();

// Check progress
$batch->progress(); // 66% complete
```
