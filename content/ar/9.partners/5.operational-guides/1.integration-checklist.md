استخدم هذه القائمة الشاملة للتحقق من تكاملك مع Protegey قبل الإطلاق. أكمل جميع البنود في بيئة الاختبار (Sandbox) أولًا، ثم تحقق منها في بيئة الإنتاج.

::callout{icon="i-lucide-clipboard-check" color="blue"}
**الجاهزية للإنتاج**: يشمل التكامل المتكامل استيعاب الإشارات، وإدارة الحالات، وسير عمل التنبيهات، ومعالجة webhooks، والتعامل السليم مع الأخطاء.
::

## المرحلة الأولى: إعداد بيئة الاختبار

### تهيئة البيئة

- [ ] **الوصول إلى بيئة الاختبار**: مفاتيح API الخاصة ببيئة الاختبار مُولَّدة من بوابة الشريك
- [ ] **التبديل بين البيئات**: إمكانية التبديل بين بيئة الاختبار والإنتاج
- [ ] **تهيئة الكوكيز/الترويسات**: تعمل آلية التبديل عبر معاملات الاستعلام أو الكوكيز أو الترويسات

### توليد البيانات التجريبية

- [ ] **توليد الإشارات**: إمكانية توليد إشارات تجريبية عبر API (`/api/v1/partner/sandbox/generate-demo-signals`)
- [ ] **اختبار القوالب**: اختبار قوالب إشارات متعددة (استيلاء على الحساب، بيانات مسروقة، إلخ)
- [ ] **توزيع المخاطر**: التحقق من توزيع ملف تعريف المخاطر (10% حرجة، 20% عالية، 30% متوسطة، 40% منخفضة)

### عزل البيانات

- [ ] **فصل المخططات**: التأكد من عدم ظهور إشارات بيئة الاختبار في لوحة تحكم الإنتاج
- [ ] **وظيفة الإعادة**: إعادة تعيين بيانات بيئة الاختبار بنجاح عبر API
- [ ] **سلامة الإنتاج**: عدم تلوث بيئة الإنتاج ببيانات اختبارية

## المرحلة الثانية: التكامل الجوهري

## الأمان

- [ ] **تخزين مفاتيح API**: تخزين المفاتيح في متغيرات البيئة أو مدير الأسرار، لا في الكود المصدري.
- [ ] **قائمة عناوين IP المسموح بها**: تهيئة عناوين IP الخاصة بالإنتاج في بوابة الشريك.
- [ ] **TLS**: جميع طلبات API تستخدم HTTPS.

## الموثوقية

- [ ] **مهلة الانتظار**: تهيئة مهلة انتظار في عميل API (موصى به: 2000ms).
- [ ] **استراتيجية الفشل المفتوح/المغلق**: وضع آلية للتعامل مع عدم توافر API (مثلاً: السماح بالتلقائي أو المراجعة اليدوية).
- [ ] **إعادة المحاولة**: تطبيق التراجع الأسي لأخطاء `429` و `5xx`.

## جودة البيانات

- [ ] **تنسيق الكيانات**: تصغير حروف البريد الإلكتروني وإزالة المسافات. تنسيق أرقام الهاتف وفق E.164.
- [ ] **التجزئة**: إن كنت تستخدم PII مُجزَّأ مسبقًا، فتأكد من استخدام SHA-256 بشكل صحيح.
- [ ] **خاص بالعمليات غير المتزامنة**: تنفيذ إرسال الإشارات بشكل غير متزامن (مهمة خلفية) لتفادي تعليق واجهة المستخدم.

## التشغيل

- [ ] **المراقبة**: تسجيل رموز استجابة Protegey API وزمن الاستجابة.
- [ ] **التنبيهات**: وجود تنبيهات عند ارتفاع أخطاء 4xx/5xx بشكل مفاجئ.
- [ ] **جهات الاتصال**: تحديث جهات الاتصال الطارئة والفوترة والفنية في البوابة.

## الامتثال

- [ ] **سياسة الخصوصية**: سياسة الخصوصية الموجَّهة للمستخدمين تُفصح عن مشاركة بيانات منع الاحتيال.
- [ ] **الاحتفاظ بالبيانات**: عدم تخزين نتائج مخاطر Protegey لأكثر من المدة الضرورية (الحد الأقصى الموصى به: 90 يومًا).
- [ ] **موافقة المستخدم**: الحصول على موافقة المستخدم المناسبة لمعالجة اكتشاف الاحتيال
- [ ] **اتفاقية معالجة البيانات**: توقيع DPA مع Protegey (مطلوب للإنتاج)

## المرحلة الثالثة: استيعاب الإشارات

### تكامل API

- [ ] **تنسيق UFES v2**: جميع الإشارات تتضمن `schema_version: "2.0"` و `primary_actor.entity_id`
- [ ] **تجزئة PII**: تجزئة المعرِّفات باستخدام HMAC-SHA256 مع **مفتاح شبكتك** (ليس SHA-256 وحده، وليس مفتاح API)
- [ ] **حقول الكاشف**: تضمين `source.ip_address` و `primary_actor.device.fingerprint` و `primary_actor.identifiers.sim_changed_at` حيثما ينطبق
- [ ] **الأمانة الإدارية**: إرسال ترويسة `Idempotency-Key` مع كل إشارة؛ إعادة استخدام نفس المفتاح عند إعادة المحاولة

### معالجة الاستجابة

- [ ] **201 Created**: استخلاص حكم المخاطر المتزامن (`risk_score`، `risk_level`، `detectors_triggered`) والتصرف بناءً عليه
- [ ] **422 Unprocessable**: معالجة أخطاء التحقق؛ تسجيل الحمولة الخاطئة لأغراض التصحيح
- [ ] **429 Rate Limit**: تطبيق التراجع الأسي (مع إعادة استخدام نفس `Idempotency-Key` عند المحاولة)
- [ ] **500 Server Error**: فشل سلس؛ إعادة المحاولة بنفس مفتاح الأمانة الإدارية

### الاختبار

- [ ] **استبدال SIM**: إرسال إشارة اختبار بـ `primary_actor.identifiers.sim_changed_at` خلال 24 ساعة ← يتشغل `SIM_SWAP_PROXIMITY`
- [ ] **جهاز جديد**: إرسال إشارة اختبار ببصمة جهاز جديدة `primary_actor.device.fingerprint` ← يتشغل `NEW_DEVICE_ACCESS`
- [ ] **مبلغ مرتفع**: إرسال إشارة اختبار بمبلغ أعلى بكثير من الخط الأساسي ← يتشغل `LARGE_OUTLIER_TRANSACTION`
- [ ] **الأمانة الإدارية**: إرسال نفس الإشارة مرتين بنفس المفتاح ← الثانية تُعيد `X-Idempotency-Replayed: true` بنفس `signal_id`

## المرحلة الرابعة: مراقبة المعاملات

### تكامل لوحة التحكم

- [ ] **خلاصة المعاملات**: إمكانية عرض خلاصة الإشارات الحية في بوابة الشريك
- [ ] **التصفية**: إمكانية التصفية حسب الحالة ومستوى المخاطر والنطاق الزمني والمستخدم المُعيَّن
- [ ] **البحث**: عمل البحث النصي الكامل لمعرِّفات المعاملات وتجزئات الجهة الفاعلة
- [ ] **تفصيل المخاطر**: إمكانية عرض عوامل المخاطر التفصيلية لكل إشارة

### اتخاذ القرار

- [ ] **القرارات اليدوية**: إمكانية الموافقة/الرفض/وضع العلم على الإشارات عبر البوابة أو API
- [ ] **تسجيل القرارات**: تسجيل جميع القرارات بشكل سليم مع السبب
- [ ] **القرارات الجماعية**: اختبار سير عمل القرارات الجماعية (ميزة Enterprise)

### التحليلات

- [ ] **مقاييس لوحة التحكم**: إمكانية عرض إحصاءات ملخصة (مجموع الإشارات، متوسط درجة المخاطر، توزيع القرارات)
- [ ] **بيانات السلاسل الزمنية**: إمكانية تحليل الاتجاهات عبر الزمن
- [ ] **خريطة المخاطر**: إمكانية تحديد الفترات الزمنية عالية المخاطر
- [ ] **وظيفة التصدير**: إمكانية تصدير الإشارات إلى CSV لأغراض التقارير

## المرحلة الخامسة: إدارة الحالات

### إنشاء الحالات

- [ ] **من إشارة**: إمكانية إنشاء حالة مباشرةً من إشارة عالية المخاطر
- [ ] **إنشاء يدوي**: إمكانية إنشاء حالة دون إشارة مرتبطة
- [ ] **تحديد الأولوية**: إمكانية تعيين الأولوية المناسبة (منخفضة، متوسطة، عالية، حرجة)
- [ ] **اختيار التصنيف**: إمكانية تصنيف الحالات (ACCOUNT_TAKEOVER، IDENTITY_THEFT، إلخ)

### سير عمل التحقيق

- [ ] **إضافة الملاحظات**: إمكانية إضافة ملاحظات التحقيق إلى الحالات
- [ ] **رفع الأدلة**: إمكانية إرفاق لقطات الشاشة والسجلات والوثائق بالحالات
- [ ] **تحديثات الحالة**: إمكانية الانتقال بين الحالات (open → in_progress → resolved → closed)
- [ ] **التعيين**: إمكانية تعيين الحالات لأعضاء الفريق

### التعاون في الحالات

- [ ] **وصول الفريق**: جميع أعضاء فريق مكافحة الاحتيال يمكنهم الوصول إلى الحالات
- [ ] **عرض الجدول الزمني**: مسار تدقيق كامل مرئي لجميع أنشطة الحالة
- [ ] **عملية التسليم**: وجود عملية واضحة لتبديل المناوبات والتصعيد

### إغلاق الحالات

- [ ] **توثيق الحل**: التقاط ملاحظات الحل المطلوبة
- [ ] **تتبع الإجراءات**: تسجيل الإجراءات المتخذة (حجب الجهة الفاعلة، عكس المعاملة، إلخ)
- [ ] **إغلاق الحالة**: إغلاق الحالات بشكل سليم بعد الحل

## المرحلة الثامنة: تكامل Webhook

### تهيئة Webhook

- [ ] **إعداد نقطة النهاية**: تسجيل رابط webhook في بوابة الشريك (يُشترط HTTPS)
- [ ] **تخزين السر**: نسخ السر الخاص بكل نقطة نهاية عند الإنشاء وتخزينه في مدير الأسرار
- [ ] **الاشتراك في الأحداث**: الاشتراك في الأحداث ذات الصلة (`signal.ingested`، `alert.created`، `case.created`)
- [ ] **إرسال اختباري**: إرسال اختبار ping والتحقق من الاستلام والتحقق من صحة التوقيع

### التحقق من التوقيع

- [ ] **قراءة الترويسة**: قراءة `X-Centry-Signature` (وليس `X-Protegey-Signature`)
- [ ] **HMAC-SHA256**: التحقق على `json_encode($payload)` / `JSON.stringify(body)` مع السر الخاص بكل نقطة نهاية
- [ ] **المقارنة الثابتة الزمن**: استخدام `hash_equals()` / `timingSafeEqual()` — وليس `===`

### معالج Webhook

- [ ] **200 فوري**: إعادة HTTP 200 خلال 3 ثوانٍ قبل المعالجة
- [ ] **المعالجة غير المتزامنة**: إرسال المعالجة الثقيلة إلى مهمة خلفية
- [ ] **الأمانة الإدارية**: التعامل مع عمليات التسليم المكررة عبر تتبع `X-Centry-Delivery-ID`

### معالجة الأحداث

- [ ] **`signal.ingested`**: استخلاص حكم المخاطر (`risk_score`، `risk_level`، `detectors_triggered`) والتصرف بناءً عليه
- [ ] **`alert.created`**: التنبيهات العالية/الحرجة تُشغِّل تدفق التصعيد الداخلي
- [ ] **`case.created`**: فتح حالة في نظام التذاكر/CRM الداخلي
- [ ] **`case.status_changed`**: مزامنة حالة القضية مع النظام الداخلي

## المرحلة التاسعة: العمليات غير المتزامنة

### الوعي بالسياق

- [ ] **مهام قائمة الانتظار**: فهم معالجة الإشارات غير المتزامنة (2-8 ثوانٍ)
- [ ] **توقعات التوقيت**: عدم توقع درجات مخاطر فورية بعد إرسال الإشارة
- [ ] **الاستطلاع مقابل Webhooks**: استخدام webhooks بدلاً من الاستطلاع في الإنتاج

### التعامل مع الأخطاء

- [ ] **فشل المهام**: منطق إعادة المحاولة للعمليات غير المتزامنة الفاشلة
- [ ] **التعامل مع المهلة**: التعامل السلس عندما تستغرق المعالجة وقتًا أطول من المتوقع
- [ ] **إشعارات المهام الفاشلة**: مراقبة webhooks المهام الفاشلة

## المرحلة العاشرة: جاهزية الإنتاج

### الأداء

- [ ] **حدود معدل الطلبات**: البقاء ضمن حدود معدل الإنتاج (1000 طلب/دقيقة للمعاملات)
- [ ] **تجميع الاتصالات**: استخدام عميل HTTP لتجميع الاتصالات لتحقيق الكفاءة
- [ ] **التخزين المؤقت**: تخزين درجات المخاطر مؤقتًا بشكل مناسب (TTL: 5 دقائق)
- [ ] **التحميل الكسول**: تأجيل العمليات الثقيلة إلى مهام خلفية

### المراقبة

- [ ] **زمن استجابة API**: تتبع زمن الاستجابة P50 وP95 وP99 لجميع استدعاءات API
- [ ] **معدلات الخطأ**: مراقبة معدلات أخطاء 4xx و 5xx
- [ ] **معدلات النجاح**: تتبع معدل نجاح استيعاب الإشارات
- [ ] **عمق قائمة الانتظار**: مراقبة عمق قائمة الانتظار الداخلية (إن وُجد)

### التنبيهات

- [ ] **معدل خطأ مرتفع**: تنبيه إن تجاوز معدل خطأ API نسبة 5%
- [ ] **فشل Webhook**: تنبيه عند تكرار فشل تسليم webhook
- [ ] **اقتراب حد المعدل**: تنبيه عند الوصول إلى 80% من حد المعدل
- [ ] **ارتفاع زمن الاستجابة**: تنبيه إن تجاوز P95 ثانيتين

### الاستجابة للحوادث

- [ ] **دورية المناوبة**: وجود عضو فريق في مناوبة لمسائل Protegey
- [ ] **كتاب التشغيل**: إجراءات موثقة للمشاكل الشائعة
- [ ] **معلومات الاتصال**: إمكانية الوصول إلى معلومات دعم Protegey
- [ ] **خطة التراجع**: القدرة على تعطيل تكامل Protegey عند الضرورة

- [ ] **المهندسون**: إلمام المطورين بتكامل API

### التوثيق

- [ ] **عتبات القرار**: توثيق عتبات درجة المخاطر
- [ ] **إجراءات التصعيد**: وجود عملية واضحة لتصعيد الحالات المعقدة

## المرحلة الثانية عشرة: الإطلاق

### ما قبل الإطلاق

- [ ] **المراجعة القانونية**: توقيع MSA وDPA
- [ ] **استبيان الأمان**: إتمامه والموافقة عليه
- [ ] **مفاتيح الإنتاج**: توليد مفاتيح API الخاصة بالإنتاج وتأمينها
- [ ] **اختبارات الدخان**: اجتياز الفحوصات الصحية الأساسية في الإنتاج

### استراتيجية الإطلاق

- [ ] **وضع الظل**: التشغيل في وضع الظل لمدة أسبوع (تسجيل الدرجات دون الحجب)
- [ ] **الطرح التدريجي**: الحجب للمخاطر الحرجة فقط في البداية (درجة ≥ 90)
- [ ] **ضبط العتبة**: خطة لخفض العتبة بعد مراقبة الأنماط
- [ ] **التواصل مع العملاء**: إعداد فريق الدعم للاستفسارات المتعلقة بالاحتيال

### ما بعد الإطلاق

- [ ] **المراقبة اليومية**: مراجعة لوحات التحكم يوميًا خلال الأسبوعين الأولين
- [ ] **مراجعة الأخطاء الإيجابية**: مراجعة الأخطاء الإيجابية وضبط العتبات
- [ ] **مقاييس الأداء**: تتبع معدل اكتشاف الاحتيال ومعدل الخطأ الإيجابي
- [ ] **تغذية راجعة الفريق**: جمع التغذية الراجعة من محللي الاحتيال حول سير العمل

---

## المرحلة الثالثة عشرة: التحسين

### ضبط العتبات

- [ ] **معدل الخطأ الإيجابي**: الهدف < 10% معدل خطأ إيجابي
- [ ] **معدل اكتشاف الاحتيال**: الهدف > 90% معدل اكتشاف
- [ ] **معدل المراجعة اليدوية**: التحسين للحفاظ على قائمة انتظار المراجعة اليدوية قابلة للإدارة
- [ ] **مراجعة شهرية**: جدولة اجتماعات مراجعة العتبة الشهرية

### تحسين سير العمل

- [ ] **قوالب الحالات**: إنشاء قوالب لأنواع الاحتيال الشائعة
- [ ] **الإجراءات التلقائية**: أتمتة المهام الروتينية (مثلاً: الحجب التلقائي للمحتالين المؤكدين)
- [ ] **توسيع التكامل**: التكامل مع CRM أو نظام التذاكر أو أدوات BI
- [ ] **تقارير مخصصة**: بناء تقارير مخصصة للقيادة

### بناء المعرفة

- [ ] **مكتبة أنماط الاحتيال**: توثيق أنماط الاحتيال الشائعة المرصودة
- [ ] **كتب التشغيل للتحقيق**: إنشاء كتب تشغيل لأنواع مختلفة من الاحتيال
- [ ] **مراجعات الفريق الدورية**: استرجاع منتظم لتحقيقات الاحتيال
- [ ] **التدريب المتقاطع**: تدريب أعضاء الفريق على فئات احتيال مختلفة
