# Corrélation Auto-STR

## Vue d'ensemble

Le `AutoStrCorrelationService` détecte lorsque les indicateurs AML `structuring` et `velocity_breach` se déclenchent tous deux sur la même entité dans une fenêtre glissante de 72 heures. Lorsque ce schéma est détecté, un rapport d'activité suspecte (SAR) est automatiquement rédigé et le partenaire est notifié.

L'auto-STR est un outil d'aide à la conformité — il réduit le risque qu'un schéma de co-occurrence soit manqué lors de la révision manuelle. Le SAR reste à l'état `draft` et n'est jamais déposé automatiquement.

---

## Conditions de déclenchement

Un SAR est rédigé automatiquement lorsque **toutes** les conditions suivantes sont réunies :

1. Un indicateur `structuring` existe pour `entity_uuid` dans les dernières `WINDOW_HOURS` (défaut : 72h)
2. Un indicateur `velocity_breach` existe pour le même `entity_uuid` dans la même fenêtre
3. Aucun SAR existant n'est déjà à l'état `draft` pour cette entité dans la fenêtre de déduplication (`dedup_hours`, défaut : 72h — configurable par le partenaire via la règle `auto_str_correlation`)

La fenêtre de déduplication empêche la création de SAR en double pour des schémas persistants sur plusieurs jours.

---

## Configuration du service

Les paramètres sont sauvegardés en base de données via la règle configurable `auto_str_correlation` (Phase R — complète). Les partenaires peuvent les remplacer via `PUT /compliance/rules/{uuid}/config`.

| Paramètre | Défaut | Description |
|-----------|---------|-------------|
| `window_hours` | 72 | Fenêtre glissante pour rechercher un indicateur complémentaire |
| `dedup_hours` | 72 | Supprime les SAR en double dans cette fenêtre |

Le `ConfigurableRuleEngine` résout les paramètres en donnant la priorité aux remplacements du partenaire sur les défauts. Les résultats sont mis en cache 15 minutes.

---

## Création du brouillon de SAR

Lorsqu'il est déclenché, `AutoStrCorrelationService::evaluate()` appelle `SuspiciousActivityReportService::draft()`. Les deux indicateurs corrélés sont liés au SAR (`sar_id`) et passent au statut `escalated`.

---

## Notification

Après la création du brouillon, un événement webhook `compliance.sar.auto_drafted` est dispatché vers tous les endpoints webhook actifs du partenaire :

```json
{
  "event": "compliance.sar.auto_drafted",
  "data": {
    "sar_uuid": "sar_01HZ...",
    "entity_uuid": "ent_01HZ...",
    "trigger": "auto_str_correlation",
    "transaction_count": 6,
    "aggregate_amount": 47200.00,
    "currency": "USD",
    "review_url": "https://app.protegey.com/compliance/sars/sar_01HZ..."
  }
}
```

## Détail de la logique de co-occurrence

`evaluate(FraudEntity $entity, array $currentFlags, string $partnerUuid)` est appelé depuis `AMLComplianceService` après l'évaluation des indicateurs de chaque signal.

1. Parcourir `$currentFlags` à la recherche d'une clé déclencheuse (`structuring` ou `velocity_breach`)
2. Interroger `AmlTransactionFlag` pour la clé complémentaire sur le même `entity_id`, dans la fenêtre `window_hours`, en excluant les indicateurs `dismissed`
3. Si trouvé, vérifier la déduplication : aucun SAR `draft` pour cette entité dans `dedup_hours`
4. Rédiger le SAR et lier les deux indicateurs (`sar_id`, `status = escalated`)

---

## Cycle de vie du SAR après rédaction automatique

```
auto_drafted → draft (partenaire modifie le narratif) → under_review → filed
                                                                      ↘ closed (décision partenaire)
```

Les partenaires doivent :
1. Réviser le SAR rédigé automatiquement dans le tableau de bord de conformité
2. Modifier le narratif si nécessaire (ajouter du contexte, corriger les montants pré-calculés)
3. Passer à `under_review` via `POST /compliance/sars/{id}/review`
4. Déposer auprès du régulateur via `POST /compliance/sars/{id}/file`

Le paquet de preuves exporté lors du dépôt utilise des identifiants d'entité hachés HMAC. Les partenaires doivent substituer les hashes par les identités KYC réelles avant la soumission à la CRF.

---

## Piste d'audit

Chaque déclenchement auto-STR et chaque transition d'état du SAR sont journalisés dans `audit_logs` avec :
- `action` : `sar.auto_drafted`, `sar.reviewed`, `sar.filed`
- `actor_type` : `system` (rédaction automatique), `user` (transitions manuelles)
- `metadata` : indicateurs déclencheurs, paramètres de fenêtre, UUID de l'utilisateur acteur
