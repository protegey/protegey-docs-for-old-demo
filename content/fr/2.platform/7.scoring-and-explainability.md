Chaque verdict de risque émis par Protegey répond à quatre questions :

1. **Quel niveau de risque ?** → `risk_score` + `risk_level`
2. **Quelle est notre certitude ?** → `confidence`
3. **Pourquoi ?** → `explanations[]`
4. **Que devez-vous faire ?** → `recommendation`

Ce contrat unifié s'applique à la fois à `/evaluate` et à `/risk/assess`. La réponse de `/evaluate` est plus légère (moins de signaux, pas d'historique complet) ; `/risk/assess` est enrichi d'une profondeur comportementale. La structure est identique.

---

## risk_score

Un nombre décimal continu entre 0,0 et 1,0 représentant la probabilité de fraude ou d'abus. Plus la valeur est élevée, plus le risque est grand.

Le score est produit par le **Moteur de Fusion de Risque Pondéré (NUFSS)**, qui agrège quatre dimensions :

| Dimension | Poids | Source |
|---|---|---|
| Comportementale | 35% | Agrégat des détecteurs (vélocité, valeur aberrante, échange de SIM, appareil, déplacement) |
| Réseau | 40% | Risque propagé à 2 sauts dans le graphe chaud |
| Contextuelle | 15% | Enrichissement par résolveurs (géo, appareil, opérateur, heure du jour) |
| Historique | 10% | Moyenne mobile de l'entité sur 90 jours |

Le nombre décimal fusionné est ce que vous voyez comme `risk_score`. Il est **déterministe** — les mêmes entrées produisent le même score.

---

## risk_level

Des niveaux normalisés dérivés du `risk_score` :

| `risk_level` | Plage de `risk_score` | Signification |
|---|---|---|
| `low` | 0,00 – 0,20 | Activité normale, aucun signal significatif |
| `medium` | 0,21 – 0,50 | Schémas suspects ; authentification renforcée recommandée |
| `high` | 0,51 – 0,80 | Forts indicateurs de fraude ; révision manuelle ou défi |
| `critical` | 0,81 – 1,00 | Haute confiance de fraude ; bloquer et enquêter |

Ces niveaux sont stables — ils ne changeront pas entre les versions de l'API sans une montée de version majeure et un avis de dépréciation.

---

## confidence

Un nombre décimal entre 0,0 et 1,0 représentant la certitude de Protegey dans le `risk_score`. Un score de risque élevé avec une faible confiance signifie : « cela semble risqué, mais nous n'avons pas suffisamment de données pour en être sûrs. »

**Ce qui détermine la confiance :**

- **Volume de signaux** : Plus de signaux = plus de certitude
- **Récence des signaux** : Les signaux récents ont plus de poids que les anciens
- **Cohérence des schémas** : Des schémas cohérents à travers plusieurs détecteurs augmentent la confiance
- **Force de correspondance** : Les correspondances OSINT robustes, les correspondances exactes dans le graphe et les identifiants de haute qualité augmentent la confiance

### Quadrant Confiance × Risque

Utilisez cette matrice pour router les décisions :

| | Haute Confiance | Faible Confiance |
|---|---|---|
| **Risque Élevé** | Agir immédiatement | Enquêter davantage |
| **Risque Faible** | Sûr de procéder | Données insuffisantes |

::callout{icon="i-lucide-info" color="blue"}
**Les nouvelles entités ont une confiance plus faible par défaut.** Une entité vue pour la première fois aujourd'hui aura une valeur `confidence` d'environ 0,3–0,5 même si des détecteurs se déclenchent. Cela évite des actions agressives sur des acteurs sans historique comportemental.
::

## explanations[]

Une liste structurée de raisons ayant contribué au verdict de risque. Chaque explication est lisible par une machine et par un humain.

### Objet Explication

```json
{
  "code": "DEVICE_REUSE",
  "category": "device",
  "severity": "high",
  "message": "Device fingerprint linked to 3 flagged entities",
  "evidence": {
    "linked_entity_count": 3,
    "highest_linked_risk": 0.91
  }
}
```

### Champs

| Champ | Type | Description |
|---|---|---|
| `code` | string | Code lisible par machine (voir la référence ci-dessous) |
| `category` | string | Catégorie du signal (voir les catégories ci-dessous) |
| `severity` | string | `low`, `medium`, `high`, ou `critical` |
| `message` | string | Explication lisible par un humain en anglais |
| `evidence` | object | Données de support utilisées pour générer cette explication |

### Catégories Standard

| Catégorie | Ce qu'elle couvre |
|---|---|
| `identity` | Signaux de risque sur le téléphone, l'email, l'identifiant national |
| `device` | Anomalies d'empreinte d'appareil, schémas de réutilisation |
| `network` | Risque du voisinage dans le graphe, entités liées |
| `behavioral` | Vélocité, montants aberrants, anomalies temporelles |
| `historical` | Implication dans des fraudes passées, changements de statut antérieurs |
| `synthetic_identity` | Signaux cohérents avec la fraude d'identité synthétique |
| `transactional` | Schémas au niveau des transactions (structuration, transfrontalier) |

### Référence des Codes d'Explication

| Code | Catégorie | Ce que cela signifie |
|---|---|---|
| `DEVICE_REUSE` | device | Empreinte d'appareil liée à plusieurs entités distinctes |
| `NEW_DEVICE` | device | Premier appareil jamais utilisé pour cette entité associé à une géolocalisation à haut risque |
| `RAPID_VELOCITY` | behavioral | La fréquence des transactions dépasse le seuil dans la fenêtre glissante |
| `LARGE_OUTLIER` | behavioral | Le montant de la transaction est une valeur statistiquement aberrante par rapport à la base de référence de l'entité |
| `SIM_SWAP_PROXIMITY` | behavioral | La transaction a eu lieu dans les heures suivant un échange de carte SIM |
| `IMPOSSIBLE_TRAVEL` | behavioral | La même entité se trouve dans deux lieux géographiques en un temps physiquement impossible |
| `EMAIL_RISK_PATTERN` | identity | Le fournisseur ou le schéma d'email est associé à des identités synthétiques |
| `PHONE_NETWORK_RISK` | identity | L'opérateur ou le type de numéro est associé à des schémas de fraude |
| `NETWORK_CONTAMINATION` | network | L'entité est connectée à des fraudeurs connus dans le graphe |
| `HIGH_RISK_NEIGHBORHOOD` | network | Le risque moyen du voisinage à 2 sauts dépasse le seuil |
| `OSINT_MATCH` | identity | L'entité correspond à un enregistrement de sanctions, PEP ou médias défavorables |

## recommendation

Une directive d'action structurée basée sur la combinaison du `risk_score` et de la `confidence`.

```json
{
  "action": "review",
  "priority": "high"
}
```

### Types d'Actions

| `action` | Quand utilisé | Réponse suggérée |
|---|---|---|
| `allow` | Risque faible, confiance suffisante | Procéder normalement |
| `review` | Risque moyen ou faible confiance | File de révision manuelle |
| `challenge` | Risque élevé, confiance modérée | Authentification renforcée (OTP, biométrie) |
| `block` | Risque critique ou correspondance confirmée | Bloquer la transaction, ouvrir une enquête |

### Niveaux de Priorité

| `priority` | Signification |
|---|---|
| `low` | Informatif, pas d'urgence |
| `medium` | Révision dans le SLA normal |
| `high` | Révision rapide (dans les heures qui suivent) |
| `critical` | Action immédiate requise |

## Contrat de Réponse Unifié

`/evaluate` et `/risk/assess` retournent la même structure de niveau supérieur. La différence est la profondeur :

```json
{
  "risk_score": 0.73,
  "risk_level": "high",
  "confidence": 0.81,
  "explanations": [
    {
      "code": "RAPID_VELOCITY",
      "category": "behavioral",
      "severity": "high",
      "message": "12 transactions in the last hour — threshold is 10",
      "evidence": { "count_1h": 12, "threshold": 10 }
    },
    {
      "code": "NETWORK_CONTAMINATION",
      "category": "network",
      "severity": "medium",
      "message": "Shares device with 1 confirmed fraudster",
      "evidence": { "shared_with_confirmed": 1 }
    }
  ],
  "recommendation": {
    "action": "review",
    "priority": "high"
  }
}
```

`/evaluate` retourne cette structure avec un contexte au niveau du signal. `/risk/assess` inclut en plus les blocs `profile`, `network` et `history` avec le package d'intelligence complet de l'entité.

## Logique de Scoring Composite

Il s'agit d'une description simplifiée à l'intention des partenaires. Les mécanismes de scoring internes sont confidentiels.

- **Atténuation par récence** : Les signaux de plus de 90 jours contribuent moins. Les signaux des dernières 24 heures ont un poids plein.
- **Diversité des signaux** : Plusieurs détecteurs indépendants qui se déclenchent augmentent davantage le `risk_score` et la `confidence` qu'un seul détecteur se déclenchant à plusieurs reprises.
- **Amplification réseau** : Une entité connectée à des fraudeurs confirmés via le graphe voit son composant `network_score` amplifié proportionnellement.
- **Limitation par confiance OSINT** : Les correspondances OSINT avec une confiance < 0,3 apparaissent comme des explications `review` mais ne génèrent pas de recommandations automatiques de type `block`.

---

## Règles de Conception

Ce sont des engagements, pas des aspirations :

- **Pas de boîtes noires** : Tout score de risque non trivial inclut au moins une entrée `explanation`
- **Sorties déterministes** : Mêmes entrées → même sortie (modulo les changements d'état du graphe entre les appels)
- **Compatibilité ascendante** : Les nouveaux codes `explanation` sont additifs ; les codes existants ne sont jamais supprimés sans dépréciation
- **Auditabilité** : Toutes les entrées et sorties de scoring sont enregistrées et disponibles via l'API du journal d'audit
