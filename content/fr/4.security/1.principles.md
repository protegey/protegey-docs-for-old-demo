La sécurité n'est pas seulement une fonctionnalité de Protegey ; c'est le principe fondamental de notre existence. Les institutions réglementées ne peuvent pas participer à un réseau de défense collective si ce réseau introduit de nouvelles vulnérabilités.

Ce document expose notre architecture "Zéro Confiance, Confidentialité Maximale".

## 1. Normes de Chiffrement

Nous employons des stratégies de chiffrement en profondeur qui dépassent les normes de l'industrie.

### Données au Repos

- **Algorithme** : AES-256-GCM.
- **Gestion des Clés** : Rotation granulaire des clés avec des clés distinctes pour les ensembles de données disjoints.
- **Portée** : Tous les stockages persistants, y compris les sauvegardes et les journaux.

### Données en Transit

- **Protocole** : TLS 1.3 uniquement (nous ne prenons pas en charge les versions héritées TLS 1.0/1.1 ou les suites de chiffrement non sécurisées).
- **Épinglage de Certificat** : Les SDK mobiles imposent l'épinglage de certificat pour empêcher les attaques de type MitM (Homme du milieu).
- **HSTS** : La sécurité de transport stricte (Strict Transport Security) est imposée pour tous les points de terminaison web.

### Chiffrement au Niveau Applicatif

Pour les champs hautement sensibles (comme les données personnelles utilisées pour la correspondance), nous effectuons un chiffrement au niveau de l'application _avant_ que les données n'atteignent la couche de base de données, garantissant que même un administrateur de base de données ne puisse lire les valeurs brutes.

## 2. Modèle d'Isolation des Données

Protegey met en œuvre une **séparation physique des données** au niveau de la base de données, et pas seulement une isolation logique. Cela fournit une défense en profondeur contre les fuites de données.

### Le Problème de l'Isolation Logique

Les systèmes multi-locataires traditionnels utilisent l'isolation logique (WHERE partenaire_id = X). Vulnérabilités :

- L'injection SQL peut contourner les clauses WHERE
- Des bogues applicatifs peuvent omettre les conditions de cadrage
- Une mauvaise configuration de l'ORM peut exposer des données d'autres locataires
- Des erreurs d'administration de la base de données peuvent entraîner des fuites de données

### La Solution Protegey : Isolation Physique par Schéma

**Séparation au niveau du schéma PostgreSQL** :

```
Base de données PostgreSQL
├── schéma public (Production + Partagé)
│   ├── signals (données des partenaires en production)
│   ├── fraud_entities (données des partenaires en production)
│   ├── fraud_cases (données des partenaires en production)
│   ├── users (partagé - RBAC)
│   ├── partners (partagé - organisations)
│   └── subscriptions (partagé - facturation)
│
└── schéma sandbox (Environnement Sandbox)
    ├── signals (données des partenaires en sandbox)
    ├── fraud_entities (données des partenaires en sandbox)
    ├── fraud_cases (données des partenaires en sandbox)
    └── [toutes les tables à portée partenaire dupliquées]
```

**Avantages en matière de sécurité** :

1. **Séparation Physique** : Les données du sandbox ne peuvent pas fuiter en production (schéma différent)
2. **Application Automatique** : Le `search_path` de PostgreSQL empêche les requêtes inter-schémas
3. **Défense en Profondeur** : Même si le code applicatif présente des bogues, la base de données impose la séparation
4. **Audit Facilité** : Les journaux d'accès au niveau du schéma montrent quelles données ont été consultées
5. **Isolation des Performances** : Les requêtes sandbox n'impactent pas les performances de la production

### Exécution Sensible au Contexte

Chaque opération s'exécute au sein d'un **CentryContext** immuable :

```php
CentryContext {
  environment: 'production' | 'sandbox'
  partner_uuid: string          // Identité du partenaire
  request_id: string            // Identifiant de traçage
  schema: 'public' | 'sandbox'  // Dérivé de l'environnement
}
```

**Flux d'Application du Contexte** :

```
1. La requête HTTP arrive
   ↓
2. Authentification (vérification de la clé API/session)
   ↓
3. Résolution du CentryContext
   - Détecter l'environnement (sandbox/production)
   - Extraire l'UUID du partenaire
   - Générer l'ID de requête
   ↓
4. Appliquer l'Isolation du Schéma
   - SET search_path TO {schema}, public
   - Mettre à jour les noms des tables de permissions
   - Marquer le schéma comme appliqué
   ↓
5. Exécuter le Code Applicatif
   - Toutes les requêtes utilisent le schéma correct automatiquement
   - Cadrage de l'UUID du partenaire appliqué
   ↓
6. Retourner la Réponse
   - Contexte préservé dans les journaux
```

**Validation par Échec Immédiat** :

```php
// Contexte requis avant toute opération de base de données
CentryContext::assertBound(); // Lance une exception s'il n'est pas lié

// Obtenir le contexte ou échouer
$context = CentryContext::getOrFail();

// Toutes les requêtes sont automatiquement cadrées
Signal::where('partner_uuid', $context->partnerUuid())->get();
// Lit dans : {schema}.signals WHERE partner_uuid = X
```

**Préservation du Contexte pour les Tâches de File d'Attente** :

```php
// Contexte capturé au moment de l'envoi
class ProcessFraudSignal extends ContextAwareJob {
    public function __construct(private string $signalId) {
        parent::__construct(); // Capture le contexte actuel
    }

    protected function perform(): void {
        // Contexte automatiquement restauré chez le worker
        // Les requêtes utilisent le schéma correct
        $signal = Signal::find($this->signalId);
    }
}
```

### Cadrage Multi-Locataire

**Application de l'UUID du Partenaire** :

- Chaque requête API est authentifiée pour un partenaire spécifique
- Toutes les requêtes de base de données incluent le filtre `partner_uuid`
- Les requêtes inter-partenaires sont explicitement interdites
- Cadrage automatique des requêtes via un middleware

**Schéma + UUID = Double Protection** :

```sql
-- Requête du partenaire A en Sandbox
SET search_path TO sandbox, public;

SELECT * FROM signals
WHERE partner_uuid = 'partner-a-uuid'
AND risk_score >= 80;

-- Retourne uniquement :
-- 1. Données du sandbox (application du schéma)
-- 2. Données du Partenaire A (application de l'UUID)
-- 3. Signaux à haut risque (filtre applicatif)
```

### Garanties de Ségrégation des Données

**Ce qui est Isolé** :

- ✅ Signaux de fraude (par partenaire, par environnement)
- ✅ Profils d'entités (par partenaire, par environnement)
- ✅ Dossiers et enquêtes (par partenaire)
- ✅ Alertes (par partenaire)
- ✅ Données de surveillance des transactions (par partenaire)
- ✅ Analyses et tableaux de bord (par partenaire)

**Ce qui est Partagé** (par conception) :

- ✅ Utilisateurs et authentification (RBAC)
- ✅ Paramètres de l'organisation partenaire
- ✅ Abonnements et facturation
- ✅ Rôles et autorisations (Spatie, schéma public)

**Ce qui est Agrégé** (respect de la confidentialité) :

- ✅ Modèles de fraude mondiaux (anonymisés)
- ✅ Modèles de scoring des risques (aucune donnée personnelle brute)
- ✅ Intelligence du réseau (identifiants hachés)

### Agrégation vs. Exposition

Bien que l'_intelligence_ (scores, modèles) soit dérivée des données réseau agrégées, les _signaux bruts_ soumis par le Partenaire A restent invisibles pour le Partenaire B.

- **Le Partenaire A** envoie : "L'utilisateur X a commis une fraude."
- **Le Partenaire B** demande : "L'utilisateur X est-il risqué ?"
- **Protegey** répond : "Oui, risque élevé en raison de l'historique du réseau." (La source n'est jamais révélée).

**Agrégation Respectueuse de la Vie Privée** :

```
Signal Brut (Partenaire A uniquement) :
  acteur : "hash_0244567890"
  transaction : 15 000 GHS
  appareil : "d3v1c3-f1ng3rpr1nt"

Modèle Agrégé (À l'échelle du réseau) :
  actor_hash : "hash_0244567890"
  fraud_count : 3
  avg_risk_score : 87
  linked_entities : 7

  // PAS de montants de transaction bruts
  // PAS d'identités de partenaires
  // PAS de détails de transaction spécifiques
```

## 2a. Validation du Contexte et Sécurité

### Validation de l'Environnement

**Application Stricte de l'Environnement** :

- Seuls deux environnements valides : `production`, `sandbox`
- Une chaîne d'environnement invalide lance une exception
- Aucun environnement = `production` par défaut (valeur par défaut sécurisée)
- Immuabilité de l'environnement (ne peut pas changer en cours de requête)

**Validation de l'UUID du Partenaire** :

```php
// Rejeter les UUID invalides
if ($partnerUuid !== null && !Str::isUuid($partnerUuid)) {
    throw new InvalidArgumentException(
        "Format d'UUID partenaire invalide : {$partnerUuid}"
    );
}
```

### Traçage des Requêtes

**ID de Requête Uniques** :

- Chaque requête reçoit un UUID unique
- L'ID de requête circule tout au long du cycle de vie de la requête
- Apparaît dans tous les journaux pour la corrélation
- Inclus dans les réponses d'erreur pour le support

**Traçage Distribué** :

```
Requête HTTP : req_abc123
  ↓
Envoi de tâche : req_abc123 (contexte sérialisé)
  ↓
Worker de file d'attente : req_abc123 (contexte restauré)
  ↓
Livraison de webhook : req_abc123 (contexte dans le payload)
```

### Sécurité de l'Application du Schéma

**Ordre des Middlewares Critique** :

```php
// Pile de middlewares Kernel.php
protected $middlewareGroups = [
    'api' => [
        'throttle:api',
        ResolveCentryContext::class,      // 1. PREMIER : Résoudre le contexte
        EnforceSchemaIsolation::class,    // 2. DEUXIÈME : Appliquer le schéma
        'auth:api',                        // 3. Puis l'authentification
        // ... reste des middlewares
    ],
];
```

**Pourquoi l'ordre importe** :

- Le contexte doit exister avant les requêtes d'authentification
- Le schéma doit être défini avant les vérifications de permissions RBAC
- Toutes les requêtes de base de données doivent utiliser le bon schéma

**Application Idempotente du Schéma** :

```php
// Ne définir le search_path qu'une seule fois
if (app()->has('schema.enforced')) {
    return; // Déjà appliqué, ignorer
}

DB::statement("SET search_path TO {$schema}, public");
app()->instance('schema.enforced', true);
```

### Sécurité du Sandbox

**Gardes de Production** :

```php
// Génération de signaux de démonstration
if (!$context->isSandbox()) {
    throw new UnauthorizedException(
        'La génération de signaux de démo n\'est disponible qu'en sandbox'
    );
}

// Fonctionnalité de réinitialisation
if (!$context->isSandbox()) {
    throw new UnauthorizedException(
        'La réinitialisation n\'est disponible qu'en sandbox'
    );
}
```

**Limitation du Débit** :

- Sandbox : 100 requêtes/minute
- Production : 1000 requêtes/minute
- Génération de démo : 3 requêtes/heure (sandbox uniquement)

**Marquage des Métadonnées** :

```json
{
  "signal_id": "sig_abc123",
  "metadata": {
    "generated_by": "centry_demo",
    "sandbox_batch_id": "batch_xyz789",
    "environment": "sandbox"
  }
}
```

### Surveillance de la Sécurité

**Détection d'Anomalies** :

- Tentatives de requêtes inter-schémas inhabituelles
- Échecs répétés de résolution de contexte
- Échecs d'authentification répétés
- Utilisation suspecte de clé API

**Alertes** :

- Échecs de liaison de contexte (critique)
- Échecs d'application de schéma (critique)
- Tentatives de requêtes inter-locataires (critique)
- Modèles d'accès inhabituels (élevé)

## 3. Philosophie du Contrôle d'Accès

Nous suivons le principe du moindre privilège (PoLP) tant pour les systèmes internes que pour l'accès aux partenaires.

### Accès Partenaire

- **Clés API** : Système à double clé (ID public + Clé secrète).
- **Permissions Cadrées** : Les clés peuvent être limitées à des permissions spécifiques (`signals:write`, `queries:read`) et à des environnements.
- **Liste Blanche d'IP** : Les partenaires peuvent restreindre l'accès API à des blocs CIDR spécifiques.

### Accès Interne

- **Pas d'accès en écriture en Production** : Les développeurs n'ont pas d'accès en écriture aux bases de données de production.
- **Accès Éphémère** : L'accès opérationnel aux données de production nécessite une demande authentifiée et limitée dans le temps avec MFA.
- **Journalisation d'Audit** : Chaque requête interne est enregistrée, analysée pour détecter des anomalies et liée à l'identité d'un employé spécifique.

## 4. Cycle de Vie du Développement Sécurisé (SDLC)

La sécurité est intégrée dans notre code, et non ajoutée après coup.

- **Analyse Statique** : Scans SAST automatisés sur chaque pull request.
- **Analyse des Dépendances** : Surveillance automatisée de toutes les bibliothèques tierces pour les vulnérabilités (CVE).
- **Revue par les Pairs** : Revue de code obligatoire avec des listes de contrôle de sécurité spécifiques.
- **Tests d'Intrusion** : Audits annuels par des tiers et programme continu de primes aux bogues (bug bounty).

## 5. Divulgation des Vulnérabilités

Nous accueillons favorablement la divulgation responsable de la part de la communauté de recherche en sécurité.

- **Programme** : Voir notre fichier `security.txt` ou notre [Politique de Divulgation des Vulnérabilités](/fr/resources/contact).
- **Sphère de sécurité (Safe Harbor)** : Les chercheurs agissant de bonne foi sont protégés contre toute action en justice.
