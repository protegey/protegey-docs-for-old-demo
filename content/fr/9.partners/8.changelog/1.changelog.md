## v1.17.0 — Tableau de bord Santé de l'intégration & Alertes proactives
*Publiée le 2026-05-21*

- **Nouveau** : Tableau de bord Santé de l'intégration (`/integration` dans le portail partenaire) — score noté A–F (0–100) indiquant quels types de signaux sont envoyés, quels détecteurs sont opérationnels et quels champs sont manquants. Le score est décomposé en quatre dimensions : couverture des signaux (40 pts), complétude des champs (40 pts), diversité des signaux (15 pts), disponibilité des détecteurs (5 pts).
- **Nouveau** : Alertes de dégradation proactives — si un type de signal critique actif au cours des 30 derniers jours cesse d'être envoyé pendant 48 heures consécutives, un e-mail de notification est envoyé à votre adresse de contact d'intégration. Les alertes ont un délai de récupération de 72 heures par type de signal.
- **Nouveau** : Score de complétude persisté — chaque signal ingéré stocke désormais un `completeness_score` (0,0–1,0) pour l'analytique et le suivi des jalons.
- **Nouveau** : Contrôle qualité des jalons — le jalon d'intégration « premier signal envoyé » exige désormais un score de complétude minimal (0,3) pour éviter que des charges utiles de test basiques ne ferment prématurément le jalon.
- **Amélioration** : Réalisme du simulateur sandbox — les modèles de signaux de démo génèrent désormais des charges utiles plus riches pour produire des scores significatifs durant les tests d'intégration.
- **Amélioration** : Page Santé de l'intégration entièrement traduite (EN + FR).

## v1.16.0 — Détection croisée de signaux et d'acteurs (Phase S)
*Publiée le 2026-05-15*

Quatre nouveaux détecteurs portent le total à **9 détecteurs actifs**. Ils identifient des schémas de fraude couvrant plusieurs signaux et plusieurs acteurs — des lacunes que les détecteurs mono-signal ne peuvent couvrir.

- **Nouveau** : `AttackChainDetector` — reconnaît les séquences d'attaque en plusieurs étapes pour le même acteur dans une fenêtre temporelle. Deux chaînes livrées :
  - `ATO_SIM_SWAP` : `ACCOUNT_TAKEOVER` → `PAYMENT_FRAUD` en 60 minutes (confiance 0,92)
  - `SOCIAL_TO_PAYMENT` : `SOCIAL_ENGINEERING` → `PAYMENT_FRAUD` en 120 minutes (confiance 0,80)
- **Nouveau** : `BeneficiaryConcentrationDetector` — se déclenche lorsque de nombreux acteurs différents envoient des fonds au même bénéficiaire (entonnoir d'arnaque à l'investissement, compte mule). Notation par paliers : ≥20 émetteurs uniques → risque maximum +35 ; ≥10 → +25 ; ≥5 → +15.
- **Nouveau** : `AgentConcentrationDetector` — même schéma au niveau des nœuds d'encaissement agent. Se déclenche lorsque de nombreux acteurs encaissent via le même agent dans le graphe de fraude.
- **Nouveau** : `SessionAnomalyDetector` — signale les sessions aux caractéristiques comportementales impossibles (interactions à vitesse bot, sessions concurrentes impossibles).
- **Graphe** : Les nœuds AGENT sont désormais matérialisés dans le graphe de fraude à partir de `related_entities` dans les signaux UFES v2 mobile/USSD. La détection de concentration d'agents nécessite que ce champ soit renseigné.
- **Aucune rupture de compatibilité** : Les identifiants de détecteurs et les formats de réponse API existants sont inchangés. Les nouveaux détecteurs apparaissent dans les tableaux `detectors_triggered` lorsqu'ils se déclenchent.

## v1.14.0 — Moteur de règles configurable (Phase R)
*Publiée le 2026-03-25*

- **Nouveau** : API des règles de conformité — les partenaires Enterprise peuvent consulter, paramétrer et activer/désactiver les règles AML sans déploiement de code. 4 endpoints : `GET /compliance/rules`, `GET /compliance/rules/{uuid}`, `PUT /compliance/rules/{uuid}/config`, `DELETE /compliance/rules/{uuid}/config`
- **Nouveau** : 9 règles AML codées désormais sauvegardées en base de données avec `parameter_schema` complet pour le rendu UI : `structuring_detection`, `velocity_1h_limit`, `high_risk_corridor`, `currency_transaction_report`, `mobile_money_velocity`, `cross_border_corridor`, `dormant_account_activation`, `auto_str_correlation`, `round_number_detection`
- **Nouveau** : Remplacements de seuils par devise — les partenaires peuvent remplacer les seuils AML par code ISO 4217 via les paramètres `currency_overrides` (ex. définir le seuil de structuration GNF indépendamment du seuil universel de secours)
- **Nouveau** : 31 devises couvertes dans les seuils AML — ajout de GNF, SLE, LRD, GMD, MRU, AOA, BWP, NAD, MWK, BIF, MGA (11 nouvelles devises africaines)
- **Nouveau** : Page de configuration des règles dans le portail partenaire — `/compliance/rules` avec onglets par catégorie, dialogue de configuration, liste de pays, éditeur de carte de devises et réinitialisation aux valeurs par défaut
- **Nouveau** : Paramètres `auto_str_correlation` configurables — `window_hours` (défaut 72h) et `dedup_hours` (défaut 72h) sont remplaçables par le partenaire
- **Protection** : Les règles système (`nufss_fusion_weights`, `sanctions_blocking`, `audit_log_creation`) ne peuvent pas être désactivées — retourne `403`

## v1.7.0

_Publiée le : 2026-02-18_

### Gestion Multi-Endpoints de Webhooks

Le système de webhooks a été entièrement repensé. Les partenaires peuvent désormais enregistrer plusieurs endpoints webhook, chacun avec son propre secret, ses abonnements aux événements et son journal de livraison.

- **Nouveau** : `GET/POST /api/v1/partner/webhooks` — lister et créer des endpoints webhook
- **Nouveau** : `GET/PUT/DELETE /api/v1/partner/webhooks/{id}` — gérer les endpoints individuels
- **Nouveau** : `GET /api/v1/partner/webhooks/{id}/deliveries` — journal de livraison par endpoint
- **Nouveau** : `POST /api/v1/partner/webhooks/{id}/deliveries/{deliveryId}/retry` — relancer une livraison échouée
- **Nouveau** : `POST /api/v1/partner/webhooks/{id}/test` — envoyer un ping de test pour vérifier la configuration
- **Nouveau** : Secrets HMAC-SHA256 par endpoint — chaque endpoint dispose de son propre secret, affiché une seule fois à la création
- **Nouveau** : Abonnements aux événements par endpoint — choisir quels types d'événements chaque endpoint reçoit
- **En-têtes** : L'en-tête de signature est `X-Centry-Signature` ; les en-têtes de livraison sont `X-Centry-Event`, `X-Centry-Delivery-ID`, `X-Centry-Timestamp`
- **Changement** : Les endpoints sont automatiquement désactivés après **3 échecs de livraison consécutifs**
- **Nouveaux événements** : `alert.created`, `alert.status_changed`, `case.status_changed`, `case.priority_changed`, `case.assigned`, `entity.risk_changed`, `signal.ingested`
