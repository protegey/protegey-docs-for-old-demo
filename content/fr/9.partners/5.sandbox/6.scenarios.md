La simulation de scénarios multi-étapes vous permet de tester des modèles de fraude complexes qui se déroulent dans le temps, imitant les schémas d'attaque du monde réel.

## Concept

Contrairement aux signaux de démo uniques, les **scénarios** génèrent une séquence de signaux liés qui représentent une attaque de fraude coordonnée :

### Exemple : Vidage de Compte après SIM Swap

1. **Étape 1** (T+0 min) : Connexion initiale à partir d'un nouvel appareil → Génère un signal `ACCOUNT_TAKEOVER`.
2. **Étape 2** (T+5 min) : Échec de la vérification par téléphone → Génère un signal `PHONE_VERIFICATION_FAILURE`.
3. **Étape 3** (T+10 min) : Détection de SIM swap → Génère un signal `SIM_SWAP`.
4. **Étape 4** (T+12 min) : Transfert de haute valeur vers un compte externe → Génère un signal `TRANSACTION` (risque critique).
5. **Étape 5** (T+15 min) : Multiples petits retraits → Génère plusieurs signaux `TRANSACTION` (modèle de vélocité).

## Caractéristiques Clés (Prévu)

### Données d'Acteur Cohérentes

Toutes les étapes d'un scénario partagent les mêmes identifiants d'acteur (numéro de téléphone, appareil d'origine, etc.), créant ainsi un modèle de fraude cohérent :

```json
{
  "scenario_variables": {
    "SCENARIO_PHONE": "0244123456",
    "SCENARIO_ACCOUNT_ID": "ACC-12345"
  }
}
```

Ces variables sont résolues une seule fois au début du scénario et réutilisées dans toutes les étapes.

### Délais Temporels

Les scénarios se déroulent sur des périodes réalistes :

```json
{
  "step": 3,
  "delay": 600, // 10 minutes après le début du scénario
  "template": "sim_swap"
}
```

**Modes de Délai** :

- **Temps réel** : Délais réels (pour les tests en direct).
- **Avance rapide** : Délais accélérés (1 seconde = 1 minute) pour des tests rapides.
- **Immédiat** : Aucun délai (pour les tests de masse).

### Suivi par Lot

Tous les signaux d'un scénario sont marqués avec un ID de lot (Batch ID) partagé :

```json
{
  "metadata": {
    "generated_by": "centry_scenario",
    "scenario_name": "sim_swap_drainage",
    "scenario_batch_id": "scenario_1738598400_abc123",
    "scenario_step": 3,
    "scenario_total_steps": 5
  }
}
```

Cela vous permet de :

- Filtrer les signaux par scénario.
- Suivre la complétion du scénario.
- Visualiser les chronologies d'attaque.
- Tester la logique de liaison des dossiers.

### Événements de Simulation (Prévu)

Les scénarios émettent des événements en temps réel pendant l'exécution :

```json
{
  "event": "scenario.step_completed",
  "scenario_id": "scenario_1738598400_abc123",
  "step": 3,
  "total_steps": 5,
  "signals_created": 1,
  "next_step_delay": 120
}
```

## Points de Terminaison API (Prévu)

### Lister les Scénarios Disponibles

```bash
GET /api/v1/partner/sandbox/scenarios
```

**Réponse** :

```json
{
  "scenarios": [
    {
      "name": "sim_swap_drainage",
      "title": "Vidage de Compte après SIM Swap",

      "steps": 5,
      "estimated_duration": "30 minutes",
      "risk_indicators": ["sim_swap", "velocity", "cross_border"]

  ]
}
```

```bash
POST /api/v1/partner/sandbox/simulate
{
  "scenario": "sim_swap_drainage",
  "mode": "fast-forward",
  "overrides": {
    "SCENARIO_PHONE": "0244123456"
  }
}
```


## Cas d'Utilisation

### Tester la Logique de Liaison des Dossiers

Exécutez des scénarios pour vérifier que votre système de détection de fraude effectue correctement :

- La liaison des signaux liés au même acteur.
- L'escalade des signaux vers les alertes et les dossiers.
- La priorisation des dossiers basée sur la gravité du modèle.

### Tester les Flux d'Enquête

Utilisez des scénarios pour former les analystes à :

- Reconnaître les modèles d'attaque coordonnée.
- Trier les alertes par chronologie.
- Identifier le modus operandi à partir des séquences de signaux.

### Tester l'Escalade des Alertes

Vérifiez que les règles d'alerte se déclenchent correctement au fur et à mesure que les scénarios se déroulent :

- **Après l'Étape 1** : Alerte de faible priorité (changement d'appareil).
- **Après l'Étape 3** : Alerte de haute priorité (SIM swap détecté).
- **Après l'Étape 5** : Alerte critique (modèle de vidage à haute vélocité).

### Tests de Performance

Lancez plusieurs scénarios simultanément pour tester la charge du système :

```bash
POST /api/v1/partner/sandbox/simulate-batch
{
  "scenarios": [
    {"scenario": "sim_swap_drainage", "count": 10},
    {"scenario": "account_takeover_cascade", "count": 5}
  ],
  "mode": "fast-forward"
}
```

## Scénarios par détecteur

Les scénarios suivants sont conçus pour déclencher de manière fiable des détecteurs de fraude spécifiques. Utilisez-les pour tester votre pipeline de traitement des alertes et vérifier que votre intégration traite correctement chaque type de détecteur.

### 1. Rafale de vélocité — `RAPID_TRANSACTION_VELOCITY`

Envoyez **12 signaux** pour le même `entity_id` dans une fenêtre de 45 minutes. Chaque signal doit avoir `event_type: PAYMENT_FRAUD` et un montant modeste (< seuil de structuration). Le 10e signal déclenchera `RAPID_TRANSACTION_VELOCITY`.

```bash
# Loop 12 times with the same entity_id
for i in $(seq 1 12); do
  curl -X POST https://api.protegey.com/api/v1/signals \
    -H "X-API-Key: $SANDBOX_KEY" \
    -d '{"event_type":"PAYMENT_FRAUD","primary_actor":{"entity_id":"test-entity-burst-001"},"event_payload":{"amount":150,"currency":"USD"}}'
  sleep 3
done
```

**Résultat attendu** : Alerte avec `detectors_triggered: ["RAPID_TRANSACTION_VELOCITY"]`, risk_level `high`.

---

### 2. Transaction aberrante — `LARGE_OUTLIER_TRANSACTION`

Commencez par établir une ligne de base en envoyant **10 signaux** pour la même entité avec des montants entre 50 et 200 USD. Envoyez ensuite un signal avec `amount: 2500`. Le z-score dépassera 3,0 et déclenchera `LARGE_OUTLIER_TRANSACTION`.

**Résultat attendu** : Alerte avec `detectors_triggered: ["LARGE_OUTLIER_TRANSACTION"]`, `fusion.behavioral_score > 0.7`.

---

### 3. Attaque par SIM swap — `SIM_SWAP_PROXIMITY`

Envoyez un signal incluant `sim_changed_at` défini **90 minutes auparavant** combiné à une nouvelle empreinte d'appareil (vue pour la première fois). Cela simule une prise de contrôle de compte suite à un SIM swap.

```json
{
  "event_type": "ACCOUNT_TAKEOVER",
  "primary_actor": {
    "entity_id": "test-entity-simswap-001",
    "identifiers": {
      "msisdn": "hash:msisdn",
      "sim_changed_at": "{{ now | minus: 90 | iso8601 }}"
    },
    "device": {
      "fingerprint": "{{ uuid }}",
      "is_first_seen": true
    }
  }
}
```

**Résultat attendu** : Alerte avec `detectors_triggered: ["SIM_SWAP_PROXIMITY"]`.

---

### 4. Nouvel appareil + géographie à haut risque — `NEW_DEVICE_ACCESS`

Envoyez un signal avec une empreinte d'appareil vue pour la première fois et une IP source qui se résout vers une juridiction à haut risque (par exemple, le Nigeria via le GeoResolver).

```json
{
  "event_type": "ACCOUNT_TAKEOVER",
  "primary_actor": {
    "entity_id": "test-entity-newdevice-001",
    "device": {
      "fingerprint": "{{ uuid }}"
    }
  },
  "source": {
    "ip_address": "197.210.0.1"
  }
}
```

**Résultat attendu** : Alerte avec `detectors_triggered: ["NEW_DEVICE_ACCESS"]`.

---

### 5. Déplacement impossible — `IMPOSSIBLE_TRAVEL`

Envoyez deux signaux pour la même entité dans un délai de **90 minutes** — l'un avec une adresse IP ghanéenne, l'autre avec une adresse IP française. Le GeoResolver calculera la distance et déclenchera le détecteur de déplacement impossible.

**Signal 1** — IP se résolvant vers Accra, Ghana : `source.ip_address: "154.160.0.1"`
**Signal 2** (90 min plus tard) — IP se résolvant vers Paris, France : `source.ip_address: "2.2.0.1"`

**Résultat attendu** : Le second signal déclenche une alerte avec `detectors_triggered: ["IMPOSSIBLE_TRAVEL"]`.

---

### 6. Anneau de fraude — réseau graphique — visualisation du graphe

Créez **3 entités** partageant la même `device.fingerprint`. Envoyez 2 à 3 signaux par entité. Après l'ingestion, appelez `GET /entities/{uuid}/graph-visualization` sur l'une des trois entités.

**Résultat attendu** : La réponse graphique montre les 3 entités connectées via des arêtes `shared_device` avec un poids ≥ 0,9. Le `propagated_risk` de chaque entité reflète le risque agrégé du réseau.
