title: Architecture du Sandbox
description: Plongée au cœur de la mise en œuvre du sandbox de Protegey utilisant l'isolation des schémas PostgreSQL et l'exécution sensible au contexte.
---

Protegey met en œuvre une **véritable isolation au niveau de la base de données** pour les environnements sandbox, garantissant une séparation complète entre les données sandbox et de production au niveau du schéma PostgreSQL.

## Isolation des Schémas PostgreSQL

### Séparation Physique

Contrairement à une séparation logique (ex : `WHERE environment = 'sandbox'`), Protegey utilise une **séparation physique des schémas** :

```
protegey_database
├── schéma public (production)
│   ├── signals
│   ├── fraud_cases
│   ├── fraud_entities
│   ├── fraud_alerts
│   └── ... (toutes les tables à portée partenaire)
│
├── schéma sandbox (sandbox)
│   ├── signals
│   ├── fraud_cases
│   ├── fraud_entities
│   ├── fraud_alerts
│   └── ... (tables dupliquées à portée partenaire)
│
└── tables partagées (uniquement dans public)
    ├── users
    ├── partners
    ├── subscriptions
    ├── plans
    └── invoices
```

### Avantages de l'Isolation des Schémas

| Avantage                           | Description                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| **Zéro Pollution des Analyses**    | Les signaux sandbox n'affectent jamais les métriques de production ni le scoring de risque |
| **Réinitialisation Facile**        | `TRUNCATE sandbox.signals` efface instantanément toutes les données sandbox                |
| **Isolation des Performances**     | Les requêtes sandbox n'entrent pas en concurrence avec les index de production             |
| **Prêt pour la Conformité**        | Séparation physique pour les exigences réglementaires de ségrégation des données           |
| **Stratégie de Sauvegarde Simple** | Sauvegardez le schéma `public` sans les données de test du sandbox                         |

### Comment fonctionne l'application du schéma

Chaque requête définit automatiquement le `search_path` de PostgreSQL :

```sql
-- Requête Sandbox
SET search_path TO sandbox, public;

-- Requête de Production
SET search_path TO public, public;
```

Cela signifie que :

1. Toutes les requêtes utilisent automatiquement le bon schéma.
2. Pas besoin de préfixer les noms de table avec le schéma (ex : `sandbox.signals`).
3. Les tables partagées (utilisateurs, partenaires) sont toujours dans `public`, elles fonctionnent donc sans interruption.

::callout{type="info"}
**Détail Technique** : Le middleware `EnforceSchemaIsolation` s'exécute après l'authentification et définit le schéma en fonction du `CentryContext` résolu. C'est une opération idempotente qui peut être exécutée plusieurs fois sans problème.
::

## CentryContext : Contexte d'Exécution Immuable

Le `CentryContext` est un objet immuable qui encapsule tout l'état de l'environnement pour une requête ou une tâche.

### Structure du Contexte

```php
CentryContext {
  environment: 'sandbox' | 'production'
  partnerUuid: string | null
  requestId: string | null
  metadata: array
}
```

### Création du Contexte

```php
// Créer un contexte sandbox
$context = CentryContext::sandbox($partnerUuid);

// Créer un contexte de production
$context = CentryContext::production($partnerUuid);

// Détecter à partir d'une requête HTTP
$context = CentryContext::fromRequest($request);

// Avec des métadonnées
$context = CentryContext::sandbox($partnerUuid)
    ->withMetadata(['user_id' => $userId]);
```

### Méthodes du Contexte

| Méthode          | Retourne       | Description                                         |
| ---------------- | -------------- | --------------------------------------------------- |
| `environment()`  | `string`       | Obtenir le nom de l'environnement                   |
| `partnerUuid()`  | `string\|null` | Obtenir l'UUID du partenaire                        |
| `requestId()`    | `string\|null` | Obtenir l'ID de suivi de la requête                 |
| `metadata()`     | `array`        | Obtenir les métadonnées supplémentaires             |
| `isSandbox()`    | `bool`         | Vérifier s'il s'agit du sandbox                     |
| `isProduction()` | `bool`         | Vérifier s'il s'agit de la production               |
| `schema()`       | `string`       | Obtenir le nom du schéma DB (`sandbox` ou `public`) |

## Priorité de Détection de l'Environnement

Lors du traitement d'une requête, le système résout l'environnement dans cet ordre :

1. **Paramètre de requête** : `?environment=sandbox`

   ```bash
   https://api.protegey.com/api/v1/signals?environment=sandbox
   ```

2. **Surcharge par Session/Cookie** : cookie `centry_env_override`

   ```javascript
   // À définir dans la console du navigateur pour un basculement persistant
   document.cookie = "centry_env_override=sandbox; path=/";
   ```

3. **En-tête de requête** : en-tête `X-Centry-Environment`

   ```bash
   curl -H "X-Centry-Environment: sandbox" \
     https://api.protegey.com/api/v1/signals
   ```

4. **Détection de domaine** : sous-domaine `sandbox.*`

   ```
   https://sandbox.api.protegey.com/api/v1/signals
   ```

5. **En-tête Referer** : Pour les appels API cross-origin depuis le Portail Partenaire

   ```
   Referer: https://sandbox.partner.protegey.com/...
   ```

6. **Utilisateur Authentifié** : Statut d'environnement du partenaire

   ```php
   if ($user->partner->is_sandbox) {
       $environment = 'sandbox';
   }
   ```

7. **Défaut** : `production` (sécurité intégrée / fail-safe)

::callout{type="warning"}
**Note de Sécurité** : La détection de l'environnement est toujours validée par rapport aux environnements autorisés pour le partenaire authentifié. Vous ne pouvez pas accéder aux données de production si vous êtes authentifié auprès d'un partenaire réservé au sandbox.
::

## Exécution Sensible au Contexte

### Requêtes HTTP

```
Requête HTTP
    ↓
[Middleware ResolveCentryContext]
    ↓
[Middleware EnforceSchemaIsolation]
    ↓
Contrôleur → Requête de Modèle
    ↓
PostgreSQL (schéma correct)
```

**Pile de Middlewares** :

```php
Route::middleware([
    'auth:api',
    'resolve.context',      // Crée le CentryContext
    'enforce.schema',       // Définit le search_path
])->group(function () {
    // Toutes les routes ici ont le bon schéma
});
```

### Tâches en File d'Attente (Queue Jobs)

Pour le traitement asynchrone, le contexte doit être préservé au-delà de la frontière de la file d'attente.

**Classe de Base ContextAwareJob** :

```php
use App\Jobs\ContextAwareJob;

class ProcessFraudSignal extends ContextAwareJob
{
    public function __construct(private string $signalId) {
        parent::__construct(); // Capture le contexte actuel
    }

    protected function perform(): void {
        // Contexte déjà restauré
        // Toutes les requêtes utilisent le bon schéma
        $signal = Signal::find($this->signalId);
        // ... logique de scoring de fraude
    }
}
```

**Comment ça marche** :

1. **Temps d'envoi (Dispatch)** : Le constructeur capture le `CentryContext` actuel depuis le conteneur de services.
2. **Sérialisation** : Le contexte est sérialisé et stocké avec le corps de la tâche.
3. **Exécution par le Worker** : Le contexte est restauré avant l'exécution de `perform()`.
4. **Application du Schéma** : Le `search_path` est défini automatiquement.

::callout{type="danger"}
**Critique** : Toutes les tâches en file d'attente DOIVENT étendre `ContextAwareJob` pour garantir l'isolation correcte des schémas. Les tâches qui n'étendent pas cette classe de base échoueront avec une `MissingContextException` si elles essaient d'être envoyées sans contexte lié.
::

### Commandes CLI

Pour les commandes Artisan qui envoient des tâches, vous devez lier explicitement le contexte :

```php
use App\Context\CentryContext;

class GenerateDemoSignalsCommand extends Command
{
    public function handle()
    {
        $partnerUuid = $this->argument('partner');

        // Lier le contexte sandbox
        app()->instance(
            CentryContext::class,
            CentryContext::sandbox($partnerUuid)
        );

        // Maintenant, les tâches envoyées par cette commande héritent du contexte
        ProcessFraudSignal::dispatch($signalId);
    }
}
```

## Garanties d'Isolation des Données

### Ce qui est Isolé

✅ **Tables à portée partenaire** (dupliquées dans le schéma `sandbox`) :

- `signals`
- `fraud_cases`
- `fraud_entities`
- `fraud_alerts`
- `case_notes`
- `case_evidence`
- Toutes les données opérationnelles spécifiques au partenaire

### Ce qui est Partagé

🔗 **Tables partagées** (uniquement dans le schéma `public`) :

- `users` - Comptes utilisateurs
- `partners` - Organisations partenaires
- `subscriptions` - Abonnements de facturation
- `plans` - Plans d'abonnement
- `invoices` - Factures
- `partner_api_keys` - Clés API (avec indicateur d'environnement)
- Tables de configuration système

::callout{type="info"}
**Pourquoi partager ces tables ?** : La facturation, la gestion des utilisateurs et la configuration système sont globales à l'organisation partenaire. Un enregistrement de partenaire sandbox est lié à son parent de production via `production_parent_uuid`.
::

## Meilleures Pratiques de Test

### Tester l'Isolation des Schémas

```php
// Dans les tests, définir explicitement le contexte
public function test_sandbox_signal_creation()
{
    $this->actingAs($user);

    app()->instance(
        CentryContext::class,
        CentryContext::sandbox($partner->uuid)
    );

    $response = $this->postJson('/api/v1/signals', $payload);

    // Le signal ne doit exister que dans le schéma sandbox
    $this->assertDatabaseHas('sandbox.signals', [
        'partner_uuid' => $partner->uuid,
    ]);

    $this->assertDatabaseMissing('public.signals', [
        'partner_uuid' => $partner->uuid,
    ]);
}
```

### Vérifier la Préservation du Contexte dans les Tâches

```php
public function test_job_preserves_context()
{
    app()->instance(
        CentryContext::class,
        CentryContext::sandbox($partner->uuid)
    );

    ProcessFraudSignal::dispatch($signalId);

    // Après l'exécution de la tâche, le signal doit être scoré dans le sandbox
    $signal = Signal::find($signalId); // Interroge le schéma sandbox
    $this->assertEquals('sandbox', $signal->environment);
}
```

## Sujets Avancés

### Noms de Schémas Personnalisés

Bien que cela ne soit pas recommandé, vous pouvez étendre le système pour supporter des noms de schémas personnalisés :

```php
// Dans CentryContext
public function schema(): string
{
    return match($this->environment) {
        'sandbox' => 'sandbox',
        'staging' => 'staging',
        'production' => 'public',
        default => 'public',
    };
}
```

### Isolation des Schémas Multi-Régions

Pour les déploiements multi-régions, vous pouvez combiner l'isolation des schémas avec une séparation au niveau de la base de données :

```
Région : Afrique de l'Ouest (WA)
└── protegey_wa
    ├── public (production)
    └── sandbox (sandbox)

Région : Afrique de l'Est (EA)
└── protegey_ea
    ├── public (production)
    └── sandbox (sandbox)
```

### Considérations de Performance

**Index** : Chaque schéma maintient ses propres index, donc :

- Les tests sandbox n'affectent pas les statistiques des index de production.
- Vous pouvez supprimer/recréer des index sandbox sans temps d'arrêt.

**Vacuum** : Les schémas sandbox et de production peuvent subir un "vacuum" indépendamment :

```sql
VACUUM ANALYZE sandbox.signals;
```

**Connexions** : L'isolation des schémas utilise le même pool de connexions, donc pas de surcoût de connexion.

## Dépannage

### Erreurs "Table not found"

**Symptôme** : `ERROR: relation "signals" does not exist`

**Cause** : Schéma non défini correctement.

**Solution** : Vérifier l'ordre des middlewares :

```php
// ResolveCentryContext DOIT impérativement précéder EnforceSchemaIsolation
Route::middleware([
    'resolve.context',
    'enforce.schema',
])->group(...);
```

### Tâches écrivant dans le mauvais schéma

**Symptôme** : Tâches sandbox créant des enregistrements en production.

**Cause** : La tâche n'étend pas `ContextAwareJob`.

**Solution** :

```php
// ❌ Incorrect
class MyJob extends Job { ... }

// ✅ Correct
class MyJob extends ContextAwareJob { ... }
```

### Contexte non trouvé dans le CLI

**Symptôme** : `MissingContextException` lors de l'exécution d'une commande Artisan.

**Cause** : Contexte non lié dans l'environnement CLI.

**Solution** :

```php
// Lier le contexte avant d'envoyer des tâches
app()->instance(
    CentryContext::class,
    CentryContext::sandbox($partnerUuid)
);
```

## Considérations de Sécurité

### Validation de l'Environnement

Le système valide l'accès à l'environnement en fonction des permissions du partenaire :

```php
// Le partenaire ne peut accéder au sandbox que si c'est explicitement autorisé
if ($requestedEnvironment === 'sandbox' && !$partner->has_sandbox_access) {
    abort(403, 'L\'accès au Sandbox n\'est pas activé pour ce partenaire');
}
```

### Portée des Clés API par Environnement

Les clés API sont limitées aux environnements :

- **Clés de production** : `cen_live_sk_*` → Peuvent uniquement accéder à la production.
- **Clés de sandbox** : `cen_test_sk_*` → Peuvent uniquement accéder au sandbox.

### Prévention des Fuites de Données entre Environnements

1. **Isolation des schémas** : Séparation physique de la base de données.
2. **Validation du contexte** : Le middleware applique les limites de l'environnement.
3. **Portée des clés API** : Les clés ne peuvent pas traverser les environnements.
4. **Capture du contexte des tâches** : Les tâches asynchrones préservent l'environnement.

::callout{type="success"}
**Résultat** : Risque nul de pollution des métriques de production par les données sandbox ou vice versa.
::
