La gestion des alertes dans Protegey fournit une détection automatique de la fraude avec des seuils personnalisables, permettant à votre équipe de se concentrer sur les menaces prioritaires tout en maintenant une visibilité sur tous les signaux de risque.

::callout{icon="i-lucide-bell" color="amber"}
**Détection automatisée** : Les alertes sont générées automatiquement lorsque les signaux dépassent les seuils de risque, permettant une réponse rapide aux schémas de fraude émergents.
::

---

## Vue d'ensemble

### Qu'est-ce qu'une alerte ?

Une **alerte** est une notification automatisée générée lorsque :

- Un signal de fraude dépasse le seuil de risque configuré
- Les limites de vélocité sont dépassées (fréquence des transactions)
- Des schémas de fraude connus sont détectés
- Des correspondances avec des listes de blocage surviennent
- La détection d'anomalies déclenche une forte confiance

### Alertes vs Signaux vs Dossiers

| Entité      | Description              | Création               | Objectif         |
| ----------- | ------------------------ | ---------------------- | ---------------- |
| **Signal**  | Événement de fraude brut | Ingestion API          | Données d'entrée |
| **Alerte**  | Notification automatisée | Générée par le système | Détection        |
| **Dossier** | Fiche d'enquête          | Manuel/depuis alerte   | Enquête          |

**Flux** :

```
Signal Ingested → Risk Scored → Alert Generated (if threshold met) → Case Created (if needed)
```

---

## Cycle de vie d'une alerte

### Flux de statuts

```
pending → acknowledged → resolved
                ↓
          false_positive
```

| Statut             | Description                          | Actions disponibles                               |
| ------------------ | ------------------------------------ | ------------------------------------------------- |
| **pending**        | Nouvelle alerte en attente de triage | Accuser réception, résoudre, marquer faux positif |
| **acknowledged**   | Analyste informé, en cours d'examen  | Résoudre, marquer faux positif, créer un dossier  |
| **resolved**       | Fraude confirmée, action prise       | Lecture seule                                     |
| **false_positive** | Pas réellement de la fraude          | Lecture seule, ajuster les seuils                 |

### Niveaux de sévérité

| Sévérité     | Plage de score | Description                   | Délai de réponse      |
| ------------ | -------------- | ----------------------------- | --------------------- |
| **low**      | 40-59          | Indicateurs de risque mineurs | Examen sous 24 heures |
| **medium**   | 60-74          | Plusieurs facteurs de risque  | Examen sous 4 heures  |
| **high**     | 75-89          | Forts indicateurs de fraude   | Examen sous 1 heure   |
| **critical** | 90-100         | Schéma de fraude confirmé     | Examen immédiat       |

## Types d'alertes

### 1. Alertes de vélocité

Déclenchées lorsque la fréquence des transactions dépasse les schémas normaux.

**Exemple** :

```json
{
  "alert_type": "velocity_check",
  "severity_level": "high",
  "message": "Unusual transaction velocity detected: 5 transactions in 10 minutes",
  "metadata": {
    "window": "10_minutes",
    "count": 5,
    "threshold": 3,
    "actor_hash": "hash_0244567890"
  }
}
```

**Schémas courants** :

- Test de carte : nombreuses petites transactions rapidement
- Prise de contrôle de compte : burst d'activité après une longue inactivité
- Mule financière : transferts rapides entrants/sortants

---

### 2. Alertes d'anomalie

Déclenchées par des écarts par rapport aux schémas de comportement établis.

**Exemple** :

```json
{
  "alert_type": "anomaly_detection",
  "severity_level": "high",
  "message": "Transaction amount 10x above user's normal pattern",
  "metadata": {
    "amount": 50000,
    "normal_avg": 4500,
    "deviation": "10.2x"
  }
}
```

**Types d'anomalies** :

- Anomalie de montant (taille de la transaction)
- Anomalie temporelle (heure/jour inhabituel)
- Anomalie géographique (nouvelle localisation)
- Anomalie d'appareil (appareil nouveau ou modifié)

---

### 3. Alertes réseau

Déclenchées par des connexions à des acteurs ou réseaux de fraude connus.

**Exemple** :

```json
{
  "alert_type": "network_link",
  "severity_level": "critical",
  "message": "Actor linked to 3 confirmed fraudsters in the network",
  "metadata": {
    "linked_entities": 3,
    "link_strength": 0.94,
    "shared_attributes": ["device_fingerprint", "ip_address"]
  }
}
```

---

### 4. Alertes de liste de blocage

Déclenchées par des correspondances avec des listes de blocage globales ou spécifiques au partenaire.

**Exemple** :

```json
{
  "alert_type": "blocklist_match",
  "severity_level": "critical",
  "message": "Actor matches global fraud blocklist",
  "metadata": {
    "list_name": "global_fraudsters",
    "match_confidence": 0.98,
    "previous_incidents": 7
  }
}
```

---

### 5. Alertes de voyage impossible

Déclenchées lorsque les localisations géographiques suggèrent un déplacement physiquement impossible.

**Exemple** :

```json
{
  "alert_type": "impossible_travel",
  "severity_level": "high",
  "message": "Login from Lagos 30 minutes after login from Accra (420km apart)",
  "metadata": {
    "location_1": "Accra, GH",
    "location_2": "Lagos, NG",
    "distance_km": 420,
    "time_elapsed_minutes": 30,
    "required_speed_kmh": 840
  }
}
```

## Flux de triage des alertes

### Étape 1 : Examen de l'alerte

**Consulter les nouvelles alertes** :

```typescript
const pendingAlerts = await client.alerts.list({
  status: "pending",
  sort_by: "severity_level",
  sort_order: "desc", // Critical first
});

for (const alert of pendingAlerts.data) {
  console.log(`${alert.severity_level} - ${alert.message}`);
}
```

**Évaluation rapide** :

1. Examiner le niveau de sévérité
2. Lire le message de l'alerte
3. Vérifier les détails du signal associé
4. Identifier le type d'alerte
5. Évaluer le risque immédiat

---

### Étape 2 : Accuser réception de l'alerte

Signaler la prise en charge et commencer l'enquête :

```typescript
await client.alerts.update(alertUuid, {
  status: "acknowledged",
  acknowledged_by: userId,
  notes: "Reviewing actor history and linked transactions",
});
```

**Quand accuser réception** :

- ✅ Les alertes critiques/élevées immédiatement
- ✅ Lors du démarrage d'une enquête
- ✅ Pour éviter les doublons de travail (signale aux autres que vous gérez)

**Objectifs SLA** :

- Critique : < 5 minutes
- Élevé : < 15 minutes
- Moyen : < 1 heure
- Faible : < 4 heures

---

### Étape 3 : Enquête

**Examiner le signal associé** :

```typescript
const alert = await client.alerts.get(alertUuid);
const signal = await client.signals.get(alert.signal_id);

// Check risk breakdown
const riskBreakdown = await client.transactionMonitoring.riskBreakdown(
  signal.id,
);

// Find similar transactions
const similar = await client.transactionMonitoring.findSimilar(signal.id, {
  threshold: 0.8,
});
```

**Liste de vérification pour l'enquête** :

- [ ] Examiner le score de risque et les facteurs
- [ ] Vérifier l'historique de l'acteur (transactions précédentes)
- [ ] Rechercher des schémas similaires (réseau de fraude ?)
- [ ] Vérifier la cohérence géographique/appareil
- [ ] Vérifier par rapport aux listes de blocage
- [ ] Examiner la santé du compte client

---

### Étape 4 : Résolution

Choisir la résolution appropriée en fonction des conclusions :

#### Résolution : Fraude confirmée

```typescript
await client.alerts.update(alertUuid, {
  status: "resolved",
  resolution_type: "confirmed_fraud",
  resolution_notes:
    "Confirmed account takeover. Actor blocked, customer notified.",
  actions_taken: [
    "blocked_actor",
    "reversed_transaction",
    "notified_customer",
    "created_case",
  ],
});

// Optionally create case for detailed investigation
if (alert.severity_level === "critical") {
  await client.cases.createFromSignal(alert.signal_id, {
    priority: "high",
    category: alert.alert_type,
  });
}
```

#### Résolution : Faux positif

```typescript
await client.alerts.update(alertUuid, {
  status: "false_positive",
  resolution_notes:
    "Verified with customer - legitimate high-value purchase. Customer traveling internationally.",
  tuning_notes:
    "Consider increasing threshold for verified customers with international travel history.",
});

// Update thresholds if pattern identified
if (shouldAdjustThreshold(alert)) {
  await client.settings.updateAlertThresholds({
    velocity_check: { threshold: 5 }, // Increase from 3
  });
}
```

## Configuration des alertes

### Règles d'alerte par catégorie

Chaque signal est classé dans l'une des 13 catégories taxonomiques (ex. `payment.mobile_money`, `geo.impossible_travel`, `identity.synthetic`). Chaque catégorie dispose de sa propre règle qui contrôle si une alerte se déclenche et à quel seuil de confiance.

Naviguez vers **Alertes → Règles d'alerte** dans le Portail Partenaire pour les configurer.

#### Résolution des règles

| Couche | Source | Priorité |
|---|---|---|
| Substitution partenaire | Votre configuration sauvegardée | La plus haute |
| Défaut système | Issu de la sévérité de base de la taxonomie | Intermédiaire |
| Seuil global de secours | 0,40 (seuil moyen) | La plus basse |

Le moteur adopte toujours une approche **fail-open** — l'absence de règle ne supprime jamais une alerte.

#### Le toggle

Active ou désactive toutes les alertes pour une catégorie de fraude, quel que soit le score. Un signal à 0,99 dans une catégorie désactivée ne génère aucune alerte.

::callout{icon="i-lucide-lock" color="red"}
**Règles système** (`identity.sim_swap`, `identity.account_takeover`, `payment.agent_collusion`) — toujours actives pour des raisons réglementaires. Les désactiver via l'API retourne HTTP 403.
::

#### Le curseur de score minimum

Définit le seuil de confiance (0,10–0,99) que le moteur doit atteindre avant de déclencher une alerte pour cette catégorie.

| Plage | Indicateur | Interprétation |
|---|---|---|
| 85–99 % | Rose | Très haute confiance — alertes peu nombreuses mais très précises |
| 70–84 % | Orange | Haute confiance — point de départ recommandé |
| 55–69 % | Ambre | Confiance modérée — plus de volume, plus de revue |
| 10–54 % | Bleu | Seuil bas — capture les signaux faibles, plus de faux positifs |

#### Workflow de sauvegarde

Les modifications sont conservées comme brouillons locaux jusqu'au clic sur **Enregistrer**. Un point orange indique les lignes non enregistrées. Le bouton **Réinitialiser** (↺) supprime la substitution et revient au défaut système.

### API

```typescript
// Lister les 13 catégories avec votre configuration effective
GET /api/v1/partner/alert-rules

// Désactiver une catégorie
PUT /api/v1/partner/alert-rules/geo.impossible_travel
{ "is_enabled": false, "override_reason": "Base clients transfrontalière" }

// Augmenter le seuil sans désactiver
PUT /api/v1/partner/alert-rules/device.anomaly
{ "min_severity_score": 0.80 }

// Réinitialiser au défaut système
DELETE /api/v1/partner/alert-rules/device.anomaly
```

### Correspondance des sévérités

**Score de risque → niveau de sévérité** (classification après déclenchement de l'alerte) :

| Score de risque | Sévérité par défaut | Délai cible |
| --------------- | ------------------- | ----------- |
| 90–100          | Critique            | Immédiat    |
| 75–89           | Élevé               | < 1 heure   |
| 60–74           | Moyen               | < 4 heures  |
| 40–59           | Faible              | < 24 heures |
| Sous le seuil   | Aucune alerte       | —           |

Le score minimum de la règle d'alerte contrôle si l'alerte se déclenche ; la classification ci-dessus intervient après sa création.

## Canaux de notification des alertes

### Notifications par webhook

Recevoir des alertes en temps réel via des webhooks :

**Configurer dans le Portail Partenaire** :

- Paramètres > Intégrations > Webhooks
- S'abonner à l'événement `alert.triggered`

**Charge utile du webhook** :

```json
{
  "id": "evt_alert_001",
  "type": "alert.triggered",
  "created_at": "2026-02-03T14:30:00Z",
  "data": {
    "alert": {
      "uuid": "alert_550e8400",
      "alert_type": "velocity_check",
      "severity_level": "high",
      "status": "pending",
      "message": "Unusual transaction velocity: 5 in 10 minutes",
      "triggered_at": "2026-02-03T14:30:00Z"
    },
    "signal": {
      "id": "sig_abc123",
      "risk_score": 87,
      "risk_level": "high"
    }
  }
}
```

**Exemple de gestionnaire** :

```typescript
app.post("/webhooks/protegey", async (req, res) => {
  const { type, data } = req.body;

  if (type === "alert.triggered") {
    const { alert, signal } = data;

    // Critical alerts → immediate notification
    if (alert.severity_level === "critical") {
      await sendPagerDutyAlert({
        title: alert.message,
        severity: "critical",
        details: { alert_id: alert.uuid, signal_id: signal.id },
      });
    }

    // High alerts → Slack notification
    else if (alert.severity_level === "high") {
      await sendSlackMessage("#fraud-alerts", {
        text: `🚨 High Priority Alert: ${alert.message}`,
        link: `https://partner.protegey.com/alerts/${alert.uuid}`,
      });
    }
  }

  res.status(200).send("OK");
});
```

const stats = await client.alerts.statistics({
  start_date: "2026-02-01",

## Bonnes pratiques

### 1. Prioriser par sévérité

**Ordre de triage** :

1. Alertes critiques (immédiat)
2. Alertes élevées (< 1 heure)
3. Alertes moyennes (< 4 heures)
4. Alertes faibles (< 24 heures)

```typescript
// Process critical alerts first
const criticalAlerts = await client.alerts.list({
  status: "pending",
  severity_level: "critical",
});

for (const alert of criticalAlerts.data) {
  await triageAlert(alert);
}
```

### 2. Ajuster les seuils régulièrement

**Examiner le taux de faux positifs chaque mois** :

```typescript
const stats = await client.alerts.statistics({
  start_date: oneMonthAgo,
  end_date: today,
});

// High false positive rate? Adjust thresholds
if (stats.false_positive_rate > 20) {
  console.warn("High false positive rate - consider tuning thresholds");

  // Identify worst performing alert type
  const worstType = stats.by_type.sort(
    (a, b) => b.false_positive_rate - a.false_positive_rate,
  )[0];

  console.log(`Adjust ${worstType.type} threshold`);
}
```

## Scénarios courants

### Scénario 1 : Triage d'une alerte critique

```typescript
async function triageCriticalAlert(alert) {
  // 1. Acknowledge immediately
  await client.alerts.update(alert.uuid, {
    status: "acknowledged",
  });

  // 2. Get signal details
  const signal = await client.signals.get(alert.signal_id);

  // 3. Check actor history
  const actorHistory = await client.actors.history(signal.actor.hashed_id);

  // 4. Find similar signals
  const similar = await client.transactionMonitoring.findSimilar(signal.id);

  // 5. Decide action
  if (actorHistory.fraud_count > 0 || similar.length > 3) {
    // Confirmed fraud - block immediately
    await blockActor(signal.actor.hashed_id);

    await client.alerts.update(alert.uuid, {
      status: "resolved",
      resolution_type: "confirmed_fraud",
      resolution_notes: `Immediate block - repeat fraudster (${actorHistory.fraud_count} previous incidents)`,
    });

    // Create case for investigation
    await client.cases.createFromSignal(signal.id, {
      priority: "critical",
      category: alert.alert_type,
    });
  } else {
    // Unclear - escalate for manual review
    await client.cases.createFromSignal(signal.id, {
      priority: "high",
      category: alert.alert_type,
      assigned_user_id: await getSeniorAnalyst(),
    });
  }
}
```

### Scénario 2 : Nettoyage en masse des faux positifs

```typescript
async function cleanupFalsePositives() {
  // Find old acknowledged alerts never resolved
  const staleAlerts = await client.alerts.list({
    status: "acknowledged",
    created_before: thirtyDaysAgo,
  });

  for (const alert of staleAlerts.data) {
    // Review and mark as false positive if appropriate
    const signal = await client.signals.get(alert.signal_id);

    if (signal.risk_score < 70 && !hasSubsequentFraud(signal.actor)) {
      await client.alerts.update(alert.uuid, {
        status: "false_positive",
        resolution_notes:
          "Cleanup: No subsequent fraud detected, likely false positive",
      });
    }
  }
}
```

### Scénario 3 : Gestion d'un storm d'alertes

```typescript
async function handleAlertStorm() {
  // Detect alert storm (>100 alerts in 1 hour)
  const recentAlerts = await client.alerts.list({
    created_after: oneHourAgo,
  });

  if (recentAlerts.meta.total > 100) {
    console.warn("Alert storm detected!");

    // Group by actor to identify coordinated attack
    const byActor = groupBy(recentAlerts.data, "signal.actor.hashed_id");

    // Focus on high-volume actors first
    const topActors = Object.entries(byActor)
      .sort((a, b) => b[1].length - a[1].length)
      .slice(0, 10);

    // Investigate top actors
    for (const [actorHash, alerts] of topActors) {
      console.log(`Actor ${actorHash}: ${alerts.length} alerts`);

      // Auto-block if clear pattern
      if (
        alerts.length > 10 &&
        alerts.every((a) => a.severity_level === "high")
      ) {
        await blockActor(actorHash);

        // Bulk resolve alerts
        for (const alert of alerts) {
          await client.alerts.update(alert.uuid, {
            status: "resolved",
            resolution_type: "confirmed_fraud",
            resolution_notes: "Part of coordinated attack - actor blocked",
          });
        }
      }
    }
  }
}
```

### Tableau de bord des alertes

**Métriques clés à suivre** :

**Exemple de tableau de bord** :
