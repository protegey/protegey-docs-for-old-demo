Protegey combine traitements synchrones et asynchrones. Les opérations les plus critiques — score de risque, détection et attribution taxonomique — s'exécutent **en ligne lors de l'ingestion du signal** afin que vous obteniez un verdict de risque dans la même réponse HTTP. Les tâches en aval plus lourdes (liaison graphe, vérification AML, enrichissement des entités) s'exécutent de manière asynchrone dans des workers en arrière-plan.

---

## Vue d'ensemble

### Ce qui s'exécute de manière synchrone ?

**Ingestion de signal** — tout ce dont vous avez besoin pour prendre une décision immédiate s'exécute en ligne :

- Validation et normalisation UFES v2
- Ingénierie des features (z-scores de transaction, fenêtres de vélocité, nouveauté d'appareil, distance géo)
- Les 9 détecteurs (RapidVelocity, LargeOutlier, SimSwapProximity, NewDeviceAccess, ImpossibleTravel, SessionAnomaly, AttackChain, BeneficiaryConcentration, AgentConcentration)
- Score de risque NUFSS et attribution taxonomique
- Verdict de risque retourné dans la réponse `201`

### Ce qui s'exécute de manière asynchrone ?

**Post-traitement du signal** (après l'envoi de la réponse HTTP) :

- Liaison au graphe chaud (HotGraphService — création de nœuds et arêtes ACTOR/DEVICE/MSISDN)
- Vérification de conformité AML (sanctions, PPE, règles de surveillance des transactions — Entreprise uniquement)
- Liaison des entités et mises à jour du score de confiance
- Génération d'alertes pour les signaux à risque élevé/critique
- Livraison du webhook `signal.ingested`

**Opérations en masse** :

- Décision en masse (fonctionnalité Entreprise)
- Exports CSV
- Migrations de données volumineuses
- Génération de signaux par lot

**Analytics** :

- Agrégation des statistiques du tableau de bord
- Génération de cartes de chaleur des risques
- Calcul des métriques de performance

**Notifications** :

- Livraison des webhooks
- Notifications par e-mail
- Alertes SMS (si configurées)

### Pourquoi l'asynchrone ?

**Réponses API rapides** : Les API retournent immédiatement sans attendre les traitements complexes.

**Scalabilité** : Les workers en arrière-plan peuvent être mis à l'échelle indépendamment des serveurs API.

**Fiabilité** : Les jobs échoués peuvent être relancés automatiquement avec un backoff exponentiel.

**Gestion des ressources** : Les opérations coûteuses (modèles ML, requêtes graphe) s'exécutent dans des workers dédiés.

**Préservation du contexte** : Les jobs maintiennent le contexte d'environnement (sandbox/production) à travers les frontières asynchrones.

## Fonctionnement

### Cycle de vie d'une requête

```
1. POST /api/v1/signals  (+ Idempotency-Key header)
   ↓
2. Synchronous pipeline  (runs inline, ~50–150ms)
   - UFES v2 validation
   - Feature engineering
   - 9 detectors run
   - NUFSS risk score computed
   - Taxonomy assigned
   ↓
3. 201 Created response  (risk verdict available immediately)
   {
     "signal_id": "...",
     "risk_score": 0.78,
     "risk_level": "high",
     "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"]
   }
   ↓
4. Background processing  (async, ~1–5 seconds)
   - Hot graph linking
   - AML screening (Enterprise)
   - Entity trust score update
   - Alert generation (if risk ≥ threshold)
   ↓
5. Webhook notifications (if endpoint subscribed)
   - signal.ingested  (always, after scoring)
   - alert.created    (if an alert was generated)
```

### Architecture des files d'attente

Protegey utilise les **Laravel Queues** avec plusieurs niveaux de priorité :

| File d'attente | Priorité | Délai de traitement | Cas d'usage                               |
| -------------- | -------- | ------------------- | ----------------------------------------- |
| `high`         | Highest  | < 1 seconde         | Alertes temps réel, opérations critiques  |
| `default`      | Normal   | 2–5 secondes        | Traitement des signaux, scoring de fraude |
| `low`          | Faible   | 5–30 secondes       | Analytics, opérations en masse            |
| `webhooks`     | Normal   | 1–3 secondes        | Livraison de webhooks                     |

**Configuration des workers** :

```bash
# High-priority queue (low latency)
php artisan queue:work --queue=high --tries=3 --timeout=30

# Default queue (normal processing)
php artisan queue:work --queue=default --tries=3 --timeout=60

# Low-priority queue (bulk operations)
php artisan queue:work --queue=low --tries=2 --timeout=300
```

## Préservation du contexte

### Le défi

Les jobs de file d'attente s'exécutent de manière asynchrone dans des processus worker séparés. Sans contexte approprié, les jobs pourraient :

- Utiliser le mauvais schéma de base de données (sandbox vs production)
- Interroger les données du mauvais partenaire
- Perdre les informations de traçage des requêtes

### La solution : ContextAwareJob

Tous les jobs asynchrones dans Protegey héritent de `ContextAwareJob`, qui :

1. **Capture le contexte** au moment de la mise en file (constructeur)
2. **Sérialise le contexte** pour la persistance dans la file
3. **Restaure le contexte** lorsque le job s'exécute dans le worker
4. **Applique le schéma** automatiquement

**Exemple** :

```php
use App\Jobs\ContextAwareJob;

class ProcessFraudSignal extends ContextAwareJob
{
    public function __construct(
        private string $signalId,
        private string $partnerUuid
    ) {
        parent::__construct(); // ⚠️ CRITICAL: Captures context
    }

    protected function perform(): void
    {
        // Context already restored - queries use correct schema
        $signal = Signal::where('id', $this->signalId)
            ->where('partner_uuid', $this->partnerUuid)
            ->firstOrFail();

        // Calculate risk score
        $riskScore = $this->fraudScoringService->calculate($signal);

        // Update signal (uses correct schema automatically)
        $signal->update(['risk_score' => $riskScore]);
    }
}
```

### Flux du contexte

```
HTTP Request (sandbox.protegey.com)
    ↓
    environment: 'sandbox'
    schema: 'sandbox'
    ↓
ProcessFraudSignal::dispatch($signalId)
    ↓ [Job Serialized to Queue]
    {
      "job": "ProcessFraudSignal",
      "data": {
        "signalId": "sig_abc123",
        "contextData": {
          "environment": "sandbox",
          "partner_uuid": "uuid",
          "schema": "sandbox"
        }
      }
    }
    ↓ [Queue Worker Picks Up Job]
    ↓
Job::handle()
    ↓ [Context Restored]
    environment: 'sandbox'
    schema: 'sandbox'
    SET search_path TO sandbox, public
    ↓
perform() executes
    ↓ [All queries use sandbox schema]
```

## Délais attendus

### Ingestion de signal

**Réponse API** : ~50–150ms (verdict de risque synchrone)

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_type": "MOBILE_MONEY_SEND",
    "risk_score": 0.78,
    "risk_level": "high",
    "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
    "taxonomy": "mobile_money_fraud"
  }
}
```

**Traitement en arrière-plan** (1–5 secondes après la réponse) :

- Liaison au graphe chaud : < 1 seconde
- Vérification AML : 1–3 secondes (Entreprise uniquement)
- Génération d'alertes : < 1 seconde

**Notification webhook** (après le traitement en arrière-plan) :

```json
{
  "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
  "event_type": "MOBILE_MONEY_SEND",
  "event_category": "transaction",
  "risk_score": 0.78,
  "risk_level": "high",
  "detectors_triggered": ["RAPID_TRANSACTION_VELOCITY"],
  "taxonomy": "mobile_money_fraud"
}
```

(livré avec l'en-tête `X-Centry-Event: signal.ingested`)

### Opérations en masse

**Décision en masse** (Entreprise) :

- Réponse API : < 500ms
- Traitement : ~100ms par signal
- 100 signaux : ~10 secondes au total
- Webhook à la fin

**Export CSV** :

- Réponse API : < 200ms (retourne un ID d'export)
- Traitement : 1–30 secondes (selon le volume)
- Webhook avec URL de téléchargement une fois prêt

**Génération de signaux par lot** (Sandbox) :

- Réponse API : < 500ms
- Traitement : ~200ms par signal
- 20 signaux : ~4 secondes au total
- Profil de risque appliqué lors de la génération

### Analytics

**Statistiques du tableau de bord** :

- Mises en cache pendant 5 minutes
- Cache miss : 2–5 secondes pour calculer
- Mises à jour en temps réel non disponibles (utiliser les webhooks)

**Analytics en série temporelle** :

- Calculées à la demande
- Plage de 30 jours : 1–3 secondes
- Plage de 90 jours : 3–8 secondes

## Vérifier le statut des jobs

### Méthode 1 : Webhooks (recommandé)

Configurer des webhooks pour recevoir des notifications lorsque les opérations asynchrones se terminent :

```typescript
// 1. Register a webhook endpoint in Partner Portal
// Settings > Integrations > Webhooks

// 2. Subscribe to relevant events
const events = [
  "signal.ingested", // fired after async post-processing completes
  "alert.created", // fired when a new fraud alert is generated
  "case.created",
  "case.status_changed",
];

// 3. Handle webhook in your application
app.post("/webhooks/protegey", express.json(), (req, res) => {
  const event = req.headers["x-centry-event"];
  const payload = req.body;

  switch (event) {
    case "signal.ingested":
      // Confirm risk scores post-graph-linking; trigger downstream enrichment
      console.log("Signal post-processed:", payload.signal_id);
      console.log("Risk score:", payload.risk_score);
      break;

    case "alert.created":
      // Route to analyst queue or PagerDuty
      if (payload.severity === "critical") {
        triggerPagerDuty(payload);
      }
      break;
  }

  res.status(200).send("OK");
});
```

### Méthode 2 : Interrogation (polling)

Interroger l'API pour vérifier si le traitement est terminé :

```typescript
async function waitForSignalProcessing(signalId: string) {
  let attempts = 0;
  const maxAttempts = 20; // 20 seconds max
  const interval = 1000; // 1 second

  while (attempts < maxAttempts) {
    const signal = await client.signals.get(signalId);

    if (signal.risk_score !== null) {
      // Processing complete
      return signal;
    }

    // Wait before next poll
    await sleep(interval);
    attempts++;
  }

  throw new Error("Signal processing timed out");
}
```

**Bonnes pratiques** :

- Commencer avec des intervalles d'1 seconde
- Utiliser un backoff exponentiel pour les longues attentes
- Définir des délais d'attente raisonnables (10–30 secondes)
- Préférer les webhooks au polling en production

## Gestion des erreurs

### Nouvelles tentatives automatiques

Les jobs échoués sont automatiquement relancés avec un backoff exponentiel :

| Tentative | Délai       | Exemple d'heure |
| --------- | ----------- | --------------- |
| 1         | Immédiat    | 0:00            |
| 2         | 30 secondes | 0:30            |
| 3         | 2 minutes   | 2:30            |
| 4         | 8 minutes   | 10:30           |
| 5         | 32 minutes  | 42:30           |

**Après 5 tentatives** : Job marqué comme échoué, webhook envoyé (si configuré).

### Scénarios d'échec courants

**1. Problèmes réseau temporaires**

- **Symptôme** : Livraison du webhook échouée
- **Relance** : Automatique avec backoff exponentiel
- **Résolution** : Se résout généralement en 2–3 tentatives

**2. Délais d'attente de l'API externe**

- **Symptôme** : Le job de scoring de fraude expire
- **Relance** : Automatique (jusqu'à 3 tentatives)
- **Résolution** : Consulter la page de statut pour les incidents de service

**3. Données invalides**

- **Symptôme** : Le job échoue immédiatement
- **Relance** : Non relancé (échec permanent)
- **Résolution** : Corriger les données et resoumettre

**4. Limites de débit (internes)**

- **Symptôme** : Job retardé dans la file
- **Relance** : Automatique avec backoff
- **Résolution** : Attend la réinitialisation de la fenêtre de limite de débit

### Webhook de job échoué

Lorsqu'un job échoue après toutes les tentatives :

```json
{
  "id": "evt_failed_123",
  "type": "job.failed",
  "created_at": "2026-02-03T15:30:00Z",
  "data": {
    "job": "ProcessFraudSignal",
    "signal_id": "sig_abc123",
    "error": "External API timeout after 3 attempts",
    "attempts": 5,
    "failed_at": "2026-02-03T15:30:00Z"
  }
}
```

## Bonnes pratiques

### 1. Utiliser le verdict de risque synchrone

**Le score de risque est disponible immédiatement dans la réponse 201** — aucun polling ni attente nécessaires :

```typescript
// ✅ CORRECT: Risk verdict is synchronous
const response = await fetch("/api/v1/signals", {
  method: "POST",
  headers: {
    "X-Centry-Key": process.env.PROTEGEY_SECRET_KEY,
    "Idempotency-Key": crypto.randomUUID(),
  },
  body: JSON.stringify(signalPayload),
});
const { data } = await response.json();

// Available immediately — no poll needed
console.log(data.risk_score); // 0.78
console.log(data.risk_level); // "high"
console.log(data.detectors_triggered); // ["RAPID_TRANSACTION_VELOCITY"]

// Apply your decision logic now
if (data.risk_level === "critical") {
  await blockTransaction(data.signal_id);
} else if (data.risk_level === "high") {
  await requireAdditionalVerification();
}
```

### 2. Utiliser les webhooks en production

**Les webhooks sont plus efficaces que le polling** :

- Aucun appel API inutile
- Notification instantanée à la fin du traitement
- Meilleure expérience utilisateur

**Configuration** :

```typescript
// Configure once in partner portal
// No polling loops needed

app.post("/webhooks/protegey", async (req, res) => {
  const { type, data } = req.body;

  // Verify signature (important!)
  if (!verifySignature(req)) {
    return res.status(401).send("Invalid signature");
  }

  // Process event
  await processEvent(type, data);

  // Acknowledge immediately
  res.status(200).send("OK");
});
```

### 3. Gérer les délais d'attente avec élégance

**Définir des délais réalistes** :

```typescript
const timeout = 30000; // 30 seconds
const signal = await client.signals.create(signalData, { timeout });

// Don't wait forever - move on
if (!signal.risk_score) {
  // Process later via webhook
  console.log("Processing async, will notify via webhook");
}
```

### 4. Implémenter l'idempotence

**Les webhooks peuvent être livrés plusieurs fois** :

```typescript
const processedEvents = new Set<string>();

app.post("/webhooks/protegey", async (req, res) => {
  const eventId = req.body.id;

  // Check if already processed
  if (processedEvents.has(eventId)) {
    return res.status(200).send("Already processed");
  }

  // Process event
  await processEvent(req.body);

  // Mark as processed
  processedEvents.add(eventId);

  res.status(200).send("OK");
});
```

### 5. Journaliser le contexte des jobs

**Inclure le contexte dans les logs** :

```php
Log::info('Processing signal', [
    'signal_id' => $this->signalId,
    'partner_uuid' => $this->partnerUuid,
    'environment' => app(CentryContext::class)->environment(),

```

### 6. Surveiller la profondeur des files

**Suivre la santé des files d'attente** :

## Résolution des problèmes

### Problème : « risk_score manquant dans la réponse 201 »

**Cause** : Probablement une erreur de validation (422) plutôt qu'un 201 — vérifier le statut et le corps de la réponse.

**Solution** : S'assurer que votre payload inclut `schema_version: "2.0"` et `primary_actor.entity_id`. Le verdict de risque est toujours synchrone pour les réponses 201 — aucun polling n'est nécessaire.

```typescript
const response = await fetch('/api/v1/signals', { ... });
if (response.status === 422) {
  const error = await response.json();
  console.error('Validation failed:', error.errors); // find missing fields
}
```

---

### Problème : « Webhook non reçu »

**Causes possibles** :

1. URL de webhook non configurée
2. Pare-feu bloquant les IPs Protegey
3. Point de terminaison retournant un statut d'erreur
4. Échec de la vérification de signature

**Étapes de débogage** :

```bash
# 1. Check webhook configuration
# Partner Portal > Settings > Integrations > Webhooks

# 2. Whitelist Protegey IPs
# 34.11.23.45, 34.11.23.46, 35.22.11.99

# 3. Check endpoint logs
tail -f /var/log/nginx/access.log | grep protegey

# 4. Verify signature
# See Webhooks documentation for signature verification
```

---

### Problème : « Jobs traités trop lentement »

**Symptômes** : Le tableau de bord affiche une grande profondeur de file, délais de traitement longs.

**Causes possibles** :

1. Workers insuffisants
2. Délai d'expiration des workers trop court
3. Pool de connexions à la base de données épuisé
4. Limites de débit des API externes

**Solutions** :

```bash
# Scale up workers
# Add more worker processes

# Increase timeout for complex jobs
php artisan queue:work --timeout=120

# Monitor worker health
php artisan queue:monitor

# Check failed jobs
php artisan queue:failed
```

---

### Problème : « Contexte non préservé dans les jobs »

**Symptôme** : Le job interroge le mauvais schéma ou les données du mauvais partenaire.

**Cause** : Le job n'hérite pas de `ContextAwareJob` ou le constructeur parent n'est pas appelé.

**Solution** :

```php
// ✅ CORRECT
class MyJob extends ContextAwareJob {
    public function __construct(private string $data) {
        parent::__construct(); // CRITICAL
    }

    protected function perform(): void {
        // Context restored automatically
    }
}

// ❌ WRONG
class MyJob implements ShouldQueue {
    // Context not captured!
}
```

## Sujets avancés

### Priorités de files personnalisées

**Dispatcher vers une file spécifique** :

```php
ProcessFraudSignal::dispatch($signalId)->onQueue('high');
```

**Ordre de priorité des files** :

```bash
php artisan queue:work --queue=high,default,low
```

### Jobs différés

**Traiter un signal après délai** :

```php
ProcessFraudSignal::dispatch($signalId)->delay(now()->addMinutes(5));
```

### Chaînage de jobs

**Exécution séquentielle de jobs** :

```php
ProcessFraudSignal::withChain([
    new CalculateEntityRisk($entityId),
    new GenerateAlerts($signalId),
    new SendNotifications($partnerId)
])->dispatch($signalId);
```

### Traitement par lots de jobs

**Suivre la progression d'un lot** :

```php
$batch = Bus::batch([
    new ProcessSignal($signalId1),
    new ProcessSignal($signalId2),
    new ProcessSignal($signalId3)
])->dispatch();

// Check progress
$batch->progress(); // 66% complete
```
