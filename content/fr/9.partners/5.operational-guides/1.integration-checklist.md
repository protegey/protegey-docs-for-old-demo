Utilisez cette liste de vérification complète pour valider votre intégration Protegey avant la mise en production. Complétez tous les éléments en sandbox d'abord, puis validez en production.

::callout{icon="i-lucide-clipboard-check" color="blue"}
**Prêt pour la Production** : Une intégration complète comprend l'ingestion de signaux, la gestion des dossiers, les flux d'alerte, la gestion des webhooks, et une gestion correcte des erreurs.
::

---

## Phase 1 : Configuration du Sandbox

### Configuration de l'Environnement

- [ ] **Accès Sandbox** : Clés API sandbox générées dans le Portail Partenaire
- [ ] **Basculement d'Environnement** : Possibilité de basculer entre les environnements sandbox et production
- [ ] **Configuration Cookie/En-tête** : Le basculement d'environnement fonctionne via les paramètres de requête, les cookies ou les en-têtes

### Génération de Données de Démonstration

- [ ] **Génération de Signaux** : Possibilité de générer des signaux de démonstration via l'API (`/api/v1/partner/sandbox/generate-demo-signals`)
- [ ] **Test de Gabarits** : Plusieurs gabarits de signaux testés (prise de contrôle de compte, données financières volées, etc.)
- [ ] **Distribution des Risques** : Profilage des risques vérifié (10 % critique, 20 % élevé, 30 % moyen, 40 % faible)

### Isolation des Données

- [ ] **Séparation des Schémas** : Confirmé que les signaux sandbox n'apparaissent pas dans le tableau de bord de production
- [ ] **Fonctionnalité de Réinitialisation** : Réinitialisation des données sandbox réussie via l'API
- [ ] **Sécurité de la Production** : Aucune donnée de test ne pollue l'environnement de production

## Phase 2 : Intégration Centrale

## Sécurité

- [ ] **Stockage des Clés API** : Les clés sont stockées dans des variables d'environnement ou un gestionnaire de secrets, et non dans le code.
- [ ] **Liste Blanche d'IP** : Les adresses IP de production sont configurées dans le Portail Partenaire.
- [ ] **TLS** : Toutes les requêtes API utilisent HTTPS.

## Fiabilité

- [ ] **Délais d'Attente** : Le client API dispose d'un délai d'attente configuré (recommandé : 2000 ms).
- [ ] **Fail-Open/Closed** : Une logique est en place pour gérer l'indisponibilité de l'API (ex. : par défaut « Autoriser » ou « Révision Manuelle »).
- [ ] **Relances** : Un backoff exponentiel est implémenté pour les erreurs `429` et `5xx`.

## Qualité des Données

- [ ] **Formatage des Entités** : Les e-mails sont en minuscules et sans espaces. Les numéros de téléphone sont au format E.164.
- [ ] **Hachage** : Si des données personnelles pré-hachées sont utilisées, vérifiez que SHA-256 est appliqué correctement.
- [ ] **Spécifique à l'Asynchrone** : Les soumissions de signaux sont effectuées de manière asynchrone (tâche en arrière-plan) pour éviter de bloquer l'interface utilisateur.

## Opérationnel

- [ ] **Surveillance** : Vous journalisez les codes de réponse et la latence de l'API Protegey.
- [ ] **Alertes** : Des alertes sont configurées pour une hausse des erreurs 4xx/5xx.
- [ ] **Contacts** : Les contacts Incident, Facturation et Technique sont à jour dans le Portail.

## Conformité

- [ ] **Politique de Confidentialité** : Votre politique de confidentialité côté utilisateur mentionne le partage de données à des fins de prévention de la fraude.
- [ ] **Conservation des Données** : Vous ne stockez pas les scores de risque Protegey plus longtemps que nécessaire (maximum 90 jours recommandé).
- [ ] **Consentement Utilisateur** : Consentement utilisateur approprié obtenu pour le traitement de détection de fraude
- [ ] **Accord de Traitement des Données** : DPA signé avec Protegey (obligatoire pour la production)

## Phase 3 : Ingestion de Signaux

### Intégration API

- [ ] **Format UFES v2** : Tous les signaux incluent `schema_version: "2.0"` et `primary_actor.entity_id`
- [ ] **Hachage des Données Personnelles** : Les identifiants sont hachés avec HMAC-SHA256 en utilisant votre **network key** (pas SHA-256 seul, pas votre clé API)
- [ ] **Champs Détecteur** : Inclusion de `source.ip_address`, `primary_actor.device.fingerprint`, et `primary_actor.identifiers.sim_changed_at` le cas échéant
- [ ] **Idempotence** : L'en-tête `Idempotency-Key` est envoyé avec chaque signal ; la même clé est réutilisée lors des relances

### Gestion des Réponses

- [ ] **201 Created** : Verdict de risque synchrone consommé (`risk_score`, `risk_level`, `detectors_triggered`)
- [ ] **422 Unprocessable** : Les erreurs de validation sont gérées ; les payloads incorrects sont journalisés pour le débogage
- [ ] **429 Rate Limit** : Backoff exponentiel implémenté (avec le même `Idempotency-Key` lors de la relance)
- [ ] **500 Server Error** : Échec gracieux ; relance avec la même clé d'idempotence

### Tests

- [ ] **SIM Swap** : Signal de test avec `primary_actor.identifiers.sim_changed_at` dans les 24 h → `SIM_SWAP_PROXIMITY` se déclenche
- [ ] **Nouvel Appareil** : Signal de test avec un `primary_actor.device.fingerprint` inédit → `NEW_DEVICE_ACCESS` se déclenche
- [ ] **Montant Élevé** : Signal de test avec un montant bien au-dessus de la ligne de base → `LARGE_OUTLIER_TRANSACTION` se déclenche
- [ ] **Idempotence** : Même signal envoyé deux fois avec la même clé → la seconde requête retourne `X-Idempotency-Replayed: true` avec le même signal_id

## Phase 4 : Surveillance des Transactions

### Intégration du Tableau de Bord

- [ ] **Flux de Transactions** : Possibilité d'afficher le flux de signaux en temps réel dans le portail partenaire
- [ ] **Filtrage** : Possibilité de filtrer par statut, niveau de risque, plage de dates, utilisateur assigné
- [ ] **Recherche** : La recherche plein texte fonctionne pour les identifiants de transaction et les hachages d'acteurs
- [ ] **Détail des Risques** : Possibilité d'afficher les facteurs de risque détaillés pour chaque signal

### Prise de Décision

- [ ] **Décisions Manuelles** : Possibilité d'approuver/refuser/signaler des signaux via le portail ou l'API
- [ ] **Enregistrement des Décisions** : Toutes les décisions correctement journalisées avec leur motif
- [ ] **Décisions en Masse** : Flux de décision en masse testé (fonctionnalité Enterprise)

### Analytiques

- [ ] **Métriques du Tableau de Bord** : Possibilité d'afficher les statistiques récapitulatives (total des signaux, score de risque moyen, distribution des décisions)
- [ ] **Données en Série Temporelle** : Possibilité d'analyser les tendances dans le temps
- [ ] **Carte de Chaleur des Risques** : Possibilité d'identifier les périodes à risque élevé
- [ ] **Fonctionnalité d'Export** : Possibilité d'exporter les signaux au format CSV pour les rapports

## Phase 5 : Gestion des Dossiers

### Création de Dossiers

- [ ] **Depuis un Signal** : Possibilité de créer un dossier directement depuis un signal à risque élevé
- [ ] **Création Manuelle** : Possibilité de créer un dossier sans signal associé
- [ ] **Définition de la Priorité** : Possibilité de définir la priorité appropriée (faible, moyen, élevé, critique)
- [ ] **Sélection de Catégorie** : Possibilité de catégoriser les dossiers (ACCOUNT_TAKEOVER, IDENTITY_THEFT, etc.)

### Flux d'Investigation

- [ ] **Ajout de Notes** : Possibilité d'ajouter des notes d'investigation aux dossiers
- [ ] **Téléversement de Preuves** : Possibilité de joindre des captures d'écran, journaux et documents aux dossiers
- [ ] **Mises à Jour de Statut** : Possibilité de faire évoluer le statut (open → in_progress → resolved → closed)
- [ ] **Assignation** : Possibilité d'assigner des dossiers aux membres de l'équipe

### Collaboration sur les Dossiers

- [ ] **Accès de l'Équipe** : Tous les membres de l'équipe fraude ont accès aux dossiers
- [ ] **Vue Chronologique** : Piste d'audit complète visible pour toutes les activités d'un dossier
- [ ] **Processus de Passation** : Processus clair pour les changements de garde et les escalades

### Clôture des Dossiers

- [ ] **Documentation de Résolution** : Notes de résolution obligatoires et consignées
- [ ] **Suivi des Actions** : Actions prises enregistrées (acteur bloqué, transaction annulée, etc.)
- [ ] **Fermeture du Dossier** : Dossiers correctement fermés après résolution

### Configuration des Alertes

- [ ] **Types d'Alertes** : Types d'alertes pertinents activés (vélocité, anomalie, réseau, liste de blocage)
- [ ] **Correspondance des Sévérités** : Correspondance score de risque → sévérité personnalisée selon l'activité

### Tri des Alertes

- [ ] **File d'Alertes** : Possibilité d'afficher les alertes en attente triées par sévérité
- [ ] **Accusé de Réception** : Possibilité d'accuser réception des alertes pour en prendre la responsabilité
- [ ] **Investigation** : Possibilité d'investiguer le signal associé depuis une alerte
- [ ] **Résolution** : Possibilité de résoudre/marquer comme faux positif les alertes avec notes

### Statistiques des Alertes

- [ ] **Tableau de Bord des Métriques** : Possibilité d'afficher le volume d'alertes, le temps de résolution, le taux de faux positifs
- [ ] **Analyse des Tendances** : Possibilité d'identifier les tendances et schémas d'alertes
- [ ] **Respect des SLA** : Suivi du temps d'accusé de réception et du temps de résolution

- [ ] **Recherche** : Possibilité de rechercher des entités par identifiant ou UUID
- [ ] **Historique des Risques** : Possibilité d'afficher l'évolution du score de risque dans le temps

### Gestion des Statuts

- [ ] **Signalement** : Possibilité de signaler des entités suspectes

- [ ] **Faux Positifs** : Possibilité de marquer les faux positifs avec justification
- [ ] **Réhabilitation** : Possibilité de lever le signalement d'entités précédemment marquées

### Analyse de Réseau

- [ ] **Liens entre Entités** : Possibilité d'afficher les connexions réseau entre entités
- [ ] **Détection de Réseaux de Fraude** : Possibilité d'identifier des réseaux de fraude coordonnés

### Décision Basée sur les Entités

## Phase 8 : Intégration des Webhooks

### Configuration des Webhooks

- [ ] **Configuration du Point de Terminaison** : URL du webhook enregistrée dans le Portail Partenaire (HTTPS obligatoire)
- [ ] **Secret Stocké** : Le secret par point de terminaison copié à la création et stocké dans un gestionnaire de secrets
- [ ] **Abonnement aux Événements** : Abonné aux événements pertinents (`signal.ingested`, `alert.created`, `case.created`)
- [ ] **Ping de Test** : Ping de test envoyé et réception + validation de signature vérifiées

### Vérification de la Signature

- [ ] **Lecture de l'En-tête** : Lecture de `X-Centry-Signature` (pas `X-Protegey-Signature`)
- [ ] **HMAC-SHA256** : Vérification sur `json_encode($payload)` / `JSON.stringify(body)` avec le secret par point de terminaison
- [ ] **Comparaison en Temps Constant** : Utilisation de `hash_equals()` / `timingSafeEqual()` — pas `===`

### Gestionnaire de Webhook

- [ ] **200 Immédiat** : Retourne HTTP 200 dans les 3 secondes avant le traitement
- [ ] **Traitement Asynchrone** : Le traitement lourd est délégué à une tâche en arrière-plan
- [ ] **Idempotence** : Les livraisons en double sont gérées en suivant le `X-Centry-Delivery-ID`

### Gestion des Événements

- [ ] **`signal.ingested`** : Verdict de risque extrait (`risk_score`, `risk_level`, `detectors_triggered`) et traité
- [ ] **`alert.created`** : Les alertes élevées/critiques déclenchent un flux d'escalade interne
- [ ] **`case.created`** : Dossier ouvert dans le système de tickets/CRM interne
- [ ] **`case.status_changed`** : Statut du dossier synchronisé avec le système interne

## Phase 9 : Opérations Asynchrones

### Prise en Compte du Contexte

- [ ] **Tâches en File** : Compréhension du traitement asynchrone des signaux (2 à 8 secondes)
- [ ] **Attentes de Délai** : Ne pas attendre de scores de risque immédiats après la soumission d'un signal
- [ ] **Interrogation vs Webhooks** : Utilisation des webhooks plutôt que l'interrogation en production

### Gestion des Erreurs

- [ ] **Échecs de Tâches** : Logique de relance pour les opérations asynchrones échouées
- [ ] **Gestion des Délais d'Attente** : Gestion gracieuse lorsque le traitement prend plus longtemps que prévu
- [ ] **Notifications d'Échec de Tâches** : Surveillance des webhooks de tâches échouées

## Phase 10 : Préparation à la Production

### Performance

- [ ] **Limites de Débit** : Rester dans les limites de débit de production (1000 req/min pour les transactions)
- [ ] **Regroupement de Connexions** : Le client HTTP utilise le regroupement de connexions pour l'efficacité
- [ ] **Mise en Cache** : Les scores de risque sont mis en cache de manière appropriée (TTL de 5 minutes)
- [ ] **Chargement Différé** : Les opérations lourdes sont différées vers des tâches en arrière-plan

### Surveillance

- [ ] **Latence API** : Suivi des latences P50, P95, P99 pour tous les appels API
- [ ] **Taux d'Erreur** : Surveillance des taux d'erreurs 4xx et 5xx
- [ ] **Taux de Succès** : Suivi du taux de succès d'ingestion des signaux
- [ ] **Profondeur de la File** : Surveillance de la profondeur de la file interne (le cas échéant)

### Alertes

- [ ] **Taux d'Erreur Élevé** : Alerte si le taux d'erreur API > 5 %
- [ ] **Échecs de Webhook** : Alerte si la livraison du webhook échoue de manière répétée
- [ ] **Approche de la Limite de Débit** : Alerte à 80 % de la limite de débit
- [ ] **Pic de Latence** : Alerte si la latence P95 > 2 secondes

### Réponse aux Incidents

- [ ] **Rotation d'Astreinte** : Membre de l'équipe en astreinte pour les problèmes liés à Protegey
- [ ] **Runbook** : Procédures documentées pour les problèmes courants
- [ ] **Informations de Contact** : Coordonnées du support Protegey accessibles
- [ ] **Plan de Retour Arrière** : Possibilité de désactiver l'intégration Protegey si nécessaire

### Outils

- [ ] **Attribution des Rôles** : Rôles correctement configurés (admin, analyste, lecteur)
- [ ] **Accès API** : Les ingénieurs disposent des clés API de production dans un stockage sécurisé
- [ ] **Favoris du Tableau de Bord** : Les tableaux de bord clés sont mis en favoris pour un accès rapide

## Phase 12 : Mise en Production

### Avant le Lancement

- [ ] **Révision Juridique** : MSA et DPA signés
- [ ] **Questionnaire de Sécurité** : Complété et approuvé
- [ ] **Clés de Production** : Clés API de production générées et sécurisées
- [ ] **Tests de Fumée** : Vérifications de santé de base réussies en production

### Stratégie de Lancement

- [ ] **Mode Ombre** : Fonctionnement en mode ombre pendant 1 semaine (journalisation des scores, sans blocage)
- [ ] **Déploiement Progressif** : Blocage uniquement des risques critiques dans un premier temps (score ≥ 90)
- [ ] **Ajustement des Seuils** : Plan de réduction du seuil après observation des schémas
- [ ] **Communication Client** : Équipe support préparée aux demandes liées à la fraude

### Après le Lancement

- [ ] **Surveillance Quotidienne** : Consultation des tableaux de bord quotidiennement pendant les 2 premières semaines
- [ ] **Révision des Faux Positifs** : Révision des faux positifs et ajustement des seuils
- [ ] **Métriques de Performance** : Suivi du taux de détection de fraude et du taux de faux positifs
- [ ] **Retours de l'Équipe** : Collecte des retours des analystes fraude sur le flux de travail

---

## Phase 13 : Optimisation

### Ajustement des Seuils

- [ ] **Taux de Faux Positifs** : Cible < 10 % de taux de faux positifs
- [ ] **Taux de Détection de Fraude** : Cible > 90 % de taux de détection de fraude
- [ ] **Taux de Révision Manuelle** : Optimisation pour maintenir la file de révision manuelle gérable
- [ ] **Révision Mensuelle** : Planification de réunions mensuelles de révision des seuils

### Optimisation des Flux de Travail

- [ ] **Gabarits de Dossiers** : Création de gabarits pour les types de fraude courants
- [ ] **Actions Automatisées** : Automatisation des tâches de routine (ex. : blocage automatique des fraudeurs confirmés)
- [ ] **Expansion de l'Intégration** : Intégration avec des outils CRM, de tickets ou de BI
- [ ] **Rapports Personnalisés** : Création de rapports personnalisés pour la direction

### Développement des Connaissances

- [ ] **Bibliothèque de Schémas de Fraude** : Documentation des schémas de fraude courants observés
- [ ] **Playbooks d'Investigation** : Création de playbooks pour différents types de fraude
- [ ] **Rétrospectives d'Équipe** : Rétrospectives régulières sur les investigations de fraude
- [ ] **Polyvalence** : Formation croisée des membres de l'équipe sur différentes catégories de fraude
