Le Sandbox (Bac à sable) est conçu pour vous aider à vous intégrer rapidement et en toute sécurité. Il se comporte exactement comme la Production mais utilise des **données physiquement isolées** avec une séparation complète des schémas au niveau de la base de données.

::callout{icon="i-lucide-database" color="blue"}
**Véritable Isolation** : Protegey met en œuvre une séparation physique des schémas de base de données à l'aide des schémas PostgreSQL. Les données du Sandbox résident dans un schéma `sandbox` distinct, garantissant un risque de pollution nul dans les analyses de production.
::

---

## Aperçu de l'Architecture

### Isolation des Schémas de Base de Données

Protegey utilise la **séparation au niveau du schéma PostgreSQL** pour garantir une isolation complète des données entre les environnements sandbox et production :

**Structure des Schémas** :
```
Base de données PostgreSQL
├── schéma public (Production + Tables Partagées)
│   ├── signals (données de production)
│   ├── fraud_entities (données de production)
│   ├── fraud_cases (données de production)
│   ├── users (partagé entre tous les environnements)
│   ├── partners (partagé entre tous les environnements)
│   └── subscriptions (partagé entre tous les environnements)
│
└── schéma sandbox (Données Sandbox)
    ├── signals (données sandbox)
    ├── fraud_entities (données sandbox)
    ├── fraud_cases (données sandbox)
    └── [toutes les tables à portée partenaire dupliquées]
```

**Avantages Clés** :
- **Zéro contamination croisée** : Les signaux sandbox n'affectent jamais les scores de risque de production.
- **Réinitialisation facile des données** : Videz le schéma sandbox sans toucher à la production.
- **Isolation des performances** : Les requêtes sandbox n'impactent pas les performances de la production.
- **Prêt pour la conformité** : Piste d'audit claire montrant la ségrégation des données.

### Comment ça marche

Lorsque vous effectuez une requête API ou que vous vous connectez au portail partenaire :

1. **Détection de l'Environnement** : Le système détecte l'environnement via les paramètres de requête, les cookies, les en-têtes ou le domaine.
2. **Liaison du Contexte** : Crée un objet `CentryContext` avec l'état de l'environnement.
3. **Application du Schéma** : Définit le `search_path` de PostgreSQL sur le schéma correct.
4. **Exécution de la Requête** : Toutes les requêtes de base de données utilisent automatiquement le bon schéma.

**Exemple** :
```sql
-- La requête Sandbox définit le search_path
SET search_path TO sandbox, public;

-- Les requêtes utilisent automatiquement le schéma sandbox
SELECT * FROM signals WHERE partner_uuid = 'votre-uuid';
-- Lit dans : sandbox.signals

-- Les tables partagées utilisent toujours le schéma public
SELECT * FROM users WHERE id = 42;
-- Lit dans : public.users (partagé)
```

**Voir aussi** : [Exécution Sensible au Contexte](./context-resolution) pour un approfondissement technique.

## Garanties de Ségrégation des Données

### Ce qui est Isolé

**Données par Environnement** (dupliquées à travers les schémas) :
- ✅ Signaux de fraude
- ✅ Entités de fraude
- ✅ Dossiers (cases) de fraude
- ✅ Alertes de fraude
- ✅ Transactions
- ✅ Données analytiques
- ✅ Historique des décisions

**Données Partagées** (identiques dans tous les environnements) :
- ✅ Utilisateurs (membres de votre équipe)
- ✅ Paramètres de l'organisation partenaire
- ✅ Abonnements et facturation
- ✅ Rôles et permissions
- ✅ Clés API

### Application de l'Isolation

**Sélection Automatique du Schéma** :
```typescript
// Appel API Sandbox
const client = new ProtegeyClient({
  accessToken: 'VOTRE_JETON',
  environment: 'sandbox'
});

// Toutes les requêtes utilisent automatiquement le schéma sandbox
const signals = await client.signals.list();
// Lit dans : sandbox.signals
```

**Application au Niveau de la Requête** :
- Chaque requête HTTP résout le contexte de l'environnement.
- Le middleware définit le `search_path` de PostgreSQL avant toute requête.
- Aucun préfixage manuel de schéma n'est requis dans le code applicatif.
- Impossible d'interroger accidentellement le mauvais schéma.

**Piste d'Audit** :
- Toutes les opérations sandbox sont enregistrées avec `environment: 'sandbox'`.
- Suivi de l'ID de requête à travers le HTTP et les tâches de file d'attente.
- Application du schéma journalisée pour le débogage.

## Basculer Entre les Environnements

### Méthode 1 : Paramètre de Requête

**Portail Partenaire** :
```
https://partner.protegey.com/dashboard?environment=sandbox
```

**Requête API** :
```bash
curl "https://api.protegey.com/v1/signals?environment=sandbox" \
  -H "Authorization: Bearer VOTRE_JETON"
```

### Méthode 2 : En-tête HTTP

```bash
curl "https://api.protegey.com/v1/signals" \
  -H "Authorization: Bearer VOTRE_JETON" \
  -H "X-Centry-Environment: sandbox"
```

### Méthode 3 : Cookie (Persistant)

```javascript
// Basculer vers le sandbox (persiste entre les requêtes)
document.cookie = 'centry_env_override=sandbox; path=/; max-age=86400';

// Revenir à la production
document.cookie = 'centry_env_override=production; path=/; max-age=86400';
```

**Voir aussi** : [Exécution Sensible au Contexte - Basculer entre Environnements](./context-resolution#basculer-entre-les-environnements) pour toutes les méthodes.

## Fonctionnalité de Réinitialisation

### Options de Réinitialisation Granulaire

Réinitialisez des types de données spécifiques dans votre sandbox sans affecter les autres :

| Option de Réinitialisation | Description | Point de Terminaison API |
|----------------------------|-------------|--------------------------|
| **Réinitialisation Complète** | Effacer toutes les données sandbox | `POST /api/v1/partner/sandbox/reset` |
| **Signaux uniquement** | Effacer les signaux, garder entités et dossiers | `POST /api/v1/partner/sandbox/reset?scope=signals` |
| **Entités uniquement** | Effacer les entités, garder signaux et dossiers | `POST /api/v1/partner/sandbox/reset?scope=entities` |
| **Dossiers uniquement** | Effacer les dossiers, garder signaux et entités | `POST /api/v1/partner/sandbox/reset?scope=cases` |
| **Alertes uniquement** | Effacer les alertes | `POST /api/v1/partner/sandbox/reset?scope=alerts` |
| **Relations** | Effacer les relations entre entités | `POST /api/v1/partner/sandbox/reset?scope=relationships` |

**Exemple de Réinitialisation Complète** :
```bash
curl -X POST "https://api.protegey.com/v1/partner/sandbox/reset" \
  -H "Authorization: Bearer VOTRE_JETON" \
  -H "X-Centry-Environment: sandbox"
```

**Exemple de Réinitialisation Sélective** :
```typescript
// Effacer uniquement les signaux, préserver les profils d'entités
await client.sandbox.reset({ scope: 'signals' });
```

### Ce qui se passe pendant la réinitialisation

**Réinitialisation Complète** :
1. Tous les signaux sandbox sont supprimés (`sandbox.signals`)
2. Toutes les entités sandbox sont supprimées (`sandbox.fraud_entities`)
3. Tous les dossiers sandbox sont supprimés (`sandbox.fraud_cases`)
4. Toutes les alertes sandbox sont supprimées (`sandbox.fraud_alerts`)
5. Les relations entre entités sont effacées
6. Les analyses sont recalculées

**Données Préservées** :
- Comptes utilisateurs (partagés)
- Paramètres partenaire (partagés)
- Clés API (partagées)
- Statut de l'abonnement (partagé)

**État après réinitialisation** :
- Environnement sandbox propre
- Prêt pour de nouveaux tests
- Aucune donnée résiduelle des tests précédents

### Fréquence de Réinitialisation

**Réinitialisation Manuelle** : Disponible à la demande via l'API
**Réinitialisation Automatique** : Hebdomadaire le dimanche à 00h00 UTC (configurable par partenaire)

::callout{icon="i-lucide-alert-circle" color="amber"}
**Important** : La réinitialisation est irréversible. Assurez-vous d'avoir exporté toutes les données dont vous avez besoin avant de réinitialiser.
::

## Meilleures Pratiques de Test

### 1. Utilisez le Sandbox pour tout Développement

Développez et testez toujours le code d'intégration en sandbox avant de passer en production :

```typescript
// ✅ CORRECT : Développer en sandbox
const devClient = new ProtegeyClient({
  accessToken: process.env.SANDBOX_TOKEN,
  environment: 'sandbox'
});

// Testez votre intégration
await devClient.signals.create({...});

// ❌ ERREUR : Développer en production
const prodClient = new ProtegeyClient({
  accessToken: process.env.PROD_TOKEN,
  environment: 'production' // Ne pas utiliser pour les tests !
});
```

### 2. Générez des Signaux de Démo pour les Tests

Utilisez l'API de génération de signaux de démo pour créer des données de test réalistes :

```bash
# Générer 20 signaux de démo avec divers profils de risque
curl -X POST "https://api.protegey.com/v1/partner/sandbox/generate-demo-signals" \
  -H "Authorization: Bearer VOTRE_JETON" \
  -H "X-Centry-Environment: sandbox" \
  -d '{
    "template": "transaction/account_takeover",
    "count": 20
  }'
```

**Distribution des Profils de Risque** :
- 10 % de risque critique (scores 80-100)
- 20 % de risque élevé (scores 60-79)
- 30 % de risque moyen (scores 40-59)
- 40 % de risque faible (scores 0-39)

**Voir aussi** : [Guide des Signaux de Démo](../sandbox/demo-signals) pour les options de modèles.

### 3. Testez les Cas Limites

**Scénarios à Haut Risque** :
```typescript
// Tester les transactions refusées
await client.signals.create({
  transaction_id: 'TXN-TEST-DECLINE-001',
  event_type: 'ACCOUNT_TAKEOVER',
  transaction: {
    amount: 50000, // Un montant élevé déclenche une anomalie
    currency: 'USD'
  },
  actor: {
    hashed_id: 'hash_new_device_001'
  },
  metadata: {
    device_fingerprint: 'new_device',
    country_code: 'NG' // Transfrontalier si le partenaire est au GH
  }
});
```

**Scénarios à Faible Risque** :
```typescript
// Tester les transactions approuvées
await client.signals.create({
  transaction_id: 'TXN-TEST-APPROVE-001',
  event_type: 'LOGIN',
  transaction: {
    amount: 100, // Faible montant
    currency: 'GHS'
  },
  actor: {
    hashed_id: 'hash_returning_user_001'
  },
  metadata: {
    device_fingerprint: 'known_device',
    country_code: 'GH' // Même pays
  }
});
```

### 4. Testez la Gestion des Erreurs

Utilisez les valeurs magiques pour forcer des erreurs (voir section ci-dessous) :

```typescript
try {
  // Forcer une erreur de limite de débit
  await client.signals.create({
    ...signalData,
    headers: { 'X-Force-Error': 'rate_limit' }
  });
} catch (error) {
  if (error.status === 429) {
    console.log('Limite de débit correctement gérée');
  }
}
```

### 5. Réinitialisez entre les Séries de Tests

Réinitialisez les données sandbox entre les suites de tests pour plus de cohérence :

```typescript
// Avant chaque suite de tests
beforeAll(async () => {
  await client.sandbox.reset({ scope: 'signals' });
});

// Exécuter les tests avec un état propre
test('ingestion de signal', async () => {
  const signal = await client.signals.create({...});
  expect(signal.id).toBeDefined();
});
```

### 6. Validez l'Isolation des Données

Vérifiez que les données sandbox ne fuitent pas en production :

```typescript
// Créer un signal en sandbox
const sandboxClient = new ProtegeyClient({
  environment: 'sandbox',
  accessToken: VOTRE_JETON
});

await sandboxClient.signals.create({ transaction_id: 'SANDBOX-001' });

// Passer en production et vérifier que le signal n'existe pas
const prodClient = new ProtegeyClient({
  environment: 'production',
  accessToken: VOTRE_JETON
});

const prodSignals = await prodClient.signals.list({
  search: 'SANDBOX-001'
});

expect(prodSignals.data.length).toBe(0); // Ne devrait pas exister en production
```

### 7. Testez la Livraison des Webhooks

Configurez un point de terminaison de test pour vérifier la livraison des événements :


## Valeurs Magiques

Le Sandbox prend en charge les "Valeurs Magiques" pour forcer des réponses spécifiques. Cela vous permet de tester votre logique pour différents scénarios de risque sans avoir besoin de créer des signaux complexes.

### Forcer les Scores de Risque

Lors de l'interrogation d'une entité (ex : un e-mail), utilisez ces préfixes pour déclencher des scores spécifiques :

| Modèle d'e-mail | Score Résultant | Recommandation |
|-----------------|-----------------|----------------|
| `low_risk_user@example.com` | `10` | APPROVE |
| `med_risk_user@example.com` | `45` | REVIEW |
| `high_risk_user@example.com` | `85` | DECLINE |
| `critical_user@example.com` | `99` | DECLINE |

### Forcer des Erreurs

Pour tester votre gestion des erreurs, passez ces valeurs dans l'en-tête `X-Force-Error` (Sandbox uniquement) :

| Valeur d'en-tête | Réponse HTTP | Scénario |
|------------------|--------------|----------|
| `timeout` | `504 Gateway Timeout` | Simuler une latence réseau |
| `rate_limit` | `429 Too Many Requests` | Simuler un épuisement des quotas |
| `server_error` | `500 Internal Server Error` | Simuler une panne de plateforme |

```bash
# Exemple : Forcer une erreur 429
curl -X GET https://sandbox-api.protegey.com/v1/queries/user \
  -H "X-Centry-Key: cen_test_sk_..." \
  -H "X-Force-Error: rate_limit"
```
