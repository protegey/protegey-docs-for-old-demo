::callout{icon="i-lucide-arrow-right" color="primary"}
**Signaux = ingestion.** Cette API ajoute des événements au graphe d'entités et renvoie un score de risque préliminaire. Pour un scoring en temps réel de données brutes sans créer d'entités, utilisez plutôt l'[API Evaluate](/partners/api-reference/evaluate).
::

L'API des Signaux permet aux partenaires de soumettre des indicateurs de fraude au réseau Protegey. Chaque signal est **validé et évalué de manière synchrone** — un verdict de risque préliminaire est retourné dans la même réponse HTTP. Le traitement asynchrone (liaison au graphe, enrichissement des entités, génération d'alertes) se poursuit en arrière-plan.

> **Vous cherchez autre chose ?**
> - Scoring en temps réel sans persistance → [API Evaluate](/partners/api-reference/evaluate)
> - Intelligence approfondie sur les entités → [API Assess](/partners/api-reference/entities#assess)
> - Ingestion de signaux dans le graphe → [API Signaux](/partners/api-reference/signals)

::callout{icon="i-lucide-shield-alert" color="amber"}
**Accès Production Requis** : Vous devez avoir des clés de production actives pour publier des signaux réels. Les signaux sandbox n'affectent pas les scores du réseau.
::

## Point de terminaison (Endpoint)

```http
POST /api/v1/signals
```

### En-têtes (Headers)

| En-tête           | Valeur                         | Requis     |
| ----------------- | ------------------------------ | ---------- |
| `Content-Type`    | `application/json`             | Oui        |
| `X-Centry-Key`    | `cen_live_sk_...`              | Oui        |
| `Idempotency-Key` | Clé unique (64 caractères max) | Recommandé |

## UFES v2 — Le Seul Format Supporté

Toutes les nouvelles intégrations doivent utiliser **UFES v2** (`schema_version: "2.0"`). Les formats legacy et v1 ont été supprimés du pipeline d'ingestion.

### Champs Requis

| Champ                     | Type    | Description                                                                    |
| ------------------------- | ------- | ------------------------------------------------------------------------------ |
| `schema_version`          | `"2.0"` | Doit être exactement `"2.0"`                                                   |
| `event_type`              | string  | Type d'événement libre (ex : `MOBILE_MONEY_SEND`, `LOGIN_FAILURE`, `SIM_SWAP`) |
| `timestamp`               | string  | Datetime ISO 8601                                                              |
| `source`                  | object  | Métadonnées de la source de soumission                                         |
| `source.confidence_score` | number  | 0.0–1.0 — votre niveau de confiance que cet événement est lié à la fraude      |
| `primary_actor`           | object  | L'entité effectuant l'action                                                   |
| `primary_actor.entity_id` | string  | Votre identifiant interne stable pour cette entité                             |

::callout{icon="i-lucide-info" color="blue"}
`event_category` est **optionnel** — il est automatiquement dérivé de `event_type` lorsqu'il est omis (ex : `TRANSFER` → `transaction`, `LOGIN` → `auth`, `SIM_SWAP` → `auth`). Fournissez-le explicitement uniquement si la dérivation automatique ne correspond pas à votre cas d'usage.
::

### Schéma Complet

```typescript
interface UFESv2Signal {
  // ── Enveloppe (requis) ───────────────────────────────────────────
  schema_version: "2.0";
  event_type: string; // ex : "MOBILE_MONEY_SEND", "SIM_SWAP", "LOGIN_FAILURE"
  timestamp: string; // ISO 8601

  // ── Enveloppe (optionnel) ────────────────────────────────────────
  event_category?: "transaction" | "auth" | "kyc" | "fraud_signal" | "system";
  flow_type?: "payment" | "auth" | "kyc"; // auto-inféré depuis event_category si omis
  trace_id?: string; // votre identifiant de traçage inter-systèmes

  // ── Source ───────────────────────────────────────────────────────
  source: {
    confidence_score: number; // 0.0–1.0, requis
    integration_channel?: "api" | "batch" | "stream";
    partner_user_id?: string; // votre référence interne
    ip_address?: string; // IP de l'utilisateur soumettant — alimente le détecteur IMPOSSIBLE_TRAVEL
  };

  // ── Primary actor (required — one plaintext identifier required) ─
  primary_actor: {
    entity_id?: string; // your stable internal ID for this actor
    entity_type?: "individual" | "business" | "account" | "device";
    display_name?: string;

    // ── Plaintext identifiers (submit as-is; Protegey normalizes + hashes) ──
    // At least one of the following is required.
    phone?: string; // E.164 recommended (e.g. "+233241234567"); spaces stripped
    email?: string; // any casing; trimmed + lowercased server-side
    account?: string; // any account reference; trimmed + lowercased server-side
    national_id?: string; // any casing; uppercased + spaces stripped server-side

    // ── Secondary identifiers (all plaintext → all hashed server-side) ────
    identifiers?: {
      msisdn?: string; // alias for phone
      bvn?: string; // 11-digit Bank Verification Number (Nigeria)
      tin?: string; // Tax Identification Number
      passport_number?: string;
      driver_license?: string;
      voter_id?: string;
      pan?: string; // Payment card number (13–19 digits)
      iban?: string;
      wallet_address?: string;
      name?: string; // display name — lowercased + collapsed spaces
      region?: string; // ISO 3166-1 alpha-2 country code (e.g. "GH")
      sim_changed_at?: string; // ISO 8601 — feeds SIM_SWAP_PROXIMITY detector
    };

    // ── Device ────────────────────────────────────────────────────────────
    device?: {
      fingerprint?: string; // opaque fingerprint (max 255 chars) — feeds NEW_DEVICE_ACCESS
      ip_address?: string; // device IP
      user_agent?: string; // raw UA string (max 512 chars)
      imei?: string; // 15 digits — hashed server-side
      sim_iccid?: string; // 18–20 digits — hashed server-side
    };
    risk_flags?: string[]; // e.g. ["high_velocity", "new_device"]
  };

  // ── Entités liées (optionnel) ────────────────────────────────────
  related_entities?: Array<{
    entity_id: string;
    entity_type?: string;
    relationship_type?:
      | "sender"
      | "receiver"
      | "beneficiary"
      | "shared_device"
      | "linked_account"
      | "mule"
      | "director"
      | "proxy";
  }>;

  // ── Payload d'événement (optionnel, données spécifiques à la catégorie) ─
  event_payload?: {
    amount?: number;
    currency?: string;
    reference_id?: string;
    geo_location?: { lat: number; lng: number };
    [key: string]: any;
  };

  // ── Blocs d'intelligence partenaire (optionnel, piste d'audit uniquement) ─
  risk_intelligence?: {
    risk_score?: number;
    risk_level?: "low" | "medium" | "high" | "critical";
    risk_factors?: string[];
    model_version?: string;
  };
  compliance_context?: {
    jurisdiction?: string;
    regulatory_flags?: string[];
    screening_results?: Record<string, any>[];
  };
  // ── Décision partenaire (v2.1) ───────────────────────────────────
  partner_decision?: {
    decision?: "approve" | "deny" | "review" | "block" | "escalate";
    decision_type?: "manual" | "automated" | "hybrid";
    timestamp?: string;
    rationale?: string;
    policy_id?: string;
  };

  // ── Résultat (v2.1) ───────────────────────────────────────────────
  event_outcome?: "success" | "failure" | "blocked" | "reversed";
  event_outcome_source?: "partner" | "system" | "regulator";
  fraud_outcome?: "fraud" | "legitimate" | "suspected" | "unknown";
  fraud_type?: "account_takeover" | "scam" | "laundering" | "mule" | "unknown";
  case_id?: string;

  metadata?: Record<string, any>;
}
```

### Dérivation Automatique de la Catégorie d'Événement

Lorsque `event_category` est omis, Protegey le dérive depuis `event_type` :

| `event_category` | Valeurs `event_type` auto-associées                                                                                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth`           | `LOGIN`, `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `SIM_SWAP`, `ACCOUNT_TAKEOVER`, `ACCOUNT_UPDATE`, `MFA_BYPASS`, `PASSWORD_RESET`, `DEVICE_ANOMALY` |
| `transaction`    | `PAYMENT`, `TRANSFER`, `WITHDRAWAL`, `MOBILE_MONEY_SEND`, `CARD_FRAUD`, `PAYMENT_FRAUD`                                                       |
| `kyc`            | `ACCOUNT_CREATE`, `ACCOUNT_OPENING`, `KYC_CHECK`, `DOCUMENT_VERIFY`, `IDENTITY_THEFT`                                                         |
| `fraud_signal`   | Tout le reste                                                                                                                                 |

## Champs Requis par les Détecteurs

Protegey exécute **cinq détecteurs** sur chaque signal. Certains détecteurs nécessitent des champs spécifiques pour se déclencher. Fournir ces champs maximise la qualité de votre évaluation de risque.

| Détecteur                    | Champ requis                    | Où le fournir                                         |
| ---------------------------- | ------------------------------- | ----------------------------------------------------- |
| `RAPID_TRANSACTION_VELOCITY` | ID de l'acteur + signaux passés | `primary_actor.entity_id`                             |
| `LARGE_OUTLIER_TRANSACTION`  | Montant de la transaction       | `event_payload.amount` + `event_payload.currency`     |
| `SIM_SWAP_PROXIMITY`         | Horodatage du changement de SIM | `primary_actor.identifiers.sim_changed_at` (ISO 8601) |
| `NEW_DEVICE_ACCESS`          | Empreinte d'appareil            | `primary_actor.device.fingerprint`                    |
| `IMPOSSIBLE_TRAVEL`          | Adresse IP de soumission        | `source.ip_address`                                   |

::callout{icon="i-lucide-zap" color="primary"}
**Enrichissez chaque signal** : Fournir `source.ip_address`, `primary_actor.device.fingerprint` et `primary_actor.identifiers.sim_changed_at` là où cela est applicable augmente significativement la précision de détection — notamment pour les schémas de SIM swap et de prise de contrôle de compte fréquents dans la fraude mobile money africaine.
::

## Traitement de la Confidentialité Côté Serveur

Protegey **ne stocke jamais les PII en clair**. Soumettez les identifiants en texte brut — le serveur les normalise et les hache automatiquement via **HMAC-SHA256 avec la clé réseau partagée** avant tout stockage ou liaison au graphe.

::callout{icon="i-lucide-shield-alert" color="red"}
**Ne pré-hachez PAS les identifiants.** Soumettre une valeur déjà hachée provoque un double hachage côté serveur, ce qui brise la correspondance d'entités inter-institutions. Soumettez toujours des identifiants bruts et non modifiés.
::

### Normalisation Automatique

Le serveur applique une normalisation spécifique au type avant le hachage :

| Type                  | Normalisation Appliquée                | Exemple de Saisie      | Forme Canonique    |
| --------------------- | -------------------------------------- | ---------------------- | ------------------ |
| Téléphone (MSISDN)    | E.164 via libphonenumber               | `0244 123 456`         | `+233244123456`    |
| Email                 | minuscules + suppression des espaces   | `User@Example.COM `    | `user@example.com` |
| Compte                | minuscules + suppression des espaces   | `ACC-00123456`         | `acc-00123456`     |
| Identité nationale    | majuscules + suppression des espaces   | `gh 12 34`             | `GH1234`           |
| BVN                   | chiffres uniquement, 11 caractères     | `123-456-789-01`       | `12345678901`      |
| PAN                   | chiffres uniquement, 13–19 caractères  | `4111 1111 1111 1111`  | `4111111111111111` |
| IMEI                  | chiffres uniquement, 15 caractères     | `35-387923-456789-0`   | `353879234567890`  |

Chaque valeur normalisée est préfixée par son type avant le hachage (ex : `phone:+233244123456`), de sorte que deux types d'identifiants différents qui se normalisent en la même chaîne ne produisent jamais le même hachage.

## Réponse

### Succès (`201 Created`)

L'ingestion du signal est **synchrone** — une évaluation de risque préliminaire s'exécute en ligne et est retournée immédiatement. Il s'agit d'un score rapide calculé au moment de l'ingestion, basé sur les données d'entité disponibles. Pour une évaluation complète avec un niveau de confiance total et des explications, utilisez `POST /risk/assess` avec l'UUID de l'entité.

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "event_type": "PAYMENT_FRAUD",
    "timestamp": "2026-03-20T10:00:00Z",
    "risk_score": 0.7821,
    "risk_level": "high",
    "detectors_triggered": [
      "RAPID_TRANSACTION_VELOCITY"
    ],
    "taxonomy": "payment.structuring",
    "normalization": {
      "event_type_submitted": "momo_send",
      "event_type_resolved": "PAYMENT_FRAUD",
      "event_type_status": "aliased",
      "match_confidence": 0.85,
      "taxonomy_applied": "payment.mobile_money"
    }
  }
}
```

`ingestion_quality` est inclus lorsque la charge utile manque de champs à fort impact. Voir [Qualité d'Ingestion](#ingestion-quality) ci-dessous.

### Niveaux de Risque

| `risk_level` | Plage de `risk_score` | Action recommandée                                          |
| ------------ | --------------------- | ----------------------------------------------------------- |
| `critical`   | 0.81 – 1.00           | Bloquer immédiatement, ouvrir une investigation             |
| `high`       | 0.51 – 0.80           | Exiger une vérification supplémentaire ou mettre en attente |
| `medium`     | 0.21 – 0.50           | Authentification renforcée ou révision manuelle             |
| `low`        | 0.00 – 0.20           | Autoriser — signal de fraude faible                         |

### Détecteurs

| ID du Détecteur              | Ce qu'il détecte                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------- |
| `RAPID_TRANSACTION_VELOCITY` | Fréquence de transaction inhabituellement élevée sur une courte période          |
| `LARGE_OUTLIER_TRANSACTION`  | Montant de transaction bien au-dessus de la ligne de base historique de l'acteur |
| `SIM_SWAP_PROXIMITY`         | Transaction de haute valeur dans les 24h suivant un changement de SIM            |
| `NEW_DEVICE_ACCESS`          | Activité depuis une empreinte d'appareil jamais vue pour cet acteur              |
| `IMPOSSIBLE_TRAVEL`          | Impossibilité géographique entre deux événements consécutifs                     |

### Erreur de Validation (`422 Unprocessable Content`)

```json
{
  "message": "The primary_actor.entity_id field is required.",
  "errors": {
    "primary_actor.entity_id": [
      "The primary_actor.entity_id field is required."
    ]
  }
}
```

### Erreurs de Validation Courantes

| Erreur                                                                        | Cause                                                                       |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `primary_actor.entity_id is required`                                         | Payload UFES v2 sans `primary_actor.entity_id`                              |
| `event_category must be one of: auth, transaction, kyc, fraud_signal, system` | Valeur de catégorie invalide — ou omettez-la pour la dérivation automatique |
| `flow_type must be one of: kyc, payment, auth`                                | `flow_type` explicite hors de l'enum autorisé                               |
| `primary_actor.device.fingerprint may not be greater than 255 characters`     | Tronquez l'empreinte à 255 caractères                                       |
| `related_entities.0.relationship_type is invalid`                             | Type de relation inconnu                                                    |
| `source.integration_channel is invalid`                                       | Canal absent de `api, batch, stream`                                        |

## Idempotence

Utilisez l'en-tête `Idempotency-Key` pour réessayer sans risque les requêtes échouées sans créer de signaux en double.

**Règles :**

- La clé doit être unique par signal logique (UUID recommandé)
- Maximum 64 caractères
- Les clés sont limitées au périmètre du partenaire et expirent après 24 heures
- Les réponses `4xx` ne sont jamais mises en cache — réessayer un mauvais payload ne rejoue pas une erreur en cache
- En cas de relecture, la réponse inclut `X-Idempotency-Replayed: true`

**Exemple — réessai avec backoff exponentiel :**

```javascript
async function submitSignal(payload, idempotencyKey, retries = 3) {
  for (let attempt = 0; attempt < retries; attempt++) {
    try {
      const response = await fetch("https://api.protegey.com/v1/signals", {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "X-Centry-Key": process.env.PROTEGEY_SECRET_KEY,
          "Idempotency-Key": idempotencyKey, // same key on every retry
        },
        body: JSON.stringify(payload),
      });

      if (response.ok) return await response.json();
      if (response.status < 500)
        throw new Error(`Client error: ${response.status}`);

      // 5xx — wait and retry
      await new Promise((r) => setTimeout(r, Math.pow(2, attempt) * 1000));
    } catch (err) {
      if (attempt === retries - 1) throw err;
    }
  }
}

// Generate key once, before the first attempt
const signalKey = crypto.randomUUID();
await submitSignal(payload, signalKey);
```

::callout{icon="i-lucide-info" color="blue"}
**Bonne pratique** : Générez la clé d'idempotence **avant** d'envoyer la première requête. Stockez-la avec le signal dans votre système afin de pouvoir réutiliser la même clé à chaque réessai, quel que soit le temps écoulé.
::

## Champs de Réponse v2.1

### Retour de Normalisation

Chaque réponse d'ingestion inclut un bloc `normalization` indiquant comment votre `event_type` a été résolu.

```json
{
  "normalization": {
    "event_type_submitted": "momo_send",
    "event_type_resolved": "PAYMENT_FRAUD",
    "event_type_status": "aliased",
    "match_confidence": 0.85,
    "taxonomy_applied": "payment.mobile_money"
  }
}
```

| `event_type_status` | `match_confidence` | Signification |
|---------------------|--------------------|---------------|
| `canonical` | `1.0` | Type UFES canonique exact |
| `aliased` | `0.85` | Alias enregistré (ex. `sim_swap` → `ACCOUNT_TAKEOVER`) |
| `aliased` | `0.65` | Déduit de `event_category` uniquement |
| `unknown` | `0.0` | Non reconnu — scoré à la sévérité par défaut `0.10` |

### Qualité d'Ingestion

Lorsque des champs importants sont manquants, la réponse inclut un bloc `ingestion_quality`. Ce bloc est **omis pour les charges utiles complètes**.

```json
{
  "ingestion_quality": {
    "completeness_score": 0.60,
    "missing_recommended": ["source.ip_address", "primary_actor.device.fingerprint"],
    "improvement_suggestions": [
      {
        "field": "source.ip_address",
        "impact": "high",
        "reason": "required for IMPOSSIBLE_TRAVEL detection"
      }
    ]
  }
}
```

## Enregistrer un Résultat

```http
PATCH /api/v1/signals/{id}/outcome
```

`{id}` accepte soit le `signal_id` attribué par Protegey (UUID de la réponse d'ingestion), soit votre propre `trace_id` soumis au moment de l'ingestion. L'utilisation du `trace_id` vous évite de stocker l'UUID de Protegey dans votre système.

```http
PATCH /api/v1/signals/TXN-2026-03-20-001/outcome   ← trace_id
PATCH /api/v1/signals/9df4a3b1-c2e3-4f56.../outcome ← signal_id
```

Soumettez le résultat réel une fois le verdict de fraude connu — des jours ou des semaines après le signal initial.

```json
{
  "event_outcome": "blocked",
  "event_outcome_source": "partner",
  "fraud_outcome": "fraud",
  "fraud_type": "scam",
  "outcome_timestamp": "2026-03-20T14:30:00Z"
}
```

`event_outcome` (opérationnel) et `fraud_outcome` (analytique) sont intentionnellement séparés : une transaction `blocked` n'est pas nécessairement `fraud`.

## Normalisation du Téléphone

Lorsque vous soumettez un signal contenant un numéro de téléphone via `primary_actor.identifiers.msisdn`, le système le convertit automatiquement au format canonique E.164 avant le hachage et la liaison au graphe.

### Marchés Pris en Charge

| Pays               | Code ISO | Exemples de Formats Locaux    | Résultat (E.164) |
| ------------------ | -------- | ----------------------------- | ---------------- |
| **Ghana**          | `GH`     | `024 123 4567`, `241234567`   | `+233241234567`  |
| **Nigeria**        | `NG`     | `0803 123 4567`, `7012345678` | `+2348031234567` |
| **Sénégal**        | `SN`     | `077 123 45 67`, `771234567`  | `+221771234567`  |
| **Côte d'Ivoire**  | `CI`     | `07 01 23 45 67`              | `+2250701234567` |
| **Kenya**          | `KE`     | `0712 345678`                 | `+254712345678`  |
| **Afrique du Sud** | `ZA`     | `082 123 4567`                | `+27821234567`   |
| **Maroc**          | `MA`     | `06 12 34 56 78`              | `+212612345678`  |
| **Égypte**         | `EG`     | `010 1234 5678`               | `+201012345678`  |

::callout{icon="i-lucide-lightbulb" color="primary"}
**Bonne Pratique** : Fournissez toujours le `identifiers.region` de l'acteur (code pays ISO) lors de la soumission de numéros de téléphone. Cela garantit une précision de normalisation de 100 % pour les formats locaux ambigus ou se chevauchant.
::

::callout{icon="i-lucide-info" color="blue"}
**La fusion de risque pondérée est asynchrone.** Le `risk_score` dans la réponse `201` est le score synchrone au moment de l'ingestion (couche de détecteurs uniquement). La fusion complète — Comportemental (35 %) + Réseau/Graphe (40 %) + Contextuel (15 %) + Historique (10 %) — s'exécute de manière asynchrone après la liaison du graphe d'entités et est livrée via l'événement webhook `signal.ingested`. Cela se termine généralement dans les 2 à 5 secondes suivant l'ingestion.
::

Le `fused_score` (0,0–1,0) est multiplié par 100 pour produire `risk_score`.

### Référence des détecteurs

Cinq détecteurs s'exécutent sur chaque signal. Chacun requiert des champs spécifiques — les champs manquants entraînent le saut du détecteur (sans échec).

| ID du détecteur | Condition de déclenchement | Champ(s) requis |
|-------------|-------------------|-------------------|
| `RAPID_TRANSACTION_VELOCITY` | ≥ 10 transactions/heure pour la même entité | `primary_actor.entity_id` |
| `LARGE_OUTLIER_TRANSACTION` | Z-score ≥ 3,0 par rapport à la ligne de base de l'entité sur 90 jours | `event_payload.amount` + `event_payload.currency` |
| `SIM_SWAP_PROXIMITY` | Changement d'appareil ou de localisation dans les 2h suivant un événement de SIM swap | `primary_actor.identifiers.sim_changed_at` |
| `NEW_DEVICE_ACCESS` | Empreinte d'appareil vue pour la première fois combinée à une géographie à haut risque | `primary_actor.device.fingerprint` |
| `IMPOSSIBLE_TRAVEL` | Même entité dans deux pays différents en 2h | `source.ip_address` (enrichi en géo par le résolveur) |

`detectors_triggered` dans la réponse liste uniquement les détecteurs qui se sont **déclenchés** (ayant atteint leur seuil). Les 5 sont évalués dans tous les cas.
