# API des Signaux

L'API des Signaux permet aux partenaires de soumettre des indicateurs de fraude au réseau Protegey. Les signaux sont validés de manière synchrone, puis traités de façon asynchrone par le Moteur de Risque.

::callout{icon="i-lucide-shield-alert" color="amber"}
**Accès Production Requis** : Vous devez avoir des clés de production actives pour publier des signaux réels. Les signaux sandbox n'affectent pas les scores du réseau.
::

## Point de terminaison (Endpoint)

```http
POST /api/v1/signals
```

### En-têtes (Headers)

| En-tête | Valeur | Requis |
|--------|-------|--------|
| `Content-Type` | `application/json` | Oui |
| `X-Centry-Key` | `cen_live_sk_...` | Oui |

---

## Formats de Schéma

Protegey prend en charge quatre formats de payload pour une flexibilité maximale. **UFES v2 est le format recommandé** pour toutes les nouvelles intégrations.

| Format | Déclencheur | Utilisation |
|--------|------------|-------------|
| **UFES v2** | `schema_version: "2.0"` présent | Nouvelles intégrations — fonctionnalités complètes |
| **UFES v1** | `event_id` + `event_type` + `source` présents | Intégrations UFES existantes |
| **Flexible** | `event_type` présent, sans `event_id`/`source` | Intégrations modernes légères |
| **Legacy** | `signal_id` + `type` + `severity` présents | Intégrations pré-UFES |

Tous les formats sont normalisés en interne vers UFES avant traitement. Aucune migration n'est requise si vous envoyez déjà des payloads v1 ou flexibles.

## UFES v2 (Recommandé)

UFES v2 introduit des acteurs typés, des graphes d'entités liées, une classification des événements par catégorie, et des blocs d'intelligence partenaire optionnels.

### Champs Requis

| Champ | Type | Description |
|-------|------|-------------|
| `schema_version` | `"2.0"` | Doit être exactement `"2.0"` pour activer le chemin v2 |
| `event_id` | string | Identifiant unique de cet événement (UUID recommandé) |
| `event_category` | string | Enum de catégorie — voir [Catégories d'événements](#catégories-dévénements) |
| `event_type` | string | Libellé de type d'événement libre (ex : `MOBILE_MONEY_SEND`, `LOGIN_FAILURE`) |
| `timestamp` | string | Datetime ISO 8601 |
| `source` | object | Métadonnées de la source de soumission |
| `primary_actor` | object | L'entité effectuant l'action |
| `primary_actor.entity_id` | string | Votre identifiant interne pour cette entité |

### Schéma Complet

```typescript
interface UFESv2Signal {
  // Enveloppe
  schema_version: "2.0";
  event_id: string;
  event_category: "transaction" | "auth" | "kyc" | "fraud_signal" | "system";
  event_type: string;
  flow_type?: "payment" | "auth" | "kyc"; // inféré automatiquement si omis
  trace_id?: string;                       // pour le traçage inter-systèmes
  timestamp: string;                       // ISO 8601

  // Source
  source: {
    confidence_score?: number;             // 0.0–1.0, défaut 0.5
    integration_channel?: "api" | "batch" | "stream";
    partner_user_id?: string;              // votre référence interne
    // partner_id est défini automatiquement depuis votre clé API
  };

  // Acteur principal (requis)
  primary_actor: {
    entity_id: string;                     // requis
    entity_type?: "individual" | "business" | "account" | "device";
    hashed_id?: string;                    // SHA-256 des PII, pour la liaison au graphe
    identifiers?: {
      msisdn?: string;
      email?: string;
      [key: string]: string | undefined;
    };
    risk_flags?: string[];                 // ex : ["high_velocity", "new_device"]
  };

  // Entités liées (optionnel)
  related_entities?: Array<{
    entity_id: string;
    entity_type?: string;
    relationship_type?:
      | "sender" | "receiver" | "beneficiary"
      | "shared_device" | "linked_account"
      | "mule" | "director" | "proxy";
  }>;

  // Payload d'événement (optionnel, données spécifiques à la catégorie)
  event_payload?: Record<string, any>;

  // Blocs d'intelligence partenaire (optionnel, stockés comme piste d'audit)
  risk_intelligence?: {
    risk_score?: number;                   // 0.0–1.0
    risk_level?: "low" | "medium" | "high" | "critical";
    risk_factors?: string[];
    model_version?: string;
  };
  compliance_context?: {
    jurisdiction?: string;                 // ISO 3166-1 alpha-2
    regulatory_flags?: string[];
    screening_results?: Record<string, any>[];
  };
  decision_context?: {
    final_decision?: "approve" | "deny" | "review" | "block" | "escalate";
    decision_timestamp?: string;
    decision_rationale?: string;
    policy_id?: string;
  };

  metadata?: Record<string, any>;
}
```

### Catégories d'événements

Le champ `event_category` classe le signal dans l'une des cinq catégories. Le `flow_type` est automatiquement inféré si non fourni explicitement.

| `event_category` | `flow_type` inféré | Valeurs `event_type` typiques |
|---|---|---|
| `transaction` | `payment` | `MOBILE_MONEY_SEND`, `CARD_PAYMENT`, `SEND_MONEY` |
| `auth` | `auth` | `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `MFA_BYPASS`, `SIM_SWAP` |
| `kyc` | `kyc` | `ACCOUNT_CREATE`, `DOCUMENT_VERIFY`, `KYC_CHECK` |
| `fraud_signal` | `payment` | `PAYMENT_FRAUD`, `ACCOUNT_TAKEOVER`, `SOCIAL_ENGINEERING` |
| `system` | `payment` | Événements de télémétrie générés par le système |

### Blocs d'Intelligence

Les trois blocs d'intelligence optionnels (`risk_intelligence`, `compliance_context`, `decision_context`) vous permettent de transmettre vos propres signaux pré-calculés avec l'événement brut. Ils sont stockés dans les métadonnées du signal comme piste d'audit, mais **n'influencent pas le scoring de Protegey** — le Moteur de Risque de Protegey s'exécute indépendamment.

::callout{icon="i-lucide-info" color="blue"}
Utilisez les blocs d'intelligence lorsque vous souhaitez conserver une trace de la décision de votre système aux côtés de l'évaluation de Protegey, par exemple pour des rapports réglementaires ou des revues post-incident.
::

```bash

  -H "Content-Type: application/json" \

    "event_category": "transaction",
    "event_type": "MOBILE_MONEY_SEND",
    "timestamp": "2026-02-19T10:30:00+00:00",
    "source": {
      "confidence_score": 0.85,
      "integration_channel": "api"
    },
    "primary_actor": {
      "entity_id": "user-abc-123",
      "entity_type": "individual",
      "hashed_id": "a665a45920422f9d417e4867efdc4fb8a04a1f3fff1fa07e998e86f7f7a27ae3",
      "identifiers": {
        "msisdn": "+233501234567"
      },
      "risk_flags": ["high_velocity"]
    },
    "related_entities": [
      {
        "entity_id": "beneficiaire-789",
        "entity_type": "individual",
        "relationship_type": "receiver"
      }
    ],
    "event_payload": {
      "amount": 2500.00,

    }
  }'
```

## Normalisation du Téléphone

Protegey utilise une **Stratégie de Normalisation à Niveaux** pour garantir une haute qualité de données pour les entités basées sur le téléphone. Lorsque vous soumettez un signal contenant un numéro de téléphone (via `primary_actor.identifiers.msisdn` en v2, ou `actor.msisdn` en format flexible), le système le convertit automatiquement au format canonique E.164.

### Marchés Pris en Charge

| Pays | Code ISO | Exemples de Formats Locaux | Résultat (E.164) |
|---------|----------|-----------------------|----------------|
| **Sénégal** | `SN` | `077 123 45 67`, `771234567` | `+221771234567` |
| **Côte d'Ivoire** | `CI` | `07 01 23 45 67`, `0102030405` | `+2250701234567` |
| **Mali** | `ML` | `07123456`, `6123456` | `+2237123456` |
| **Burkina Faso** | `BF` | `54123456`, `76123456` | `+22654123456` |
| **Cameroun** | `CM` | `690123456` | `+237690123456` |
| **RD Congo** | `CD` | `810123456`, `990123456` | `+243810123456` |
| **Maroc** | `MA` | `06 12 34 56 78`, `612345678` | `+212612345678` |
| **Algérie** | `DZ` | `05 12 34 56 78`, `512345678` | `+213512345678` |
| **Tunisie** | `TN` | `21 123 456`, `98123456` | `+21621123456` |
| **Égypte** | `EG` | `010 1234 5678`, `1112345678` | `+201012345678` |
| **Ghana** | `GH` | `024 123 4567`, `241234567` | `+233241234567` |
| **Nigeria** | `NG` | `0803 123 4567`, `7012345678` | `+2348031234567` |

::callout{icon="i-lucide-lightbulb" color="primary"}
**Meilleure Pratique** : Fournissez toujours le code pays (ISO 3166-1 alpha-2) si connu. Cela garantit une précision de normalisation de 100% même pour les formats locaux complexes ou ambigus.
::

## Réponse

### Succès (`201 Created`)

```json
{
  "success": true,
  "data": {
    "signal_id": "9df4a3b1-c2e3-4f56-a789-b0c1d2e3f456",
    "status": "received",
    "event_type": "MOBILE_MONEY_SEND",
    "timestamp": "2026-02-19T10:30:00+00:00"
  },
  "message": "Signal received and queued for processing"
}
```

### Erreur de Validation (`422 Unprocessable Content`)

```json
{
  "message": "The primary_actor.entity_id field is required.",
  "errors": {
    "primary_actor.entity_id": [
      "The primary_actor.entity_id field is required."
    ]
  }
}
```

### Erreurs de Validation Courantes

| Erreur | Cause |
|-------|-------|
| `primary_actor.entity_id is required` | Payload UFES v2 sans `primary_actor.entity_id` |
| `event_category must be one of: auth, transaction, kyc, fraud_signal, system` | Valeur de catégorie invalide |
| `flow_type must be one of: kyc, payment, auth` | `flow_type` explicite hors de l'enum autorisé |
| `related_entities.0.relationship_type is invalid` | Type de relation inconnu |
| `decision_context.final_decision is invalid` | Décision absente de `approve, deny, review, block, escalate` |
| `source.integration_channel is invalid` | Canal absent de `api, batch, stream` |
